# B-2: Carry one transit/parking-zone status on the study so every option reads it (check C-8)

| | |
|---|---|
| From lane | B |
| Owner of the file(s) | C (per OWNERSHIP.yaml: `packages/contracts/**`, the study/results wiring) |
| Files | `packages/contracts/schemas/v1/` (a study-level slot, or a `results` slot; description + shape); regenerated TypeScript; bundled copies under `services/api/app/_contract_schemas/**`; the option/results assembly that reads site facts |
| Why | Queue B-10 (plan check C-8: "Parking or transit status is applied identically across all options"). The reviewed competitor report fails C-8 - one scenario needs 16 parking spaces while others claim a 0-space transit exemption (competitor review section B, rows 58-63) - because each option decided parking for itself. Lane B now resolves the lot's transit-zone classification ONCE from one official source (PLUTO `transitzone`, dataset `64uk-42ks`, version-pinned and assessed by B-06): `services/api/app/profile/transit_parking.py` `resolve_transit_parking_status(profile)` -> `TransitParkingStatus`, and `applied_to_options(status, option_ids)` hands every option the identical value. The site_fact `key` enum is closed and has no transit/parking key, and the study/results contracts have no slot for this status, so it cannot yet travel to the options, Lane D (details) or Lane E (report). |
| What is blocked | Attaching the one status to the study so every option reads it (and so C-8 can be checked automatically). Until then, consumers call `resolve_transit_parking_status(...)` / `applied_to_options(...)` directly. B-10's own tests do not need the change. |
| Proposed change | **1. A single study-level transit/parking slot (additive).** Add a `transit_parking` object carried once per study (not per option): `{ "lot_bbl": bbl, "status": "recorded" \| "check_needed", "transit_zone": non_empty_string \| null, "source": site_fact `source` object \| null, "detail": non_empty_string, "missing_source": non_empty_string \| null }`, `additionalProperties: false`. The producer shape is `TransitParkingStatus.to_dict()` (its `status_label` is display-only and may be dropped or kept). Because it is carried once and read by every option, options cannot disagree; the C-8 check is "every option's transit/parking status is this one object". **2. Keep the legal boundary.** `transit_parking` is a DATA fact only - PLUTO's recorded transit-zone classification. It never states a parking requirement, a waiver, or a number of spaces; that is a rule-engine (Lane A) determination confirmed at G6. The parking-specific DCP layers (Appendix I Transit Zones `dpnc-b2hd`, Greater Transit Zone `vhqf-adkz`) have no registered connector, so any parking-rule use of them stays "Check needed". **3. B-06 pinning.** `transit_parking.source` is a site_fact `source`, so `app.profile.data_versions` already pins it and can mark it "Out of date" / "Version unknown"; no extra wiring needed there. |
| State | open |
