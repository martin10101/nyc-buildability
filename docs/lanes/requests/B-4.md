## Decisions this hands to Lane C (B states a recommendation; Lane C decides)

The probe adds one network call to study assembly, so two product decisions are Lane C's, not B's:

1. **When the probe fails (timeout / outage / rate-limit / schema drift).** The probe raises the
   same typed errors as `fetch_by_bbl` (`SourceTimeoutError`, `SourceUnavailableError`,
   `RateLimitedError`, `SchemaDriftError`). Two options:
   - (a) **Fall back to retrieval-only** — catch the typed error, log it with the correlation id,
     and call `assess_data_versions(pins, published_from_pins(pins))` exactly as today. The study
     still assembles; PLUTO facts read "current" (today's behaviour) because no independent newer
     version is on record.
   - (b) **Mark version_unknown** — when the probe fails, leave out the probe's `PublishedVersion`
     AND drop the retrieval-only self-observation for PLUTO so the pin has nothing to compare with,
     which the rule already turns into `version_unknown` ("Version unknown", fail-closed, never
     current).

   **B recommends (a) retrieval-only fallback.** Reasons: it fails *open to today's behaviour* rather
   than degrading every PLUTO fact to "Version unknown" on a transient city-API blip (the probe is a
   best-effort freshness signal, not a correctness gate); it keeps the study assembling under an
   outage (platform principle: conflicts/stale data stay visible, but a transient probe failure is
   not evidence the pin is stale); and "Out of date" simply does not fire until a probe succeeds,
   which is honest — we have not *seen* a newer version. If the owner later wants an outage to be
   loud, (b) is a one-line switch. Either way, surface the probe failure (correlation id + error
   type) so it is visible, never swallowed silently.

2. **Caching / probe frequency.** The published PLUTO version changes at most monthly (minor) /
   quarterly (major) per the README release model, while a study may assemble many times. Options:
   one probe **per process per N minutes** (a small TTL cache keyed on the dataset), vs **per
   request**. **B recommends a short per-process TTL cache (e.g. 15-30 min), Lane C to pick N**, so a
   burst of studies shares one freshness observation and the city API is not hit once per study
   (polite shared-pool use, matching the connector's tokenless-pool note). The probe is pure w.r.t.
   its inputs and injectable (transport/clock/correlation_id), so a cache wrapper is straightforward
   and testable offline. B has **not** built the cache — where it lives (assembly layer vs a small
   Lane C helper) is Lane C's call, as is N.

B built only the library pieces (probe + adapter + tests); it did not touch `study_inputs.py` or add
any caching, so the fallback and cache decisions above are genuinely open for Lane C.
