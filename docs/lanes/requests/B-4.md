## Decisions this hands to Lane C (B states a recommendation; Lane C decides)

The probe adds one network call to study assembly, so two product decisions are Lane C's, not B's:

1. **When the probe fails (timeout / outage / rate-limit / schema drift).** The probe raises the
   same typed errors as `fetch_by_bbl` (`SourceTimeoutError`, `SourceUnavailableError`,
   `RateLimitedError`, `SchemaDriftError`). There is a real trap here, so this is **decided**, not
   open.

   **The fail-open risk, plainly.** It is tempting to catch the error and fall back to
   retrieval-only — call `assess_data_versions(pins, published_from_pins(pins))` exactly as today.
   That is **fail-open**: with only the retrievals' own self-observations on record, the rule
   (`app.profile.data_versions.assess_source`, lines 314-375) has nothing newer than the pin to
   compare against, so it returns `current`. So if the city is genuinely at 26v2 while a lot is
   pinned at 26v1, then during any probe outage that stale lot still reads "current" — the outage
   silently MASKS the staleness the check exists to catch. Retrieval-only hides exactly the case
   "Out of date" is for.

   **Decision (Lane C, the integrator, already taken): fail closed.** On any probe failure, mark the
   PLUTO-sourced facts `version_unknown` ("Version unknown"), never `current`, and surface the
   failure (correlation id + error type) so it is visible and never swallowed. Concretely: when the
   probe raises, leave out the probe's `PublishedVersion` AND drop the retrieval-only
   self-observation for PLUTO, so the pin has nothing to compare with and the rule already turns
   that into `version_unknown` (fail-closed, never current). Retrieval-only
   (`published_from_pins(pins)` alone) remains acceptable ONLY when no probe was attempted by design
   — never as a fallback after a probe failed.

2. **Caching / probe frequency.** The published PLUTO version changes at most monthly (minor) /
   quarterly (major) per the README release model, while a study may assemble many times. Options:
   one probe **per process per N minutes** (a small TTL cache keyed on the dataset), vs **per
   request**. **B recommends a short per-process TTL cache (e.g. 15-30 min), Lane C to pick N**, so a
   burst of studies shares one freshness observation and the city API is not hit once per study
   (polite shared-pool use, matching the connector's tokenless-pool note). The probe is pure w.r.t.
   its inputs and injectable (transport/clock/correlation_id), so a cache wrapper is straightforward
   and testable offline. B has **not** built the cache — where it lives (assembly layer vs a small
   Lane C helper) is Lane C's call, as is N.

B built only the library pieces (probe + adapter + tests); it did not touch `study_inputs.py` or add
any caching. The failure-fallback is now recorded as decided (fail closed, item 1 above); the cache
shape and N remain open for Lane C.
