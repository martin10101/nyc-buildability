zr.planning.nyc.gov exposes a per-section print/PDF render at
`https://zr.planning.nyc.gov/entityprint/pdf/node/<node-id>` (a real multi-page PDF,
footer reads "File generated by https://zr.planning.nyc.gov on <date>"). Find the
node id from the section's own HTML page: `grep -oE 'data-node-id="[0-9]+"'` near the
section's anchor (`id="<section-number>"` / `id="nav-item-<section-number>"`), or grep
the section page for `entityprint/pdf/node/<id>` directly if the section has its own
page. Fetch with plain `curl -o out.pdf -A "Mozilla/5.0" -L <url>`; read it with the
Read tool (`application/pdf` is supported, page-by-page text comes back verbatim,
figures render as images) - no extra PDF library needed.

Non-obvious finding (M4-T012, 2026-09-13): a prior blocker record
(`docs/ARCHITECT_REVIEW_QUESTIONS.md`) asserted the site's HTML render "loses"
ZR 23-421 paragraph (g) in text extraction on both mirrors. Direct `curl` of the raw
HTML and a raw-byte string search (not a text-extraction/readability tool) found
paragraph (g) present, byte-identical to the PDF, inside the `field--name-body`
container - immediately after a large inline base64-encoded PNG data URI. The
"HTML loses it" finding most likely came from a readability/markdown-conversion tool
truncating after that large embedded image blob, not from the raw HTTP response
lacking the text. Lesson: when a prior blocker claims a channel "cannot" render
something, re-verify from raw bytes before trusting it, and disclose any discrepancy
rather than silently repeating or silently overriding the prior claim - the task
packet's binding channel (print/PDF here) should still be used as the citation record
even when the raw-HTML finding turns out to be fine, since the packet's instruction
governs and the corroborating finding is additive evidence, not a substitute.

Digest-binding trap avoided: never edit an already-cited, already-accepted snapshot
file to add more text - its `content_digest_sha256` is `sha256(verbatim_excerpt)` and
every rule that cites the OLD digest would break. Capture the additional text as an
independent NEW snapshot_id instead (e.g. `zr-23-421-g` alongside the existing
`zr-23-421-r3-r4`), even when it overlaps another accepted snapshot's content.
