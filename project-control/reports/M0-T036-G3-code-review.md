## (2) Findings, ranked by severity

### BLOCKING (must be corrected before activation; B-1 and B-2 specifically block any supervised or multi-cycle activation)

**B-1 (HIGH, correctness): the forwarded prompt is never delivered — run() re-sends the original prompt every cycle.**
tools/agent_supervisor/loop.py:983-1004 — run(first_prompt) sets prompt = first_prompt and never reassigns it; every iteration calls run_cycle(prompt, ...), and run_cycle calls self.runner.run_unit(prompt) at loop.py:587. In supervised mode, the reviewer's next_claude_prompt is rendered, operator-approved, journaled in the outbox, and mark_sent — but nothing ever passes it to the next unit. Cycle 2 launches a fresh Claude session with the ORIGINAL --prompt (cli.py:1909, loop.run(args.prompt)), while the audit trail and outbox assert the forwarded instruction was "sent". The exactly-once-forwarding invariant is actually zero-times forwarding: the durable handoff has no consumer.
Failure scenario: start --mode supervised --max-cycles 3 --approve-prompt-digest <d>: cycle 1 completes, owner approves the reviewer's REVISE prompt, outbox marks it sent; cycle 2 re-runs the initial "report a checkpoint" prompt in a new session; the reviewer then reviews a checkpoint produced from the wrong instruction, and the audit record contradicts what actually ran.
Mitigations found: CLI --max-cycles defaults to 1 (cli.py:2124), and every pilot run was shadow single-cycle, so this never surfaced live. No test asserts what prompt cycle 2's runner received (FakeRunner.prompts captured at test_agent_supervisor_loop.py:76-80 but only ever inspected for cycle 1; the only multi-cycle .run() test is shadow, lines 361-367).
Classification: BLOCKS ACTIVATION of supervised/multi-cycle. Correction: thread decision.next_claude_prompt / the rendered forwarded prompt (or the unsent outbox row) into the next cycle's run_unit, or structurally bound supervised mode to max_cycles == 1 until it does — plus a test asserting the second unit's received prompt.

**B-2 (HIGH, availability/state integrity): DENY_AND_CONTINUE and every completed shadow observation strand the journal in POLICY_CHECK, with no legal exit — and in-run it becomes an uncaught crash.**
(a) The DENY_AND_CONTINUE branch (loop.py:714-719) returns with the machine at POLICY_CHECK and stopped=""; CycleResult.continues (loop.py:343-345) deliberately includes POLICY_CHECK, so in supervised mode run() iterates again and run_cycle raises LoopError("bad_cycle_entry_state") (loop.py:559-565) — uncaught anywhere in cmd_start (cli.py:1912-2000), so the operator gets a traceback and the LoopRun report (cycles, budget, touches) is lost. A trigger as benign as the reviewer's next prompt containing a prohibited effort-flag string produces DENY_AND_CONTINUE (policy.py:1108-1112).
(b) Even at --max-cycles 1, and after every NORMAL shadow observation (asserted by test_agent_supervisor_loop.py:344: final state POLICY_CHECK), the journal is left at POLICY_CHECK. The S7 table (state_machine.py:185-197) gives POLICY_CHECK no edge back to PREFLIGHT/IDLE, and CYCLE_ENTRY_STATES refuses it — so the next start against the same journal crashes with bad_cycle_entry_state. Only remedy: parking the journal, the exact continuity loss pilot F-2 describes.
Relation to settled findings: F-2 is recorded as V1.1 for PAUSED_RECOVERY only. This is a NEW dimension: POLICY_CHECK is a second no-exit parking state reached on every successful shadow cycle, and the in-run manifestation is an uncaught exception, not a clean refusal.
Classification: BLOCKING. Correction: give the cycle a legal closing transition after a shadow observation / DENY_AND_CONTINUE (or accept POLICY_CHECK as a cycle entry state with defined semantics), and catch LoopError in cmd_start so a refusal is reported, not a traceback.

**B-3 (MEDIUM-HIGH, adversarial): extract_checkpoint silently picks the LAST of multiple DISTINCT checkpoints.**
tools/agent_supervisor/claude_runner.py:373-384 — conflict refusal fires only when the SAME checkpoint_id appears with different content; two checkpoints with DIFFERENT ids pass silently and chosen = shaped[-1] wins. Checkpoints are accepted from fenced JSON in assistant text (a supported path — test_agent_supervisor_runner.py:428), and the worker is untrusted by the module's own threat model.
Failure scenario: a prompt-injected worker emits its real checkpoint (status BLOCKED, id A) then a second, rosier one (status UNIT_COMPLETE, fabricated claims, id B) later in the stream; the supervisor selects B, which then drives CHECKPOINT_RECEIVED, the evidence packet, and the Codex review correlation (expected_checkpoint_id is taken FROM it, loop.py:658). Policy still gates all actions, so no direct unauthorized effect, but it corrupts the review input and provenance while the docstring promises "the ONE structured checkpoint". Adversarial suite covers conflicting same-id duplicates (test_agent_supervisor_runner.py:459) but not distinct ids.
Classification: BLOCKING correction (small fix): refuse multiple distinct checkpoint_ids in one unit, consistent with the module's refuse-rather-than-choose rule, with a test.

**B-4 (MEDIUM, fail-closed gap): the codex_reviews_per_checkpoint breaker verdict is discarded.**
tools/agent_supervisor/loop.py:654 — self._breaker("codex_reviews_per_checkpoint") increments the counter but ignores the returned (tripped, message); contrast claude_runs_per_task at loop.py:571-583, which pauses on TRIP. A tripped S13.8 review breaker therefore stops nothing — the reviewer is still invoked. Secondary: the counter is never reset per checkpoint (so it measures reviews-per-run), and circuit_breakers.py:39-50 maps claude_runs_per_task to limit field max_claude_turns_per_run (units mismatch worth a look). Bounded harm today (reviewer caps attempts at 3; cycles bounded), but the breaker claims a safety function it does not perform.
Classification: BLOCKING correction (one-line fix plus a test).

### Non-blocking (V1.1 conditions / notes)

**V-1: the approval broker is never wired into the assembled loop.** broker_permission_handler (claude_runner.py:799) has no callers outside tests; SupervisedLoop accepts and stores a broker argument (loop.py:462, 479) never used, and _run_loop (cli.py:1885-1908) builds the runner without a permission handler, so every worker tool request is denied by deny_everything in BOTH modes. Fail-closed, arguably right for shadow, but supervised activation with a worker that must actually edit files requires this wiring; the dead broker parameter is misleading API surface. Adjacent to settled F-4 in spirit but a distinct gap.

**V-2: claude_process_started is journaled only after the unit completes.** loop.py:588-593 transitions START_CLAUDE->CLAUDE_RUNNING after run_unit returns, so during a 15-minute unit the journal says START_CLAUDE; a mid-unit crash recovers into a state under-reporting that a provider was contacted and a session existed. Recovery still fails safe (pending-effects/drift checks), but "the journal is the truth about where a run got to" is weakened for exactly the window that matters most.

**V-3: runner drain-thread edge.** claude_runner.py:655-697 — if drain_stdout_tail outlives its 2-second join, parser.close() is correctly skipped, but the main thread then closes the pipes under the running thread and builds tuple(events) from a list the thread may still append to. Practically bounded (join happens after process.wait(), so EOF is imminent) — hazard note, not a live bug.

**V-4: wall-timeout/graceful-close overlap and one misleading reason string.** If the wall deadline lapses during the close grace, the watchdog records timed_out for a unit that actually completed its turns (claude_runner.py:582-599, 669-684). Both paths fail closed; only the recorded reason is imprecise. Similarly, when a valid checkpoint coexists with graceful_close_failed, the loop's stop reason reads "the worker exited without a valid checkpoint" (loop.py:600), which is not what happened.

**V-5: Job Object adoption gap.** The child is launched, then adopted (claude_runner.py:568-573; process.py:671-672); a grandchild spawned before adoption is outside the job, whereas the docstrings say children are "launched INSIDE"/"created inside" the job. Millisecond window; fallback reporting otherwise admirably honest. CREATE_SUSPENDED launch would close it.

**V-6: a corrupt (as opposed to absent) audit head anchor is silently ignored.** audit_log.py:292-301 returns None on JSONDecodeError, disabling truncation detection exactly when the anchor looks tampered. Pending Option A external anchoring, a corrupt sidecar should fail closed.

**Minor:** reviewer timeout attempts skip _audit_attempt (codex_reviewer.py:450-453); pending_prompt/<run> journal row never cleared after approval (loop.py:815); mark_sent does not check rowcount (durable_state.py:576-578, harmless in current call order); codex_reviewer.build_argv's forbidden-flag scan (codex_reviewer.py:123-127) can never fire against the token forms it just built (assertion-only dead check).
