**MINOR-2 — Dedup key's `task_id` participation is unpinned (missing mutant class).**
Probe confirms `_dedup_digest` includes `task_id` (taskA≠taskB), so distinct tasks with identical condition+summary correctly produce distinct notifications. But `test_exact_duplicates` forces a re-send by changing the *summary* only; a `digest-drops-task_id` mutant would survive and wrongly deduplicate different tasks (e.g. `approval_waiting` for M0-T111 vs M0-T112). This is exactly the item-4 "same condition / different task_id" concern.
*Smallest fix:* add an assertion — same condition + same summary, different `task_id` → both `delivered`, `len(delivered)==2`.

**MINOR-3 — L1.1 "each mapped to its fixed risk class" is weaker than claimed.**
The test verifies the risk-map *keys* equal `CONDITIONS` and that each delivers; it never asserts the specific value (e.g. `stop_for_owner→ask`, `unrecovered_controller_failure→synchronous_stop`, `golden_run_complete→info`). A within-`RISK_CLASSES` swap survives (unobservable downstream because `unit_can_proceed=True` neutralizes `requires_owner_input`).
*Smallest fix:* `assertEqual(ts.CONDITION_RISK, {…exact map…})`.

**MINOR-4 — One-way source scan has dead/evadable checks (permanent backstop).**
Probe confirms `functional_text` never yields `"exec("`/`"eval("` (paren absent from extracted identifiers), so those two `assertNotIn` checks can never fail; `import subprocess`/`from subprocess import run` evade the Name-based extraction; the matrix's "receive/approval" are not in the token list; and the sibling raw-source R248 check omits `subprocess`/`exec`/`eval`. Telegram-specific receive methods (getUpdates/webhook/setWebhook/getMe) *are* effectively caught, and the actual code is genuinely one-way (direct read + grep). This is a backstop-soundness gap, not a defect in the artifact.
*Smallest fix:* check bare `"exec"`/`"eval"` identifiers (or walk `ast.Call` func names), add `ast.Import`/`ast.ImportFrom` module names to the blob, and extend the R248 raw-source list with `subprocess`/`exec`/`eval`.

**MINOR-5 — L2.2 asserts a bound, not redaction, despite its name/matrix claim ("text redacted").**
`test_the_summary_is_hard_bounded_and_text_redacted` only checks `len(sent_text)<700`. Redaction (pattern replacement, `redaction_count`) on the telegram compose path is unasserted (it is covered generically in the adversarial pack, not on this path).
*Smallest fix:* feed a redactable token in the summary and assert it is replaced in `compose_text` output / `redaction_count>0`, or rename the test.
