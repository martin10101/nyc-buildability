## Threat-by-threat findings

**T1 — F-1 closure / divergence removed — PASS.**
The M5-T015 F-1 (report lines 52-54): split names (`INTERNAL_RULE_EVAL_UI` on web, `INTERNAL_RULE_EVAL_ENABLED` on API) let the endpoint's flag-off generic 404 be reached under a specific misconfiguration, and diverge from design-spec §6. Verified the rename closes the NAME divergence: the web now reads exactly `INTERNAL_RULE_EVAL_ENABLED` (`rule-evaluation.ts:83` const, `:88` `process.env` read) — byte-identical to the name the API reads (`services/api/app/config.py:28`, READ-ONLY reference) and to design-spec §6 (`docs/design/address-entry-confirm-design-spec.md:118`: "All ship behind `INTERNAL_RULE_EVAL_ENABLED`, the same flag the endpoint is gated by").
Honest characterization of the *residual* surface: web and API are two independent Render services, each with its own env. Unification eliminates the name-divergence class (the actionable F-1 defect — where setting the intended flag on the web under the old name silently did nothing, or the two sides used different names). It does **not** eliminate the multi-service reality: an operator can still set the single name inconsistently *across the two services* (web-on / API-off or vice versa). That residual degrades safely — a web-on/API-off request hits the endpoint's generic `404 {"detail":"Not Found"}`, which the client maps to the benign `feature_unavailable` outcome (`rule-evaluation.ts:116-120, 353-356`), never a coerced answer. The task objective and producer report S4 scope the closure correctly to "the NAME divergence / inert on the web side," not to eliminating all cross-service misconfiguration — **this is the right claim for the record.** F-1 is formally **CLOSED on the web side** as scoped.
