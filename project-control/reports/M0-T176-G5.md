THE CHANGE (review_slots.py): a new `_is_windows()` seam (pure os.name read) and a dedicated `except PermissionError` branch in `_SlotLock.acquire`, placed after `except FileExistsError` and before the general `except OSError` (correct specific-before-general ordering; both are OSError siblings). On Windows a PermissionError from the O_EXCL create is treated as transient "busy": it calls the shared `_wait_or_fail_closed(deadline)` and `continue`s — NEVER `_holder_is_stale`/`_take_over`. On POSIX it still raises slot_lock_error at once. `_wait_or_fail_closed` factors the identical wait/timeout out of the FileExistsError path. A holder-read comment pins that reads stay short-lived (read_text opens/reads/closes).

(1) FAIL-CLOSED PRESERVED — YES.
A slot is granted ONLY when os.open(O_CREAT|O_EXCL) SUCCEEDS (returns fd) and the payload write+fsync completes, then try_reserve writes the durable reservation under the held lock. The new branch cannot grant: it only sleeps one poll and loops back to re-attempt the atomic O_EXCL create (fresh lock_id each iteration). It never takes over: takeover remains gated solely by `_holder_is_stale() and _take_over()` in the FileExistsError path, and `_holder_is_stale` still returns False for an unreadable (None), undetermined, or live holder — so a live or unreadable (delete-pending) lock is never stolen. The inner write-failure path still fails closed as slot_lock_error (unchanged, separate try/except). Proven by test_transient_permission_error_waits_then_succeeds (calls==3: it actually acquired via a real O_EXCL success, len(active)==1 — a real lock+record, not a fake grant) and test_persistent_permission_error_times_out (slot_lock_timeout, admitted False, reservation None, retried >1).

(2) DoS OF THE NEW WAIT — ACCEPTABLE, BOUNDED, DISCLOSED.
A permanent Windows PermissionError now costs a full-deadline wait (bounded by timeout_s, default 10s via DEFAULT_LOCK_TIMEOUT_S) then a fail-closed slot_lock_timeout refusal — never an over-admission. Windows-only; POSIX permission faults still refuse instantly. Crucially, a waiting reserver holds NO lock during the wait (it never acquired one), so its latency cannot block other lanes; it spins at poll_s=0.01 with negligible CPU. The realistic delete-pending case is microsecond-transient; only a commissioning ACL misconfiguration would make it permanent, and that refuses fail-closed. Disclosed in the class docstring (lines 209-215) and the inline acquire comment (303-313).

(3) NEW SAME-TRUST EXPLOIT PATH — NONE BEYOND EXISTING.
To force a victim into the Windows busy-wait, a process would have to keep the lock file delete-pending/ACCESS_DENIED. Any such process is the same trusted supervisor user, which could already block all lanes simply by holding the lock legitimately (a live holder is never stolen). The new branch grants no additional power, and the worst outcome remains fail-closed (fewer slots / DoS), never over-admission. The victim does not hold the lock while waiting, so there is no amplification to other lanes. `_is_windows()` reads os.name (fixed per platform, not runtime-attacker-controllable; patched only in tests). POSIX is a no-op change.
