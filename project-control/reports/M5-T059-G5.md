### F1 — MEDIUM: revoke ignores the path BBL's condo identity

`revoke_site_definition_confirmation` normalizes the path BBL for **shape only** (422 on malformed), then calls `store.revoke(record_id, …)` with no resolver call and no `condo_key` check. `InMemorySiteDefinitionStore.revoke` (`store.py:214-232`) checks only existence and ACTIVE status. The `supersede` path **does** enforce the binding (`store.py:195-199` → 404).

**Reproduction** (two condos behind one stubbed resolver: `3022647515` → `condo:A`, `1000167515` → `condo:B`):

```
POST /api/v1/properties/3022647515/site-definition-confirmations   -> 201, condo_key=condo:A, id=X
POST /api/v1/properties/1000167515/site-definition-confirmations/X/revoke
     {"confirmer":{"name":"Attacker","role":"user"},"reason":"cross-condo"}
  -> HTTP 200   (record condo_key returned: "condo:A")
GET  /api/v1/properties/3022647515/site-definition-confirmations
  -> status "unconfirmed", active_confirmation null
```

Control: the same cross-condo attempt against `supersede` → **404** `"a superseding confirmation must belong to the same condo key as the record it supersedes"`.

**Impact today: none additional.** The router is unmounted, the flag is default-off, and there is no authentication at all — so the path BBL is not yet an authorization boundary, and a caller who can reach `revoke` can equally reach it at the correct BBL. **Impact at mount:** the path identity is the only resource scoping this route has; a per-property authorization check placed on the path would be bypassed by supplying a `record_id` belonging to another property, and the revoke transition is recorded against a condo the caller never named.

**Remediation:** mirror `supersede` in `revoke_site_definition_confirmation` — `store.get(record_id)` (or re-read the resolver for the path BBL) and refuse 404 `not_found` when `record.condo_key != resolution.condo_key`; add a cross-condo revoke test. ~5 lines. **This must be closed in the same packet that adds the `main.py` mount line, before any auth surface is added on top.**

### F2 — LOW: no length cap on stored/echoed free text

**Reproduction:** `POST … {"parcels":[…], "confirmer":{"name":"Q"*3000,"role":"user"}, "note":"N"*60000}` → **201**; `note` stored at 60,000 chars, `name` at 3,000; the subsequent `GET` list document was **127,501 bytes** for two records.

Refusal messages are bounded (400 chars) and web display is bounded (`boundedText` 600 / `note` not rendered), so this is storage and response size only, and it is unreachable in production (write route unmounted). **Remediation:** cap `note` (~2,000) and `confirmer.name` (~200) in `records.py` with a typed 422; cap the `list` result.

### F3 — LOW: unbounded chain growth, unbounded in-memory retention

Each `supersede` is individually legal and appends a record plus a transition to `_DEFAULT_STORE` (`store.py:249`) with no cap; `_current_status`/`_superseded_by`/`_transitions_for` each scan the whole transition list, making `list_for_condo_key` quadratic. Unreachable today (unmounted + flag-off). **Remediation:** cap chain depth and list output; index by `condo_key` in the durable store.

### F4 — LOW: record-id collision overwrites an immutable record

`store.py:157` and `:200` assign `self._records[record_id]` unconditionally. `create_confirmation(..., record_id=…)` (`records.py:450, 482`) permits an explicit id, so an internal caller could silently replace a frozen record — an append-only violation. **Not reachable from the route** (probe P1 proved a body-supplied `record_id` is ignored; probe P13 proved self-supersede is impossible). **Remediation:** raise a typed refusal when `record_id` already exists.

### F5 / F6 / F7 — informational, mount-packet inputs

F5: the mounted, flag-gated `condo_records` document embeds `confirmer.name` and `note` verbatim (`condo_records.py:668-674`) with no authentication. Nothing is exposed today — I verified the production default store is empty — but the read-authorization posture for confirmer identity must be decided alongside B-001 auth, since the *same* `INTERNAL_RULE_EVAL_ENABLED` flag gates both the read and (once mounted) the write route. F6: record a constraint that confirmation free text must be treated as untrusted at any future AI-drafting boundary. F7: document that uuid4 ids are not a capability, so a later slice does not build access control on them.

**None of F1–F7 are disclosed in the producer report** (`project-control/reports/M5-T059-producer-report.md`) — routed to the orchestrator as new discovery items, not fixed in-packet.
