## RULING ON THE CENTRAL GATE QUESTION (R124)

**What the operator's named digest actually attests over.** At approval the operator supplies `--approve-prompt-digest`, which is checked ONLY against `pending["digest"]` (cli.py:1678 `recorded = str(pending.get("digest"))`). That field is `prompt_digest = self.approval_digest_for(decision)` (loop.py:1712), i.e. the **S13.5 timestamp-free approval envelope** over structured fields (task_id, stage, allowed_paths, requested_action, stop_conditions) — `approval_digest_for` at loop.py:1863-1870. It does **not** cover the forwarded bytes. The forwarded bytes (`build_forwarded_prompt`, codex_reviewer.py:660-684) append `FORWARDED AT: {to_utc_iso()}` and are therefore non-reproducible outside the journal. Byte integrity rests entirely on `prompt_bytes_digest`, a value written into **mutable journal state** at park (loop.py:1776) and re-checked at approve (cli.py:1710-1728, loop.py:660-679) and at resume (loop.py:2042 `digest_of(prompt) != approved_digest`).

**Can a journal-write attacker who rewrites `prompt` + `prompt_bytes_digest` consistently (leaving `digest` intact) still get tampered bytes forwarded under a valid operator approval?** **Yes — confirmed by code.** Approve enforces only (a) `supplied == pending["digest"]` [attacker leaves intact] and (b) `digest_of(held_prompt) == pending["prompt_bytes_digest"]` [attacker sets both consistently]; it then binds `approved_digest = anchor` (loop.py:678). Resume re-checks `digest_of(prompt) == approved_digest` — also satisfied. Malicious bytes forward. The operator-named digest is never cryptographically related to the forwarded bytes. This is the producer's disclosed **residual 3**.

**Ruling (both halves true, stated explicitly):**

1. **The residual is genuinely the same class the original LOW-1 excluded.** It requires full journal-write, forges two journal fields (same capability that "already forges checkpoints/decisions/flags"), yields **no new privilege escalation**, and SHADOW-ONLY forwards nothing regardless. The fix *does* close the exact window LOW-1 described — a single-field `prompt` tamper — proven by `test_tamper_between_park_and_approval_is_refused` (fail-closed, sealed hash-chained refusal, no state change) and the post-approval variant caught at resume by `test_tamper_after_approval_is_caught_at_resume`. Notably, LOW-1's own literally-suggested remedy ("operator names `digest_of(parked bytes)`") would be **no stronger** against this attacker, because the operator cannot compute the timestamped byte digest independently — they would read it from the same journal the attacker rewrote. So the producer's park-time anchor is not weaker than the finding's prescription, and it preserves the S13.5 "change only the clock" invariant.

2. **But the fix does NOT achieve the directive's stated intent.** The directive says "bind the forwarded prompt bytes to the OPERATOR-NAMED approval digest" so "the park→approve window no longer rests solely on the journal file ACL." The chosen anchor lives **in the parked record the attacker writes**, so for the realistic (journal-write) adversary the byte integrity **still rests on the journal ACL** — trust was not re-anchored, only moved from an approval-time re-hash to a park-time journal field. AS-1's literal text ("binds `approved_digest` to the **OPERATOR-NAMED value**") is **not implemented**: `approved_digest` binds to the anchor, and the operator-named value is a different (S13.5) digest. The only construction that would satisfy the intent is binding the forwarded *content* to the operator's **independently-known** approval_digest (e.g. inject `FORWARDED AT` at forward time so the timestamp-free instruction — already covered by `approval_digest` — is what is anchored, or persist the structured fields and recompute `approval_digest` at approve/resume). That was not done.

**Disposition:** The residual does **not** block this SHADOW-ONLY gate (same excluded class; posture strictly improved; no new exploitable surface under shadow). It **is** a required pre-activation item (see C2). The `directive-compliance-verifier` must independently rule whether **R124's literal "bind to the operator-named digest" is satisfied by the adapted design**; I judge the adaptation *security-sound and honestly disclosed* but the *literal AS-1/R124 wording unmet* — that call belongs to the directive-compliance lane and, if it rules R124 unmet, is a separate acceptance blocker outside my lane.

## Findings (severity-ranked)

**MEDIUM M-1 (SCOPE 1) — directive-literal + intent gap; byte binding rests on a journal-resident anchor.** File evidence: cli.py:1678, 1710-1728; loop.py:660-679, 1776, 2042; codex_reviewer.py:684. The operator-named digest does not cover the forwarded bytes; a two-field journal-write forgery (`prompt` + `prompt_bytes_digest`, leaving `digest` intact) still forwards tampered bytes under a valid operator approval. **Activation-relevance:** does **not** block shadow-acceptance (same excluded class; SHADOW forwards nothing); **pre-activation checklist blocker** → **C2**.

**MEDIUM M-2 (SCOPE 3) — fail-OPEN via `icacls` binary planting.** `os_acl.py:254-255` invokes `["icacls", str(path)]` by **bare name**. On Windows, `subprocess.run` → `CreateProcess(lpApplicationName=NULL)` searches the **process CWD before System32** (SafeProcessSearchMode is not enabled by default and must not be relied on). An attacker with unelevated write to the supervisor's CWD — squarely within this task's threat model — can plant `icacls.exe` and spoof ACL output. The file verdict is partly corroborated by the **real** `os.open` probe (a planted icacls cannot fake a genuinely-writable file → still NOT_PROTECTED), but `evaluate_directory` (os_acl.py:343-364) is **ACL-only**, so a spoofed "clean" parent ACL yields a **false PROTECTED** parent → combined PROTECTED while the parent is actually writable (attacker replaces the config via the parent). This directly contradicts the directive's "never assumes protected / fail-closed" requirement. **Remediation:** resolve to the absolute path, e.g. `os.path.join(os.environ.get("SystemRoot", r"C:\Windows"), "System32", "icacls.exe")`. **Activation-relevance:** does not affect shadow (posture not a pass/fail check) but the false PROTECTED is read by activation gating (`controller_config_acl.protected`); **blocking for acceptance → C1** (cheap, contained, and the SCOPE-3 deliverable's own fail-closed contract).

**LOW L-1 (SCOPE 3) — verifier does not check ownership.** `os_acl.py` PROTECTED is DACL-only; it never asserts the file/parent OWNER is Administrators/SYSTEM. A file owner keeps implicit WRITE_DAC and can re-grant write, defeating "cannot change ACLs." The sanctioned PS apply always transfers ownership (takeown-first, stop-on-error), so the *applied* state is correct and the write-probe returns denied for an owner-without-write-data; but the verifier would report PROTECTED for a hypothetical "RX-DACL + user-owned" state. **Recommend** os_acl additionally assert non-unelevated ownership (`icacls /save` owner or a `Get-Acl` owner check). Pre-activation hardening.

**LOW L-2 (SCOPE 3) — elevated bare-name binaries in the PS script.** `harden_controller_config.ps1:121-162` invokes `takeown`/`icacls` by bare name under UAC. PowerShell command resolution does not search CWD by default (materially safer than the Python case), so exposure is limited to a tampered PATH; defense-in-depth: use absolute `%SystemRoot%\System32` paths. Pre-activation hardening.

**INFO** — SCOPE-2 estop fix is correct and fully fail-closed (no auto-heal, no privileged silent repair). No new deps; config.py digest gate untouched; SHADOW-ONLY and R129 intact; no secrets/PII; doctor posture correctly excluded from pass/fail checks. The producer's residual 3, "parent-container residual," and "AS text unavailable" disclosures are accurate and honest.
