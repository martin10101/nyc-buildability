## 4. Findings

### Required corrections (block acceptance; recorded, not gate-failing)

**C-1 — `list_for_condo_key` violates its own "newest first" contract on a timestamp tie, and the tie-break comment is false.**
`store.py:176` is `views.sort(key=lambda view: view.record.confirmed_at, reverse=True)`. The comment at `store.py:174-176` claims "then by the reverse of insertion order so a same-instant pair is still deterministic" — Python's sort is stable and `reverse=True` does **not** reverse equal elements, so a same-instant pair keeps **insertion** order, i.e. oldest first. The ABC contract at `store.py:63-65` and packet SCOPE 2/4 both state "newest first". Reproduced:

```
=== PROBE B: same-instant chain ordering (store.py:174-176 comment claim) ===
  confirmed_at equal: True
  list order: ['AAA', 'BBB']  (docstring claims NEWEST first)
  active: ['BBB']
```

Active-record selection is unaffected (`records.py:514-516` scans for status, not position), so no confirmed/unconfirmed decision changes. Trigger requires two records at the identical microsecond, which `datetime.now(UTC)` per HTTP request makes effectively unreachable today — but the durable B-001 store will implement this same ABC, possibly with a coarser clock. Fix: add a deterministic secondary key (e.g. reversed insertion index) **or** correct both `store.py:63-65` and `store.py:174-176` to state the real guarantee; either way add a same-instant ordering test. Existing tests (`test_site_definition_records.py:216-221`, `test_site_definition_api.py:297-313`) both use distinct timestamps and cannot see this.

**C-2 — `store.create` admits an orphan `supersedes_id`, an append-only-integrity hole in the published ABC.**
`store.py:148-158` validates only the one-active-per-`condo_key` invariant. A record carrying `supersedes_id` pointing at an unknown (or another condo's) record is accepted as ACTIVE with no transition appended and no chain flip. Reproduced:

```
=== PROBE A: store.create accepts a record claiming supersedes_id (no chain flip) ===
  created orphan-supersede record: ConfirmationStatus.ACTIVE supersedes_id= some-other-record
```

Not reachable through the route today (`site_definition.py:374-385` never passes `supersedes_id` on create; `store.supersede` **does** guard the reference at `store.py:183-199`). But `SiteDefinitionStore` is the public interface the durable implementation will satisfy, and `store.py:44-51` states "Implementations MUST … record every status change as an appended transition". Fix: refuse a `supersedes_id`-carrying record in `create` (route the caller to `supersede`), plus a covering test.
