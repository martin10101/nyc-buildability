## Findings (Minor only)

**F-1 (Minor / Informational) — Frontend and backend feature flags are distinct env vars, so the endpoint's flag-off 404 is reachable under a specific misconfiguration.**
- Evidence: UI gate = `INTERNAL_RULE_EVAL_UI` + `?ruleeval=on` (apps/web/src/lib/rule-evaluation.ts:75-95); endpoint gate = `INTERNAL_RULE_EVAL_ENABLED` (services/api/app/api/v1/address_resolution.py:119,420). The design spec §6 states both should ship "behind `INTERNAL_RULE_EVAL_ENABLED`, the same flag."
- Impact: In the fail-safe default (frontend flag off) the surface never mounts and the fetch never fires — the primary requirement holds. Only if an operator explicitly enables the frontend flag while the backend flag is off does the fetch fire and receive the generic 404. That 404 renders as the honest `unexpected_response` card ("This is not an 'address not found' result — the response body was not trusted or rendered", AddressResolutionScreen.tsx:513-549), NOT as a `not_found`/coerced address answer. Because the 404 has no `state`, `DOCUMENTED_PAIRS.has("404|")` is false (address-api.ts:334) → `unexpected_response`. The endpoint's "never coerced into not_found" intent is preserved; the leak only occurs in a session where the operator already deliberately turned the surface on. Not a code defect in this packet; the dual-flag scheme is the reused M4-T005 precedent. Recommend the orchestrator/owner note the flag-coupling divergence from the design spec for Packet 2 (where the ZoLa/attribute URL context lands).

**F-2 (Minor / Test thoroughness) — S6 hostile coverage exercises only the not_found and ambiguous cards.**
- Evidence: S6 test 1 drives hostile content through the not_found card; test 2 through the ambiguous chooser. It does not render hostile content through the resolved card (`street_name_normalized`/`borough_name`), the `resolved_with_warnings` grc block, or `unexpected_response.receivedState`.
- Impact: None to runtime safety — those sites use the identical `boundedText`/`boundedToken` + JSX-text-node mechanism (verified by source inspection), and the element-absence sweep + `window.__pwned` sentinel would catch an escape in any rendered card. This is a suggestion to add a hostile-`resolved` fixture in a future increment, not a defect.
