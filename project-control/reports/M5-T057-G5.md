2. Add a binding test asserting `len(body["field"]) < cap` and that an over-length lot-line id cannot appear in a 200 body.

### BP-4 — compute budget tighter than library ceilings, no path escaping the product bound: **OPEN** → finding **F2 (MEDIUM)**
The *product* half is implemented well: `ROUTE_MAX_EXTERIOR_WALLS=500`, `ROUTE_MAX_LOT_LINE_SEGMENTS=800`, `ROUTE_MAX_STREET_LINES=400` (`:122-124`), each strictly below its library counterpart (4000/1000/500), enforced by O(1) `len` before any heavy work (`_enforce_route_caps`, `:415-440`), typed refusal naming the exact cap, arithmetic shown (`:109-121`: `500 × (800+400) = 600,000 < ~1e6`), tested at `:313/328/340/354/366`. I re-derived it against `derivation.py`: the wall loop (`_derive_wall_setbacks:665`) × `_lot_line_setback:597` is exactly `walls × lot_line_segments` distance tests, and the street term is an O(1)-per-comparison `wall_id` scan plus one distance test per wall. The product is not escapable via many small polygons or attested street lines. That sub-requirement is CLOSED.

**But the requirement is "keeping worst case under ~1e6 segment tests" and "verify no path escapes the product bound" — and one does.** The O(n²) ring-simplicity test (`proposal.py:_ring_is_simple:174-183`) is bounded only by the *inherited* DB-034(a) budget (`MAX_TOTAL_VERTICES = 5000` → ≤5e6 segment tests per pass), and this route runs that validation **twice**: once explicitly (`:529 validate_proposed_massing_input`) and again inside `check_proposal` → `derive_proposal` → `validate_proposed_massing` (`derivation.py:704`). Worst case ≈ **1e7 segment tests**, ~17× the capped product. The route comment acknowledges the separate budget exists but neither quantifies it nor notes the double pass, and `test_bp4_documented_worst_case_product_under_1e6` asserts only the 600,000 product.

**Measured, at the frozen code, all returning HTTP 200 (single request, inside `MAX_BODY_BYTES`):**

| payload (all ≤ 256 KiB) | request bytes | single-request CPU |
|---|---|---|
| at-cap product: 500 walls × (800 lot-line + 400 street), 501-vertex outline | 158,278 | **4.57 s** |
| DB-034(a)-budget outlines: 5 × ~1000 positions, 1 wall | 205,807 | **14.24 s** |
| **combined at-cap**: 5×999-vertex outlines + 500 walls + 800 lot lines + 400 street lines (compact integer coords) | **196,035** | **17.31 s** |

The combined worst case is reachable within the body ceiling. Compounding it: `post_proposal_checks` is `async def` (`:444`) and `check_proposal` / `validate_proposed_massing_input` are synchronous CPU-bound calls, so this runs **on the event loop** — one such request stalls every other endpoint in the worker process for ~17 s.

**Remediation (either satisfies BP-4's own recorded remediation text):**
- Move the compute off the loop — declare the handler `def` (FastAPI runs it in the threadpool) or `await run_in_threadpool(check_proposal, …)`; and/or
- add a route-level total-outline-position cap tighter than the inherited 5000 (e.g. 1200 → ≤2×1.44e6), enforced with the same O(1) pre-count pattern as `_enforce_route_caps`, with a typed refusal naming the cap; and
- correct the `:109-121` arithmetic comment and the BP-4 test to state the route's *actual* worst case, including the double validation pass.
