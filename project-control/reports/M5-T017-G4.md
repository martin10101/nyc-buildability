## Numbered findings

**Finding 1 — vacant-lot bldgarea == 0 is a deliberately-designed, product-central behavior with zero test coverage. Severity: MEDIUM. ADVISORY (recommend blocking-for-acceptance fast-follow).**
The producer specifically introduced `_nonnegative_finite_float` (distinct from `_positive_finite_float`) with the documented rationale "an existing area of exactly 0 — e.g. a vacant lot — is usable" (module docstring, models.py, producer report). No test in the pack sends `bldgarea == 0`. The tests exercise the *result*-zero boundary (S3, bldgarea == cap) and the negative-input rejection (S4b, -1.0), but not the *input*-zero acceptance. Consequently the one-character mutant `_nonnegative → _positive` survives the entire suite and would silently reclassify a vacant lot from `computed` (value == full cap — the C1 headline "unused floor area" answer) to `not_computable / existing_building_area_unusable`. The code is correct today; the gap is missing regression protection for the single most product-central C1 case. Recommended fix: one assertion — a `computed` document with `bldgarea == 0.0` and `value == cap`. Non-blocking for D-041-R001 (its required harness — normal/over-built/missing/no-cap — is fully covered), but I recommend the orchestrator require it as a ~3-line fast-follow given the case's product centrality.

**Finding 2 — "unrounded subtraction" invariant is undiscriminated (rounding mutant survives). Severity: LOW–MEDIUM. ADVISORY.**
S1 and S6 assert an unrounded value, but the canonical trace cap is `15000.0` and every helper bldgarea is round (cap−5000, cap−100, 10000, 4000), so every asserted remainder is an integer. A `round(value)` / `round(value, 0)` mutant survives. Real caps (FAR × lot area) and PLUTO bldgareas are frequently fractional, so a rounding regression would be undetected and materially wrong. Recommended fix: one computed assertion using a fractional remainder (e.g. cap − 4999.5). Non-blocking (no acceptance-scenario or directive-harness case requires fractionality), but cheap and worthwhile.

**Finding 3 — USABLE coverage set breadth only partially pinned. Severity: LOW. ADVISORY.**
S4b tests that `data_conflict` and `unsupported` are unusable, but no test asserts unusability for an arbitrary/unexpected status (e.g. `verified`, `professional_review_required`, or an unknown string). A mutant broadening `USABLE_EXISTING_AREA_COVERAGE_STATUSES` beyond `{"conditional"}` would partially survive. Low risk (existing-building facts are `conditional` in practice; code is fail-closed). Optional hardening only.

**Finding 4 — integration/sequencing observation (not a defect in M5-T017). Severity: informational.**
M5-T017 alone (`08bf965b`) turns `web-e2e` red because the hand-written web mirror validator (`apps/web/src/lib/scenario-contract.ts`) rejects the new required key in the closed, drift-guarded contract. `apps/web/**` is *forbidden* to M5-T017, so this is by-design cross-layer coupling, resolved only in combination with M5-T018 (combined head `44048007` green except owner-gated `web-dependency-security`). For M5-T017's own scope (services/api + contracts) all relevant CI jobs are green. Implication: M5-T017 must not reach deployed web without M5-T018 — the orchestrator's progress log already recognizes and handles this. No action for M5-T017.
