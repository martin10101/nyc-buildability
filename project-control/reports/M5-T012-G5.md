## 2. BLOCKING-1 — an untrusted body produces an unhandled exception, a plain-text 500, no correlation id, and an undocumented (status, state) pair

**Files:** `services/api/app/api/v1/scenario_analysis.py:195-200` (`_json`), reached from
`scenario_analysis.py:536-545` (`_finish`'s pre-send guard) and from all four handlers
(`:586`, `:621`, `:654`, `:699`).

### Mechanism

`_finish()` proves the envelope "strict-JSON-safe" with

```python
json.dumps(envelope, allow_nan=False)          # scenario_analysis.py:537  -- ensure_ascii defaults to TRUE
```

but Starlette renders the response with

```python
json.dumps(content, ensure_ascii=False, allow_nan=False, …).encode("utf-8")   # starlette/responses.py:186-191
```

With `ensure_ascii=True` an unpaired UTF-16 surrogate is *escaped* (`"\ud800"`) and the guard
passes. With `ensure_ascii=False` the same string must be encoded to UTF-8 and raises
`UnicodeEncodeError`. `json.loads` accepts `\udXXX` escapes and produces exactly such a string, and
the four engine calls plus `_finish` are **not inside any `try`/`except`** — so the raise escapes the
handler entirely.

### Reproduction (verified, probe `p5_raise.py` / `p6_surrogate_detail.py` / `p12_fixproof.py`)

```
POST /api/v1/properties/1000010100/scenario/sensitivity
Content-Type: application/json
INTERNAL_SCENARIO_ENABLED=1

{"variable":"\ud800"}            <-- 21 ASCII bytes, valid JSON, under every documented cap
```

Observed (Starlette `TestClient`, `raise_server_exceptions=False`, i.e. what a real client sees):

```
HTTP/1.1 500
content-type: text/plain; charset=utf-8
(no X-Correlation-ID header)
Internal Server Error
```

Traceback captured with `raise_server_exceptions=True`:

```
  File ".../services/api/app/api/v1/scenario_analysis.py", line 196, in _json
    return JSONResponse(
  File ".../starlette/responses.py", line 191, in render
    ).encode("utf-8")
UnicodeEncodeError: 'utf-8' codec can't encode character '\ud800' in position 906: surrogates not allowed
```

All four endpoints and every echoed field are affected — 10/10 targeted bodies crashed:

| Endpoint | Minimal hostile body | Bytes | Result |
|---|---|---|---|
| sensitivity | `{"variable":"\ud800"}` | 21 | 500 text/plain, no corr-id |
| sensitivity | `{"variable":"utilization_factor","values":["\udfff"]}` | 53 | 500 |
| sensitivity | `{"variable":"utilization_factor","values":[{"\ud801":1}]}` (surrogate in a **key**) | 57 | 500 |
| ranking | `{"objective":"\ud800"}` | 22 | 500 |
| ranking | assumption `key` = `"\ud800"` | 100 | 500 |
| ranking | assumption `unit` = `"\ud800"` | 111 | 500 |
| comparison | set `name` = `"\ud800"` | 86 | 500 |
| comparison | assumption `rationale` = `"\ud800"` | 103 | 500 |
| threshold | candidate `"\ud800"` in `domain` | 64 | 500 |
| threshold | `variable` = `"\ud800"` | 47 | 500 |

### Why this is BLOCKING, not cosmetic

1. **AS-5 violated literally.** "Exceeding any cap yields a typed 422… Deeply-nested, oversized,
   cyclic-shaped or otherwise malformed bodies produce a typed 422 and NEVER an unhandled raise."
   This body is malformed and produces an unhandled raise.
2. **AS-4 violated.** `STATUS_STATE_MATRIX` is declared the single source of truth and
   `test_as4_every_emitted_pair_is_in_the_matrix` asserts the emitted set *equals* it. This path
   emits a tenth pair — `(500, no state, text/plain)` — that the matrix does not contain and no
   test drives. The same request also violates "Every response carries `X-Correlation-ID`".
3. **AS-6's assurance is false, not merely incomplete.** The producer report (§3) rests the
   no-NaN/strict-JSON claim on `json.dumps(envelope, allow_nan=False)`; that guard is evaluated with
   different parameters from the encoder that actually runs, so it can pass on a body that cannot
   be rendered. This is an assurance defect as much as a crash.
4. **Log-side disclosure.** The module's own `_internal_error_500` docstring states the policy — log
   the correlation id only, never `str(exc)`/a traceback, "the chain may embed untrusted upstream
   strings" (M1-T002 G5 F5). Escaping the handler hands the exception to the framework's default
   error handler, which logs the full traceback — filesystem paths, internal module/function names,
   and the offending character — exactly the disclosure the policy exists to prevent. The 500
   *response* leaks nothing; the *log* does.
5. **It is introduced by this task.** I verified the accepted body-less siblings cannot be reached
   with an unpaired surrogate: Starlette decodes the path with `unquote(..., errors="replace")`, so
   `%ED%A0%80` arrives as U+FFFD and `GET /properties/%ED%A0%80/{scenario,rule-evaluation}` and
   `GET /properties/%ED%A0%80` all return a clean typed 422 (probe `p7_pathcheck.py`). The body is
   the new vector — the precise surface this task was shaped to defend.
6. It is the same class as the M5-T011 G5 BLOCKING finding: a "never raises for any input" boundary
   that does raise, on a path no test drives.

### Exact minimal fix required (NOT applied — I am read-only)

**Primary (required): reject unencodable text at the boundary**, inside the existing iterative walk
`_structural_error` (`scenario_analysis.py:263-295`), which already visits every string value and
every dict key. For each string node and each string key, add:

```python
try:
    node.encode("utf-8")          # and: key.encode("utf-8") in the dict branch
except UnicodeEncodeError:
    return _validation_error(
        "request body contains a string that is not encodable text (an unpaired surrogate)",
        correlation_id,
    )
```

This reuses the existing `(422, "validation_error")` pair, introduces no new matrix pair, adds no
new constant, and is the honest answer (the body is malformed). **Verified** in
`p12_fixproof.py`: with this patch applied in-process, all 10 hostile bodies become
`422 state=validation_error`, in-matrix, with `X-Correlation-ID`, 0 crashes; and all 5 legitimate
bodies — including a non-ASCII one (`"é中😀"`) — still return 200. No other behaviour changes.

**Secondary (strongly recommended, defence in depth): make `_finish`'s pre-send guard match the
renderer** — `json.dumps(envelope, ensure_ascii=False, allow_nan=False).encode("utf-8")` at
`scenario_analysis.py:537`. `UnicodeEncodeError` is a `ValueError` subclass, so the existing
`except (ValueError, TypeError)` already catches it and returns the documented
`(500, "internal_contract_error")`. **Verified** in `p12_fixproof.py`: 10/10 hostile bodies become
typed in-matrix 500s with a correlation id, legitimate bodies unaffected. Apply this *in addition
to* the boundary check (it converts any *future* unrenderable envelope into a typed response), not
instead of it — a caller-malformed body deserves a 422, not a 500.

A regression test must assert both: an unpaired surrogate in each of `variable`, `objective`,
a set `name`, an assumption field, a candidate value and a dict **key** returns the typed 422 with
`X-Correlation-ID`, for all four endpoints.

## 3. HIGH-1 — the engine call and the response construction have no fail-closed guard

**Files:** `scenario_analysis.py:585-586`, `618-621`, `653-654`, `692-699`.

`_rebuild_scenario` wraps its fetch stage and its whole build stage in `except Exception` → typed
500 (`:443-448`, `:506-511`), mirroring the accepted route. But the part that consumes **untrusted
input** — the engine call and `_finish`/`_json` — is outside every guard:

```python
result = analyze_scenario_sensitivity(scenario, body.get("variable"), body.get("values"))
return _finish("sensitivity", canonical_bbl, scenario, result, correlation_id)
```

So any raise from the engines, from `_finish`, or from response rendering bypasses the documented
contract entirely (this is how B-1 reaches the client as plain text). The asymmetry is backwards:
the trusted server-side stage is guarded, the untrusted-input stage is not.

I did try hard to find an engine-internal raise and **found none** — the engines are genuinely
hardened (1,600 fuzz requests, 0 engine raises; see §5). Specifically:

- The SEC-L1 backlog item (`derive.py:366-367` renders an out-of-domain factor value with
  `_bounded_echo(repr(value))`, and `repr()` of a >4300-digit int raises `ValueError`) is **reachable
  in principle** through `ranking`, which deliberately passes the RAW deep copy to `derive`
  (`ranking.py:314`, unlike `comparison.py:316` which sanitizes first). It is **not reachable
  through this route today** because CPython's digit ceiling applies to `str→int` as well:
  `json.loads` itself raises on a 4301-digit literal, and the route's parse is wrapped →
  typed 422. Verified: 4300-digit factor value → 200; 4301-digit → `422 validation_error`.
  This is a coincidental rescue by a parser limit, not a designed defence — which is exactly why
  the missing guard matters.

**Fix:** wrap the engine call + `_finish` in the same `except Exception:` → `_internal_error_500`
guard the rebuild stage already uses (four handlers, or better: one shared helper). Cheap,
symmetric with the accepted route's own "everything after the fetch runs inside one generic-500
guard" comment, and it makes the documented matrix true by construction instead of by audit.

## 4. MEDIUM findings

### M-1 `FORBIDDEN_FACT_KEYS` is top-level only: a caller can plant `"coverage_status":"verified"` and a forged cap field inside the 200 body

**File:** `scenario_analysis.py:135-166` (the set) and `:348-357` (the check —
`FORBIDDEN_FACT_KEYS & set(body.keys())`, top level only).

The **authoritative** claim holds and I could not break it: in every probe the envelope's
`scenario_cap_sq_ft` was the server-rebuilt `15000.0`, the engines only ever merge
`{**scenario_document, "assumptions": …}` (verified in all four engines:
`sensitivity.py:326`, `ranking.py:314`, `comparison.py:316`, `breakeven.py:351`), and
`_bounded_coverage_status` ceilings an incoming `verified` to `conditional`. Case variants (`CAP`,
`Cap`), a fullwidth-unicode `CAP`, `__proto__`/`__class__`/`constructor`, trailing-underscore and
non-listed aliases (`cap_sq_ft`, `draft_cap`, `max_floor_area`, `evaluated_input`) all left the cap
at `15000.0`. Duplicate JSON keys (`"cap":1,"cap":2`) are correctly rejected (last-wins still hits
the set).

But a forbidden key nested **one level down** is neither rejected nor neutralized — it is echoed
verbatim into the 200 body (probe `p9_factinject.py`):

```
POST …/scenario/comparison
{"assumption_sets":[
   {"name":"a","assumptions":[{"coverage_status":"verified",
                               "draft_zoning_floor_area_cap_sq_ft":1000000000}]},
   {"name":"b","assumptions":[]}]}
 -> 200
    envelope scenario_cap_sq_ft = 15000.0            (correct, unforged)
    response body CONTAINS  "coverage_status": "verified"
    response body CONTAINS  "draft_zoning_floor_area_cap_sq_ft": 1000000000
```

Same result via `ranking` (planted inside an assumption's `rationale`). Consequences:

- The packet's AS-2 wording is unqualified ("a body key that would supply or override … a cap
  value, or a coverage/verification status is REJECTED with a typed 422, never merged"); the
  producer report §2 silently narrows it to "a **top-level** body key". The implementation matches
  the report, not the acceptance scenario.
- It defeats the pack's own never-Verified invariant check. The test helper `_coverage_values`
  (`test_scenario_analysis_api.py:299-308`) walks the whole response for `coverage_status` values
  and asserts none is `verified`; that invariant is violable by caller input on a body the tests do
  not send. In a platform whose cardinal rule is that nothing is ever Verified, a response that
  carries `"coverage_status":"verified"` — planted by an untrusted caller, nested inside a
  structure a UI may render as "assumption set detail" — is an integrity problem even though the
  authoritative field is right.

**Fix (3 lines, no new constant):** move/extend the forbidden-key test into the dict branch of the
iterative walk `_structural_error`, which already visits every key in the body:
`if key in FORBIDDEN_FACT_KEYS: return _validation_error(… detail={"rejected_keys": [key]})`.
No existing test uses a forbidden key as an assumption key, so nothing legitimate regresses.

### M-2 the 64 KiB cap is applied after the entire body is buffered in memory

**File:** `scenario_analysis.py:320-325`.

```python
raw = await request.body()                 # reads the WHOLE stream into memory, unbounded
if len(raw) > MAX_BODY_BYTES: …422
```

`Request.body()` accumulates every chunk with no limit, so the cap bounds what is *parsed*, never
what is *allocated*. Verified with `tracemalloc` around the request (probe `p3_bounds.py`):

```
20,971,562-byte body -> 422 "request body exceeds the maximum of 65536 bytes"
tracemalloc peak during the request = 20.1 MiB   (i.e. the full body was buffered first)
```

A chunked upload therefore consumes memory proportional to whatever the client sends, per
concurrent request, before the documented cap can reject it. Neither uvicorn nor this app sets a
body-size limit. Two mitigating facts, confirmed: with the flag **off** the body is never read
(peak 0.1 MiB, 404 returned), and a malformed BBL is rejected at step 1 before the read.

**Fix:** check `request.headers.get("content-length")` against `MAX_BODY_BYTES` first (typed 422 on
a declared over-cap length), and/or read `request.stream()` with a running byte count and abort at
`MAX_BODY_BYTES + 1`. The producer-report row "checked on raw bytes BEFORE parsing" should read
"before parsing, after buffering" until then.

### M-3 unbounded response amplification and caller-controlled CPU, with no auth and no rate limit

Measured in a fresh process, one client, 15 timed requests after warm-up (probe `p11_cost.py`):

| Body | In | Out | Amplification | Median latency |
|---|---|---|---|---|
| trivial (`values:[0.5]`) | 51 B | 5,852 B | ×115 | 251 ms |
| 256 plain floats in `values` | 2,097 B | 847,466 B | **×404** | 410 ms |
| 256 × 29-deep nested candidates | 16,174 B | 775,266 B | ×48 | 679 ms |
| 256 candidates in threshold `domain` | 2,118 B | **925,029 B** | **×437** | 386 ms |

All six input caps bound the **input**; nothing bounds the **output** or the per-request cost. A
2 KB request returns ~0.9 MB and costs ~0.4 s of single-core CPU (~1.5–2.5 req/s/core). The ~250 ms
baseline is the server-side rebuild and is inherited from the accepted M5-T003 route; the
caller-controlled *increment* (+160…+430 ms and ~×437 bytes) is new with this task. With no
authentication and no rate limiting anywhere in the service, a handful of concurrent requests
saturates the instance.

**Fix options (not blocking):** lower `MAX_CANDIDATE_DOMAIN_LENGTH`, or add a documented response
envelope-size ceiling enforced in `_finish` (it already serializes the envelope once), or record
this as an accepted, documented limit tied to the flag-gated/no-auth status.

## 5. LOW findings

**L-1 Wrong-method existence oracle (inherited).** Flag **off**, `GET` (or PUT/DELETE/PATCH/
OPTIONS/HEAD) on a real analysis path returns `405 {"detail":"Method Not Allowed"}`, whereas an
unmounted sibling returns `404 {"detail":"Not Found"}` — so the path's existence is discoverable
regardless of the flag, contradicting AS-3's "no header, body, or timing hint that the feature
exists". **Not introduced here:** I verified the identical behaviour on the accepted
`GET /properties/{bbl}/scenario` (M5-T003) and `GET /properties/{bbl}/rule-evaluation` (M4-T005)
with a `POST` probe. Closing it requires a routing-level change touching forbidden paths; record it
as a posture-wide known limitation rather than a packet defect.

**L-2 Flag-off timing delta (inherited).** Flag off, 400 requests each: new `POST` route
6.05 ms/req vs unmounted `POST` 3.83 ms/req; accepted `GET` scenario route 6.57 ms/req vs unmounted
`GET` 4.20 ms/req. A consistent ~1.6× in-process delta exists for the new route and, to the same
degree, for the accepted routes it mirrors (dependency resolution runs before the handler's flag
check). Over a network this is likely unexploitable; AS-3's "no timing hint" is nonetheless an
overclaim for the whole pattern, not just for this packet.

**L-3 Unbounded raw-BBL reflection in the 422 body (inherited).** `BBLValidationError.to_payload()`
(`app/connectors/bbl.py:57-64`) puts `repr(raw_value)` in `detail.raw_value` and the raw value in
`message`, with no length bound; the route forwards both (`scenario_analysis.py:314-318`). A very
long path segment is reflected into the response. Shared verbatim with the accepted property /
rule-evaluation / scenario routes (forbidden paths here), and bounded in practice by the server's
request-line limit. Out of scope to fix in this packet; worth a backlog note alongside SEC-L1.

**L-4 The AS-7 egress assertion covers 1 of the 4 new endpoints.** `test_as7_full_analysis_runs_
fully_offline` exercises only `comparison`. I independently checked seam completeness and the four
seams **are** the complete outbound set for this route's reachable code: every connector egress in
`services/api/app` goes through `urllib.request` — `app.resilience.transport.urllib_transport`
resolves `DEFAULT_OPENER` from the **module global at call time** (`transport.py:168`), so patching
`resilience_transport.DEFAULT_OPENER` intercepts the ztldb / mappluto / zoning-features connectors
too, and `pluto_soda._OPENER` (`pluto_soda.py:345`) covers the PLUTO-specific alias; beneath them
`http.client.HTTP(S)Connection.connect` and `socket.create_connection` are the only sockets urllib
opens. There is no `requests`/`httpx`/`urllib3`, no psycopg/Supabase client, no `subprocess`, no
raw `socket.socket` use anywhere in `services/api/app`. The only uncovered theoretical paths
(a hand-rolled `socket.socket().connect()`, a C-extension client such as libpq, DNS-only egress)
correspond to no code in this service. I also confirmed the route itself reads **no** environment
variable other than the feature flag (`grep environ|getenv` on `scenario_analysis.py`: no hits) and
that no `x-app-token` is placed on an outbound header with no token present. **The producer's
claim "no egress occurs and no product change was needed" is independently confirmed.** The
residual gap is test breadth, not product behaviour.

**L-5 Request `Content-Type` is not enforced.** A body sent as `text/plain`, with no Content-Type,
or with a UTF-8 BOM is accepted and parsed as JSON (probe `p10_misc.py`). Harmless today — the
endpoints are read-only, there are no cookies/credentials to ride on, and the parse is strict — but
a `text/plain` POST is a CORS "simple request" (no preflight), so this widens the browser-reachable
surface once `API_CORS_ALLOWED_ORIGINS` is populated. Also noted: `json.loads` accepts the
non-standard `NaN` / `Infinity` literals; the engines handle them safely (see §6).

## 7. Explicit finding on the no-authentication containment question

**The service has no authentication of any kind** (`app/main.py` module docstring; M0-T007/T008
blocked on the owner's Supabase credential). For these four endpoints the *only* containment is
`INTERNAL_SCENARIO_ENABLED`.

What I verified:

1. **The flag is genuinely fail-safe and is off in every deployed environment.**
   `internal_scenario_enabled()` returns True only for `{1,true,yes,on}` after strip/lower; unset,
   empty and unknown tokens are off. `INTERNAL_SCENARIO_ENABLED` is **not declared anywhere in
   `render.yaml`** or any CI workflow — it appears only in `app/`, `tests/`, and
   `project-control/`. So today, in production, all four endpoints return a generic 404 and B-1 is
   **not** remotely reachable. The flag check is the first statement in each handler, before a
   correlation id is minted, before the body is read, and before any dependency callable is
   invoked (landmine-seam verified).
2. **Therefore B-1 is not an exposed production vulnerability today — it is a latent one**, and the
   flag is the only thing standing between it and anonymous callers.
3. **Flag reuse couples two very different surfaces.** The packet required reusing the existing
   flag (no new flag), so the same token that enables the accepted **body-less, read-only GET**
   scenario route now also enables **four POST endpoints that parse an untrusted body**. Anyone who
   flips `INTERNAL_SCENARIO_ENABLED=1` to demo or debug the accepted GET route — an internal
   staging box, a Render shell, a developer's deploy — simultaneously exposes B-1 (a 21-byte
   anonymous request that produces plain-text 500s and framework tracebacks) and M-3 (a ×437
   amplifier) to whoever can reach the host. This is a consequence of the packet's design
   instruction, not a producer error, but it materially changes what that one flag now means and
   should be recorded.
4. **My judgement:** flag gating is *adequate* containment for the accepted body-less GET route. It
   is *not* adequate containment for a body-accepting surface that currently has a reachable
   unhandled-exception path. B-1 and H-1 must be fixed before the flag is ever turned on in any
   environment reachable from outside the operator's own machine, and regardless of that, before
   the auth layer lands. M-2 and M-3 should be fixed or explicitly accepted *in writing* as
   conditions on enabling the flag — they are resource-exhaustion vectors that authentication,
   when it arrives, will mitigate only partially (an authenticated tenant can still amplify ×437).
5. Nothing here weakens the existing M1-T005 G5 condition: the service must not be publicly
   exposed until auth/organizations land. I re-affirm that condition and add: **when auth does
   land, these four endpoints need a rate/size limit, not only an identity check.**
