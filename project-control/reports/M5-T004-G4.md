## Findings

**1. HIGH — `scenario-api.ts` is a rename-clone of `rule-evaluation.ts`; a matrix fix to one will silently not reach the other.**
`apps/web/src/lib/scenario-api.ts:53-359` vs `apps/web/src/lib/rule-evaluation.ts:102-403`. Not "similar code" — line-for-line identical with identifiers renamed:
- `scenario-api.ts:175-186` `DOCUMENTED_SCENARIO_PAIRS` and `rule-evaluation.ts:222-233` `DOCUMENTED_RULE_PAIRS` are the **same ten pairs in the same order**
- `:192-194` `isDocumentedScenarioPair` ≡ `:239-241` `isDocumentedRulePair`
- `:202-206` `asRecord` ≡ `:249-253` `asRecord` (also ≡ `api.ts:156-160`)
- `:213-359` `fetchScenario` ≡ `:260-403` `fetchRuleEvaluation` — same AbortController/timeout wiring, same `timedOut` flag, same inner try/catch, same eight classification branches, same `finally`
- the twelve outcome interfaces and `scenarioOutcomeIsRecoverable` (`:155-165`) ≡ `ruleOutcomeIsRecoverable` (`:202-212`)

`docs/GATES_AND_CHECKPOINTS.md:83` lists "No duplicate or contradictory implementations" as a G4 item.

*Concrete drift scenario:* `apps/web/src/lib/contract-matrix.ts:48` **already** carries a pair the other two clients do not — `(500, "unsupported_contract_version")`. The day `services/api/app/api/v1/scenario.py:96-108` adds a pair (or `rule_evaluation.py` does), whoever fixes one client has no mechanical reason to find the other; the un-fixed client classifies a documented, recoverable server response as `unexpected_response` and shows the analyst "Unexpected response from the platform API" with a Retry that can never succeed. This is now the **third** copy of the pattern (`api.ts` → `rule-evaluation.ts` → `scenario-api.ts`).

*Fix:* extract the transport shell — `asRecord`, the pair-key set builder, the AbortController/timeout/`aborted`/`client_timeout`/`network_error` envelope, and the state→outcome dispatch — into one parameterized module (e.g. `apps/web/src/lib/envelope-client.ts`) taking `{ pathSuffix, documentedPairs, validate, copy }`, and have all three clients call it.

**ORCHESTRATOR NOTE — not a rework item for this packet.** The packet's `allowed_paths` did **not** cover `rule-evaluation.ts`, so the producer could not have done this in scope. Recorded as a separate orchestrator-scoped follow-up task. M5-T004's rework must not be held on it.

**2. HIGH — the AS-4 contract gate does not validate `cap_provenance`, so a maximum value can render with an empty optimized-objective name.**
`apps/web/src/lib/scenario-contract.ts:339-341` and `:350`; consumed at `apps/web/src/components/compare/ScenarioCard.tsx:70-99`.

**What the schema requires** (parsed, not eyeballed): `scenario.schema.json` `$defs.cap_provenance` declares `required = ["rule_id","rule_version","rule_status","output_name","citations","note"]` with `additionalProperties: false`. The top-level document likewise declares `additionalProperties: false` with 16 required keys. The generated type (`packages/contracts/generated/scenario.ts:34-41`) makes all six non-optional; `rule_status` is a 4-value enum.

**What the validator actually accepts**, in its entirety:
```ts
if (!(body.cap_provenance === null || isRecord(body.cap_provenance))) {
  problems.add("cap_provenance", "must be an object or null");
}
```
Not one of the six required fields is examined. Then `:350` returns `{ ok: true, document: body as unknown as Scenario }` — an unchecked double cast handing the caller a value typed `CapProvenance` that was never verified to be one. **The type lies.**

**Concrete failure.** A 200 body carrying `draft_zoning_floor_area_cap_sq_ft: 15000`, a valid `cap_label`, and `cap_provenance: {"note":"tbd"}` passes `validateScenarioDocument`, so `scenario-api.ts:288-298` returns `{kind:"scenario"}` and the screen renders:
- `ScenarioCard.tsx:50-52` — "Draft maximum residential zoning floor-area cap: **15,000 square feet**"
- `:75-77` — `<code data-testid="scenario-objective-name">` **EMPTY** (React renders nothing for `undefined`)
- `:83-86` — "Rule: *(empty)* (version *(empty)*, status *(empty)*)"

The analyst sees a 15,000 sq ft maximum with **no objective naming what was maximized and no rule identifying what produced it**.

**The rule it violates:** `.claude/rules/frontend-web.md:13` — *"Never show 'best' without naming the optimized objective."* `ScenarioCard`'s own header comment at `:16-17` asserts the opposite is guaranteed — "the optimized objective NAMED from `cap_provenance.output_name` (the UI rule forbids showing a 'best'/max value without naming the objective)" — so the intent was right and only the enforcement is missing. Also note `{}` is truthy, so `ScenarioCard.tsx:70` takes the **populated** branch rather than the honest "No cap provenance is attached" fallback: silent degradation, the worse failure mode.

**Why this is an AS-4 defect specifically.** AS-4 promises every 200 body is runtime-validated against scenario@1.0.0 before any render, precisely so a malformed-but-plausible payload cannot reach the screen. **The ordering is right; the depth is not.** This is defence-in-depth against a server bug — and the server has `internal_contract_error` for the same reason, so "the server validates too" is not a reason to omit it.

**Structural, not a one-off.** The same file also (a) never enforces the schema's top-level `additionalProperties: false`, and (b) omits `assumptions[].value` and `assumptions[].unit` at `:232-253`, both schema-required. Contrast `checkConstraints` at `:196-230`, which *does* check all seven required constraint keys — so this is an omission in an otherwise careful validator, not a deliberate tolerance.

*Interaction:* G5 independently found the same class (LOW) — the validator never rejects unknown keys despite documenting a "documented key set" check. G1 reached it from field presence, G4 from validator depth, G5 from key discipline: **three methods, one root cause — the validator claims guarantees it does not implement.**

*Complements DCV rather than duplicating it:* DCV CRITICAL-1 is that `cap_provenance.citations` are never **rendered**; this is that `cap_provenance` is never **validated**. Different layers, same field, and they compound — a cap can presently reach the screen with neither a verified provenance nor a displayed citation.

*Fix:* add `checkCapProvenance(problems, body.cap_provenance)` — when non-null, require non-empty `rule_id` / `rule_version` / `output_name` / `note`, `rule_status` within its 4-value enum, and `citations` as an array; and assert `cap_provenance !== null` whenever `draft_zoning_floor_area_cap_sq_ft !== null`. Add the missing `assumptions` checks in the same pass.
