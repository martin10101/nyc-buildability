## Summary

No dependencies added, no secrets, no storage/cookie/analytics/console writes, no `dangerouslySetInnerHTML`, no dynamic URL construction. The BBL is validated to `^[0-9]{10}$` with borough 1–5 before interpolation; the API base URL is build-time pinned and not runtime-influenceable. The error path is well hardened — reflected server strings are length-capped and control-stripped, the correlation id is token-allowlisted, and both 500 paths deliberately discard the server message. ## Findings

**1. MEDIUM — no bound on response size or array length on the validated success path. Not reachable today.**
`scenario-api.ts:258` calls `await response.json()` with no `Content-Length` check and no streamed read cap. `validateScenarioDocument` then walks four server-controlled arrays uncapped — `scenario-contract.ts:158` (`reasons`), `:201` (`constraints`), `:237` (`assumptions`), `:260` (`coverage_matrix`) — and the renderers map over them unbounded: `ScenarioResult.tsx:50`, `:61` (`base_district_candidates`, a weakly-typed `unknown` array read at `scenario-display.ts:96` with no cap), `ScenarioCard.tsx:103`, `CoverageMatrixSection.tsx:83`. `MAX_REPORTED_PROBLEMS = 20` (`scenario-contract.ts:116`) bounds only the problem report, not the iteration producing it.
*Attack scenario:* an actor controlling the API response returns a contract-valid document with a 500k-element `constraints` array; validation walks all 500k, React renders 500k nodes, the tab hangs with no error state. Requires controlling the response — a remote unauthenticated attacker cannot influence any array in this document.
*Fix:* cap each array during validation at a documented maximum (reject with an explicit contract problem, or truncate with a visible notice — never silently), and check `Content-Length` before `.json()`.

**Correction to the gate brief (orchestrator error, not a producer defect):** the 64 KiB / 200-leg caps cited in the review brief bound the **request** body of the separate POST analysis route (`services/api/app/api/v1/scenario_analysis.py:141`, `:381`). `GET /api/v1/properties/{bbl}/scenario` has **no response-size cap at all**; its arrays are bounded only structurally by the builder's current output shape. The UI's implicit "the data is bounded" assumption has no server-side guarantee behind it.

**2. MEDIUM — success-path strings are neither length-capped nor control-stripped, contradicting `scenario-api.ts:26-27` ("All reflected server text is length-capped and control-stripped"), which is true only of the failure path. Not reachable today.**
Raw render sites: `ScenarioResult.tsx:51` (`reasons[]`), `:120`/`:174` (`not_verified_disclaimer`); `ScenarioCard.tsx:63` (`cap_label`), `:76`/`:83-85`/`:91` (`cap_provenance.*`), `:105-108` (`constraint.key`/`unit`/`value`), `:130`/`:133` (`integrity_check.note`/`method`); `CoverageMatrixSection.tsx:85-86` (`constraint_family`/`governs`).
Sharpest instance: `constraint.value` is validated only as "key exists" (`scenario-contract.ts:211`), then `format.ts:23` `JSON.stringify`s any object straight into the DOM uncapped.
**Not XSS** — React escapes all of it, and there is no `dangerouslySetInnerHTML` anywhere in the diff. Impact is control characters reaching the DOM / clipboard / accessibility tree, plus unbounded length.
*Fix:* route success-path strings through `boundedText`/`boundedToken` inside `fetchScenario`, or correct the docstring.

**3. LOW — `validateScenarioDocument` never rejects unknown keys despite claiming a "documented key set" check** (`scenario-contract.ts:14-16`, `:306-351`; `:350` casts the raw object). No exposure — rendering is by explicit field. The risk is a maintainer trusting a guarantee the code does not provide.

## Security reviewer's ruling — bounding MUST land in the same rework

Asked by the orchestrator whether the array/string bounding should fold into the M5-T004 rework or stay carry-forward, given that the rework will surface many previously-unrendered server-controlled fields. **Ruling: same rework.** Three reasons, strongest first.

**1. `cap_provenance` is not merely unbounded, it is unvalidated — and the rework renders deeper into it.** `scenario-contract.ts:339-341` checks only "object or null"; all six of its fields already render raw at `ScenarioCard.tsx:76, 83-85, 91` with zero type checking. A non-string field there makes React throw *"Objects are not valid as a React child"* **after validation passed** — and there is **no error boundary**: `error.tsx` exists only under `/dashboard`, none under `/property`, none at the app root. **That throw blanks the route.** Surfacing the full `citations` block extends rendering further into that same unvalidated region. This part needs real per-field type checks, not bounds, and should not be deferred under any circumstance.

**2. The newly-projected fields are the worst candidates.** `assumptions[].rationale` and all 11 `constraints[].note` are free-text prose with no length discipline anywhere in the stack — the longest string in any committed fixture is already `constraints[0].note` at 342 chars. Hoisting `constraints` and `integrity_check` into the `no_scenario` branch (0 of 96 leaves render today) multiplies the raw-string sites on exactly the path finding 2 covers.

**3. Nothing upstream bounds it.** Verified against the schema directly: **no `maxItems` on any array, no `maxLength` on any string**, and the GET route has no response cap. There is no guarantee to lean on, and deferring means re-touching all 13 files and re-running five reviewers on a change the producer is already making.

**Reachability does not change** — findings 1 and 2 stay MEDIUM and still require a controlled API response. This is called on cost and coherence, **not** because the rework creates a live vulnerability. That distinction is recorded deliberately.

### Required spec (bounds grounded in measured fixture sizes: `constraints` 11, `coverage_matrix` 11, `reasons` 1–2, `assumptions` 0, `citations` 1; longest string 342 chars)

| Target | Bound | Action |
|---|---|---|
| Every document array — `constraints`, `assumptions`, `reasons`, `coverage_matrix`, `citations`, `base_district_candidates` | **64** (one shared constant) | **REJECT** — contract problem |
| Free-text strings — `note`, `rationale`, `governs`, `cap_label`, `not_verified_disclaimer`, `reasons[]`, `citations[].*` | **600** — existing `MAX_REFLECTED_TEXT_LENGTH` | **TRUNCATE** — existing `TRUNCATION_MARKER` |
| Machine identifiers — `constraint.key`, `constraint_family`, `rule_id`, `rule_version`, `rule_status`, `output_name` | **64** — existing `MAX_TOKEN_LENGTH` | **TRUNCATE** via `boundedToken` |
| Raw body before `.json()` | **256 KiB** `Content-Length` check | **REJECT** → existing `unexpected_response` |
| `cap_provenance` sub-fields (all six + `citations` element shape) | type validation, not a bound | **REJECT** — contract problem |

Both string constants already exist in `bounded.ts`; the producer reuses them and invents nothing.

**Reject for arrays, truncate for strings is deliberate.** An over-long array is a document the platform cannot produce; truncating one would *silently drop* content, and dropping a `reasons` entry hides why no scenario could be stated — the same class of silent omission G1 and DCV just failed this packet for. Reject needs no new UI either: it surfaces through the already-tested `validation_failure` card. Strings truncate because `bounded.ts:16-17` already establishes that rule, with truncation explicit and never silent.
