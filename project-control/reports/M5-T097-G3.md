PIN HEAD 83f86ce0 (matches expected). Material commit 9a281517 (4 files, all within allowed_paths). Method: old (9a281517^) vs new reader + full diff; from services/api ran `ruff check .` (clean) and `pytest test_dxf_reader.py test_dxf_roundtrip.py -q` (56 passed); static-traced the splitter vs str.splitlines; TIMED the splitter on large inputs; cross-checked INSUNITS against M5-T081-G1.md.

BLOCKING - B1: O(n^2) parse time on pure-LF (and pure-CR) input. services/api/app/drawings/dxf_reader.py:550-551 runs, every line:
    nl = text.find("\n", pos); cr = text.find("\r", pos)
When one terminator is ABSENT, its find() scans from pos to EOF on EVERY iteration. A pure-LF file (no \r) - the most common line ending, and exactly what our own dxf_writer emits (LF) - makes find("\r", pos) re-scan the whole remaining file every line: O(n^2).

Reproduced (services/api, consuming _iter_dxf_lines on "0\n"*L):
  pure-LF:  L=50k 0.49s; 100k 1.44s; 200k 6.32s  (~4x per doubling = quadratic)
  CRLF (has \r): 50k 0.20s; 100k 0.36s; 200k 0.67s  (~linear)
  str.splitlines on the same 200k: 0.012s  (~500x faster)
Quadratic extrapolation: a VALID ~2M-line (~4MB) pure-LF file - the DEFAULT max_lines - is ~10 min; near the 64MB / 8M-line ceiling it is hours. The max_lines/max_bytes bounds do NOT bound the WORK: the O(n^2) cost is paid up to the limit before refusal.

Why blocking: the packet objective is "harden ... before any user DXF can reach it" / "safe on hostile files," yet this change turns a moderately large, perfectly valid, common-format file into a CPU-pinning work-amplification DoS - and it is a REGRESSION from the replaced text.splitlines(), which was O(n). No test catches it: the AS-2 allocation probe caps max_lines=1000 (~1000 iterations) and measures MEMORY, not time. Producer fix: find the next terminator in a single bounded scan (e.g. a precompiled re.compile(r"\r\n|\r|\n").search(text, pos), or a pure-\n fast path when "\r" not in text). Part 2/3 follows.
