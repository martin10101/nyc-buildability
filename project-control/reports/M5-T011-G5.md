## Findings by severity

### BLOCKING-1 (gate: High; security severity: Medium — availability/robustness) — Uncaught `RecursionError` on a deeply-nested candidate defeats the fail-closed / strict-JSON-safe guarantee

**Location:** `services/api/app/scenario/breakeven.py:344` — `echo = copy.deepcopy(generated)` inside `_build_candidate`.

**What happens:** For each candidate the code sanitizes the value with the shared `_json_safe` (correctly, iteratively, bounding nesting to `_MAX_JSON_SAFE_DEPTH = 500`), then does `copy.deepcopy(generated)` over that sanitized structure. `copy.deepcopy` is *recursive* (~2 interpreter frames per nesting level), so a candidate nested ~500 levels overflows the default 1000-frame recursion limit and raises `RecursionError`, which propagates out of `find_scenario_threshold` (no try/except on the path). The sanitizer's whole L2 design goal — "never raises RecursionError regardless of depth" — is silently undone by this intervening recursive copy. `derive()` itself is not implicated: it rejects a non-numeric (dict/list) factor value via `_invalid_assumption` *before* it deep-copies it, so line 344 is the sole crash site.

**Reproduction (live, reviewed SHA, Python 3.11.9, default recursionlimit=1000):**
```
find_scenario_threshold(doc, ThresholdVariable.UTILIZATION_FACTOR, 13000, [nested(500), 0.9])
# nested(n) = a dict {'n':{'n':{...}}} n levels deep
depth=  300 OK   kind=target_already_met  (json_ok)
depth=  400 OK
depth=  500 RAISED RecursionError: maximum recursion depth exceeded
            last breakeven.py frame: line 344 in _build_candidate: echo = copy.deepcopy(generated)
            crash site: copy.py line 229 _deepcopy_dict
depth= 1000/5000/10000 RAISED RecursionError  (same site)
```
A deeply-nested list candidate (`[[[...]]]` 600 deep) raises identically. Contrast — the sanitized structure itself serializes fine at every depth:
```
_json_safe(nested(500|600|5000)) -> json.dumps(allow_nan=False) OK (len=3618, truncated at 500 w/ max_depth marker)
copy.deepcopy(_json_safe(nested(600))) -> RecursionError   <-- root cause
```

**Why in-scope:** the packet commits the finder to fail-closed for ANY candidate (AS-4 "No unhandled raise"; AS-5 "never raises for any input"), and the module's own docstring claims the shared sanitizer makes json.dumps never raise. Every other pathological candidate class is handled fail-closed and verified (huge-int 10**5000, unserializable object, cyclic list/dict, non-string dict keys, NaN/Inf). A deeply-nested candidate is squarely in the same class and is the one gap — both a code defect and an acceptance-pack coverage gap (LOW-1).

**Reachability (honest):** Currently the module is a contract-free service function with no HTTP endpoint wiring, so there is no external attacker path today — not a data-exfil, cross-tenant, secret-leak, or Verified-fabrication issue. If/when wired to an endpoint accepting a JSON `domain` array, a ~500-deep nested candidate would force an uncaught exception (HTTP 500 / availability). Python's own JSON parser accepts ~500-deep input, so it would reach this code. Given the packet's emphatic "for ANY input" hard boundary and the explicit security probe, held blocking for the G5 gate.

**Remediation (direction verified viable):** the `copy.deepcopy(generated)` is redundant for read-only safety: `_json_safe(candidate)` already returns a fresh structure that never aliases the caller's input, and `derive()` deep-copies assumptions internally and rejects our non-numeric candidate before copying it. Replace line 344 with a non-recursive construction (build `echo` directly from the already-fresh sanitized fields instead of re-deep-copying); the emitted ≤500-deep echo then serializes safely. Confirm with a red/green test that (a) derive() does not mutate the shared echo and (b) the sanitizer output does not alias the input at depth. Do NOT raise sys.setrecursionlimit (that reintroduces the exact stack-dependence L2 exists to avoid).
