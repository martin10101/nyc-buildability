G5 SECURITY REVIEW (1/4) — M5-T081 DXF writer (services/api/app/cad/dxf_writer.py, material 4fd58a98). HEAD verified 1414e1a7.

VERIFIED CLEAN:
- Imports math/collections.abc/dataclasses — stdlib only; no network/file/clock/random I/O; zero new deps.
- ONE sanitizer is the sole output path: every line enters via `_GroupCodeStream.pair` (`real`→`pair`; `render` only joins pair output; grep shows no other `_lines.append`). `_sanitize_value` (L203-218) allowlists bytes 0x20–0x7E only, rejecting CR/LF/all control chars/DEL/non-ASCII (incl. lone surrogates via `ord`) as a TYPED `DxfSanitizationError` — no scrub-and-continue. Group codes are `str(int(code))` (integer-only, no smuggling). CR/LF group-code smuggling via `TextLabel.text` (deliberately unsanitized at validate, L366-369) is blocked at emit (L530 `pair(1, text.text)`). Layer names double-guarded: `_validate_layer_name` allowlist (A-Z0-9_$-, ≤31) + emit sanitize. No injection defect.
- Non-finite coords rejected up front (`_format_real` L194; every entity `validate`). Determinism: LF EOL, `.6f` fixed precision, -0.0→0.0, no dict/set in output, no clock. Info leak: none — fixed GENERATOR_NOTE constant, no path/env/timestamp.

FINDINGS:
F1 (MEDIUM, ADVISORY — resource bound; dxf_writer.py:655-704). `build_site_plan_document` materializes `rings`/`faces`/`lines` BEFORE `doc.validate()` enforces MAX_ENTITIES(50k)/MAX_RING_VERTICES(10k). `floor_heights` has NO count cap (L657) and `_normalize_ring` (L563) has NO vertex cap, so `faces = len(building_ring) × len(floor_heights)` (L689-704) is built in memory before the late cap check → memory-exhaustion DoS on a caller-supplied huge floor count or building ring. The direct `serialize_document(doc)` entry is safe (validate() checks the entity cap before rendering); the gap is the builder. Repro: `build_site_plan_document([(0,0),(1,0),(1,1)], [(0,0),(1,0),(1,1)], [1.0]*10_000_000)` allocates ~30M Face3D before refusing. Fix: before materializing, refuse `len(building) > MAX_RING_VERTICES` and `len(building)*len(floor_heights) > MAX_ENTITIES`, and cap `len(floor_heights)`.

F2 (LOW, ADVISORY). No coordinate-magnitude bound (unlike the PDF writer's 1e8): a finite but astronomically large coord formats to a ~300-digit `.6f` string (printable, passes sanitizer) and would confuse AutoCAD. Bounded per-value; not a vuln — consider a magnitude guard for interoperability.

M5-T081 G5 VERDICT: PASS

G5 SECURITY REVIEW (2/4) — M5-T085 PDF site-plan writer (services/api/app/cad/pdf_sheet_writer.py, material 519bc360).

VERIFIED CLEAN:
- Imports math/dataclasses — stdlib; no network/file/clock/random I/O; zero new deps.
- ONE escaper is the sole text path: all strings enter the content stream via `_draw_text`→`_escape_pdf_text` (L322-346); numbers via `_num`; operators are literal constants. `_escape_pdf_text` maps every byte outside 0x20–0x7E to "?" (kills CR/LF/control/non-ASCII; defeats Unicode/normalization tricks) then backslash-escapes `(` `)` `\` → a user address/BBL cannot unbalance or early-terminate the literal string, inject operators, or smuggle `endstream` (it stays inside balanced parens and `/Length` is byte-exact). Title block feeds user address/bbl/generated_at/generator_version (L301-310) — all through the escaper. No injection defect.
- xref/offset integrity: offsets computed from actual byte lengths (`len(out)` per object), `/Length = len(content)`, `{offset:010d} 00000 n`, classic free entry `f`, trailer `/Size`/`/Root`, `startxref`, `%%EOF` — ISO 32000-1 §7.5, byte-exact and input-independent. Content is pure ASCII (escaper + `_num` both emit ASCII), so `.encode("latin-1")` len == byte len; no xref/offset corruption from input.
- Determinism: `generated_at`/`generator_version` are INPUTS, never a clock; `_num` rounds to 3dp and collapses -0.0; no random. Resource bound: `_MAX_RING_VERTICES=1024` checked right after `tuple(ring)` and before per-vertex work; `_MAX_COORD_ABS=1e8`; oversize/zero-extent/non-finite → typed `SitePlanRefusal`. Info leak: none (no path/env/timestamp).

FINDINGS:
F1 (LOW, ADVISORY — robustness/contract; `_validate_ring` L186-220). The docstring promises "never raises on caller data; every refusal is a returned SitePlanRefusal," but a malformed `SitePlanInput` RAISES instead: a non-iterable `lot_ring` → `tuple(ring)` TypeError; a vertex with no `len` (e.g. an int) → `len(vertex)` TypeError (L199); a non-numeric coord ("a") → `float(...)` ValueError (L201) — and these echo the offending value. If a future route doesn't wrap the call, that surfaces as a 500/stack rather than a typed refusal. Fix: guard `isinstance`/`len`/`float(...)` and return `SitePlanRefusal("invalid_ring", …)`.

F2 (LOW, ADVISORY). `_num` (L349) has no finite guard; NaN/inf would render the token "nan"/"inf" into the stream. Not reachable today (all coords pass `_validate_ring`'s finite check; derived values stay finite), but a defensive guard hardens it against future callers.

M5-T085 G5 VERDICT: PASS

G5 SECURITY REVIEW (3/4) — M5-T082 massing truth object (services/api/app/scenario/massing_model.py, material b9b0d31e).

VERIFIED CLEAN:
- Imports hashlib/json/math/collections/dataclasses/typing (stdlib) + numpy + shapely (admitted deps, per docstring) + internal `.proposal`. No network/file/clock/random I/O. Zero NEW deps.
- Inputs validated finite: `_is_finite_number` rejects bool/NaN/inf on every coordinate (`_prepare_ring` L198) and floor height (`_expand_floor_stack` L468). Footprint AND per-level outlines pass `validate_proposed_massing` FIRST (L577), which bounds coords to NYC 2263 (~1e6), caps levels≤500 / floor_count≤500 / vertices≤1000, and guarantees each level is a dict — so `_expand_floor_stack`'s `sorted(...level_index...)` and `.get("outline")` cannot raise. Floor stack capped at MAX_TOTAL_FLOORS=2000 (bounded materialization). Output JSON is strict (`to_json` `allow_nan=False`, L421). Honesty labels fixed to proposed/generated_option. Provenance = input digests + passthrough + constant version (no clock/env/path). Determinism: quantise 6dp, sort_keys, deterministic numpy reductions.

FINDINGS:
F1 (MEDIUM, ADVISORY — this is the threat-model NaN/inf path). The `lot_ring` argument is NOT magnitude-bounded — only finiteness + vertex count in `_prepare_ring`, and holes/validity in `_lot_polygon` (L514-527). A lot ring with near-overflow coordinates (~1e154) makes `Polygon(lot).area` and `.centroid` overflow to ±inf/NaN → `parcel["area_sq_ft"]`, `metrics.lot_area_sq_ft`, and `crs.local_origin` become inf/NaN → a later `MassingModel.to_json()`/`content_hash()` RAISES `ValueError` ("Out of range float values are not JSON compliant", confirmed by probe) instead of a typed `MassingModelError`. A giant lot polygon whose corner sits at real NYC coords still `contains` the NYC-bounded footprint, so the containment gate (L593-606) does NOT block it. This is exactly the "untrusted numeric input → inf into JSON / crash not a typed refusal" case the threat model asked me to judge. Fix: bound `|x|,|y|` in `_prepare_ring` (mirror the PDF writer's `_MAX_COORD_ABS`) so overflow is impossible and the refusal stays typed.

F2 (MEDIUM, ADVISORY — resource bound). `_triangulate` (L236-281) is worst-case O(n³) — per-ear O(m²) containment scan × n ears — on rings up to MAX_OUTLINE_VERTICES=1000, run once for the footprint plus once per distinct per-level outline (≤ MAX_LEVELS=500, cached per level_index but NOT deduped by content). A crafted-but-valid proposal (500 distinct 1000-vertex outlines) forces ~1e9 ops × ~500 ≈ minutes-to-hours of CPU per request → authenticated CPU-DoS once wired. Fix: cap triangulated-ring vertices well below 1000, and/or a per-request triangulation-work budget, and/or content-dedupe identical outlines.
