## 6. Findings by severity

### BLOCKING for the next gate and for acceptance (required corrections)

**C1 — HIGH — AS-1: the pack cannot detect the route discarding the caller's illustrative
parameters.**
`services/api/tests/api/test_scenario_analysis_api.py:316-340`
(`test_as1_endpoint_returns_engine_result_envelope`) asserts the result only through
`result[kind_field] == kind` — a discriminator string the engine emits regardless of input. Two
mutations survive all 75 tests:

* M11 — `services/api/app/api/v1/scenario_analysis.py:585` passes `None` instead of
  `body.get("values")`;
* N4 — `services/api/app/api/v1/scenario_analysis.py:618-620` passes `None` instead of
  `body.get("assumption_sets")`.

The defect is plainly visible in the response body, so the gap is purely in the assertions. Probing
the shipped code:

```
SENSITIVITY (3 values supplied):  "sensitivity_kind": "sensitivity_response", ... "point_count": 3
SENSITIVITY (values OMITTED)   :  "sensitivity_kind": "sensitivity_response", ... "point_count": 1
RANKING (2 sets supplied)      :  "ranking_kind": "...", "candidate_count": 2, "candidates": list[2]
RANKING (sets OMITTED)         :  "ranking_kind": "...", "candidate_count": 1, "candidates": list[1]
```

*Minimal fix (not applied at this gate):* in the AS-1 parametrised test, assert the request->result
cardinality per endpoint — `result["point_count"] == len(SENSITIVITY_BODY["values"])`,
`result["candidate_count"] == len(RANKING_BODY["assumption_sets"])` and
`len(result["candidates"]) == 2`, and the equivalents for comparison and threshold.

**C2 — MEDIUM — AS-4: one emission path has no state assertion, so an undocumented (status, state)
pair ships green.**
`services/api/tests/api/test_scenario_analysis_api.py:621-639` (`test_as5_assumption_set_caps`)
asserts only `status_code == 422` on both of its cap paths. Mutation M6c rewrote
`services/api/app/api/v1/scenario_analysis.py:390-394` to emit `(422, "too_many_sets")` — a pair
absent from `STATUS_STATE_MATRIX` — and all 75 tests passed.
`test_as4_every_emitted_pair_is_in_the_matrix` (line 475) is otherwise excellent (it asserts set
**equality**, both directions, over all nine pairs) but it never drives either cap helper.
*Minimal fix:* add `assert response.json()["state"] == "validation_error"` to both halves of
`test_as5_assumption_set_caps` — the sibling `test_as5_candidate_domain_length_cap:617-618` already
does this, which is exactly why M6e was caught and M6c was not.

**C3 — MEDIUM — AS-6: "never Verified" is only checked on `coverage_status`-keyed values.**
`_coverage_values` (`services/api/tests/api/test_scenario_analysis_api.py:300-308`) yields values
**only** under a key literally named `coverage_status`, and line 680 checks
`envelope["coverage_status"] != "verified"`. Mutation M5c added
`"verified": True, "verification_status": "verified"` to the 200 envelope at
`services/api/app/api/v1/scenario_analysis.py:533` and all 75 tests passed. For a platform whose core
legal guarantee is "nothing is ever Verified", this check must not depend on the key name a future
defect happens to choose.
*Minimal fix:* scan every string value in the envelope (not just `coverage_status` keys) for
`"verified"` case-insensitively, and/or pin the exact envelope key set.

**C4 — MEDIUM — AS-5: the body-bytes cap has no isolating test; removing it entirely ships green.**
`services/api/tests/api/test_scenario_analysis_api.py:569-576`
(`test_as5_oversized_body_is_typed_422`) builds one `"note"` string of `MAX_BODY_BYTES + 10`
characters. That string trips `MAX_STRING_LENGTH` (4096) long before the byte cap is consulted, so
the test passes for the wrong reason. Evidence: mutation M3a (delete the `MAX_BODY_BYTES` check at
`services/api/app/api/v1/scenario_analysis.py:322-325`) -> `75 passed`; mutation M3ac (delete the
byte **and** string checks) -> that same test fails with `assert 500 == 422`, i.e. it never reached a
cap at all. The product cap itself is functional — I verified a 124 860-byte body of 100-character
strings returns `422 validation_error / "request body exceeds the maximum of 65536 bytes"`, and a
62 460-byte one returns 200.
*Minimal fix:* build the oversized body from **many short strings** (e.g. `["q"*100] * 1200`) so only
the byte cap can reject it, and assert the message names the byte cap.
*Context:* `MAX_BODY_BYTES` is a producer-added sixth cap; AS-5 and the packet objective name only
five (assumption sets, candidate-domain length, assumptions per set, nesting depth, string length),
and each of those five **is** load-bearing (M3b-M3f all RED). That is why C4 is Medium rather than a
verdict-changing defect.

### Non-blocking findings (record; fix opportunistically)

**C5 — LOW/MEDIUM — AS-5: every cap assertion is relative to the module constant, so loosening a cap
is invisible.** The tests import `MAX_BODY_BYTES`, `MAX_CANDIDATE_DOMAIN_LENGTH`,
`MAX_ASSUMPTION_SETS`, `MAX_ASSUMPTIONS_PER_SET` (lines 46-52) and send `CONSTANT + 1`. Raising

leave 75 green. The pack proves "the route enforces whatever number it declares", never "the route
declares a bounded number". One assertion pinning the six declared values (or an upper bound on each)

`>` -> `>=` (N15a-d, at `scenario_analysis.py:273`, `:279`, `:373`, `:389`) survive. The shipped

200), it is simply unasserted — so a future tightening that rejected legitimate at-limit requests
would ship green. Caps are tested at N+1 only.

**C7 — LOW — AS-7: registration order is unpinned by any test.** Mutation M7b moved

Deleting a registration **is** caught (M7a RED, M7c RED).

**C8 — LOW — AS-2: the fact-key parametrisation is an 11-of-23 subset, and nested placement is
untested.** `FORBIDDEN_FACT_KEYS` (`scenario_analysis.py:140-166`) holds 23 keys; the parametrised
test (lines 363-378) covers 11. I verified the other 12 (`profile`, `evaluation`, `document`,
`canonical_cap_sq_ft`, `cap_value`, `cap_label`, `coverage_matrix`, `coverage`, `data_completeness`,
`verification`, `needs_review`, `professional_review_required`) all return 422 — no defect — but
narrowing the frozenset to drop one of those 12 would ship green. Separately, the guard is top-level
only by design (documented at `scenario_analysis.py:135-139`, implemented at `:349`); I confirmed a
**nested** fact key (`{"assumption_sets":[{"name":"a","assumptions":[],"scenario":{cap:1e9}}]}`)
returns 200 with the cap **unchanged at 15000.0**, and a fact key one level under a legitimate key
likewise cannot move the cap. The security property holds; AS-2's "never merged" simply has no
nested-placement test. Parametrise the full frozenset and add one nested-placement test asserting
`scenario_cap_sq_ft == TRACE_CAP`.

**C9 — LOW — AS-1: the threshold endpoint's documented default is never exercised.** `THRESHOLD_BODY`

`scenario_analysis.py:688-690` is dead in the pack; mutation M12 replaced
`ThresholdResponseMetric.USABLE_RANGE_POINT` with the string `"not-a-metric"` and 75 passed. Add one

**C10 — INFO — one defensive branch and three endpoints are unexercised for JSON safety.** The
pre-send `json.dumps(envelope, allow_nan=False)` guard (`scenario_analysis.py:536-544`, which maps to
`(500, internal_contract_error)`) is never driven — removing it entirely leaves 75 green (M13). And

`json.dumps(..., allow_nan=False)` when fed `NaN` / `Infinity` literals, so AS-5/AS-6 hold in fact —

**C11 — INFO (product observation, not a test gap).** `MAX_BODY_BYTES` is checked *after*
`raw = await request.body()` (`scenario_analysis.py:321-325`), i.e. the whole body is already
buffered in memory before the cap is consulted. The cap therefore bounds *processing*, not
*ingestion*. AS-5 does not require an ingestion bound and the deployed edge imposes its own limits,
so this is recorded rather than charged against the task. If it is ever tightened, a `Content-Length`
pre-check is the place.
