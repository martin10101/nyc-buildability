## Part 5a — Blocking finding F1

**F1 (BLOCKING). AS-4 adoption is unreachable by construction; the AS-5 stub returns a server state the asserted request cannot produce.**

`maxEnvelopeRequestForProfile` (`max-envelope-api.ts:527-548`) always sends `lot_line_segments: []` and `street_lines: []`. On the server, `_build_lot_context` carries those into `LotContext`, and `_lot_rectangle` (`max_envelope.py:632-636`) returns `None` for empty segments:

```python
    segments = lot.lot_line_segments
    if not segments:
        return None, (
            "no lot-line geometry was supplied, so the footprint cannot be fitted to the lot; "
            "no candidate is emitted (never a fixed-anchor schematic)"
        )
```

The caller (`max_envelope.py:795-798`) then returns `CandidatePlacementStatus.LOT_GEOMETRY_UNSUPPORTED` with no candidate. So `candidateIsAdoptable` is false for every response this client can ever elicit, and the "Adopt as a proposed starting draft" button can never appear on the real surface.

The producer knows this and says so in a code comment (`max-envelope-api.ts:41-42`, :520-525). That is honest as documentation. The problem is the proof: `proposal-editor.spec.ts:543` asserts the exact real request with a strict `toEqual` and then returns `candidate_placement.status: "fitted"` — so within one test the request half is real and the response half is counterfactual, and the two contradict each other.

Every adoption assertion in the packet (panel, entry, editor, e2e) rests on that same unreachable fixture. This is not a scope limitation from the route being unmounted; it is an internally inconsistent proof, and it is exactly what a G4 integration gate exists to catch.

**Required correction (F1):** state the limitation plainly in the producer report and evidence map as a named AS-4 limitation, and commit at least one test asserting the production-reachable state — placement `lot_geometry_unsupported` with `candidate: null` rendering the honest `candidate-unavailable` card — so the mount seam cannot silently ship a permanently dead adoption affordance. The honest card text will read well: the panel renders `envelope.placement.detail`, which is the server's own prose quoted above.

## Part 5b — F2

**F2 (BLOCKING correction). Placement-status fixtures use an invented enum value.**

`max-envelope-panel.test.tsx:193` and `max-envelope-api.test.ts:297` both use `status: "no_fit"`. The server enum `CandidatePlacementStatus` (`max_envelope.py:149-171`) has no such member — the values are `fitted`, `no_saturating_binding`, `lot_geometry_unsupported`, `footprint_exceeds_lot`, `construction_invalid`. I grepped `services/api` and `packages/contracts`: `"no_fit"` does not exist server-side.

The assertions still hold (any non-`fitted` value is non-adoptable), so this is not a false pass, but no real non-`fitted` value is exercised anywhere in `apps/web` — including `lot_geometry_unsupported`, the one value production will always return. In fairness, the packet's binding input says "exact names — never guess", and the field *names* are correct; the *value vocabulary* is where the guessing happened.

**Required correction (F2):** replace `"no_fit"` with real enum values, covering `lot_geometry_unsupported` at minimum.

## Part 5c — F3

**F3 (BLOCKING correction). `gap_reason` fixtures use free prose where the server emits an enum token.**

`max_envelope.py:319` serializes `"gap_reason": reason.value`, one of four `EnvelopeGapReason` tokens (`no_applicable_rule`, `allowance_unresolved`, `family_unsupported`, `non_commensurable_with_massing`). But AS-1's typed-gap display is proven only against a shape the server never emits, and this will be the common case, since sending no `street_lines` makes wide-street-dependent dimensions gap out.

**Required correction (F3):** fix the fixtures to real tokens, and decide the analyst-facing rendering — either a token-to-copy mapping or leading with `detail`.
