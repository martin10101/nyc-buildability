## Threat-by-threat findings

### Threat 1 — Weakening the tamper guard (residual-forgiveness analysis)
Normalization primitive (`tools/directive_registry.py:390-401`):
`return data.replace(b"\r\n", b"\n").replace(b"\r", b"\n")`

Exact equivalence classes that now hash identically (empirically confirmed):
- Any two byte strings differing **only** in line-break representation, where a break may be `\r\n`, `\n`, or a bare `\r`. Confirmed: `ab\ncd` ≡ `ab\rcd` ≡ `ab\r\ncd` → all normalize to `ab\ncd` (digest `41b72d4b…`).
- **No non-CR/LF byte is ever altered.** Word characters, digits, dates, requirement IDs, punctuation are byte-preserved. An attacker **cannot** change a word, a number, a date, an ID, or flip "REMAINS HELD" — the semantic text of a directive is fully protected. The character sequence (excluding CR/LF) is identical and in the same order under the map.
- Byte-count is **not** naively collapsed: `a\r\rb`→`a\n\nb` (two breaks) while `a\r\nb`→`a\nb` (one). So an attacker cannot freely add or delete logical line breaks; they can only substitute an existing break's representation.

The one genuinely **new** forgiveness versus the prior raw-byte hashing (the exact case the threat model flagged): a **bare CR inserted mid-line** hashes identically to an LF line break. Assessment by artifact type:
- **requirements.json — NEUTRALIZED.** `json.loads` **rejects** a raw control char (`Invalid control character`, confirmed empirically for both raw `\r` and raw `\n` inside a string value). The validator parses requirements.json as JSON elsewhere in the load path, so a raw CR embedded in a requirements body fails parsing → fail-closed. The higher-value, machine-consumed artifact is therefore protected.
- **source-*.md — residual is live but LOW severity.** Free-text Markdown has no parser gate, so `ab\rcd` on disk hashes the same as the attested `ab\ncd`. Exploitability to change **meaning**: LOW because (a) no word/value/ID/date can change — only line reflow/Markdown block structure; (b) prose reflow rarely flips meaning with the identical character stream; (c) modern consumers (GitHub, VS Code, `git diff`) render a bare CR as a line break or a visible control glyph, so attested vs actual rendering seldom diverges; (d) the digest is defense-in-depth behind commit/write access, git review, the append-only source rule, and the c2 check itself.

AS-5 coverage: `test_content_tamper_still_detected_under_crlf` (`tools/test_directive_compliance.py:614-628`) covers **character-substitution** tampering only (independently reproduced: PASS). It does **not** exercise the mid-line-CR class, which is **intentionally** forgiven and asserted-forgiven by AS-1's `test_crlf_lf_and_lone_cr_hash_identically` (`:571-591`, independently reproduced: PASS) and documented in the `normalize_text_artifact_bytes` docstring. So the residual is by-design and documented, not an unnoticed hole.

→ **F-1 (advisory)** and **F-2 (advisory)** below.
