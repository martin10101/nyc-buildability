FINDING 1 race (cont.): production `run_in_threadpool` runs with abandon_on_cancel=False, so on cancellation anyio either never dispatched the worker (started stays False -> cancel-path release) or waits for the running thread to finish (worker finally already released, started True -> cancel path no-ops). The two release owners are mutually exclusive; no leak, no double-release. The only theoretical transient (slot freed while a worker still runs) needs a NON-production abandon-on-cancel runner that also runs the worker after cancel — unreachable with the real runner, availability-only, and documented at rate_limit.py:300-304. INFO, not blocking.

SLOT COUNT vs anyio POOL (48 > 40): I confirmed anyio's default thread limiter = 40 tokens. The fix converts the former PERMANENT leak into a self-healing per-request timeout, but Sum(max_slots)=3x16=48 still exceeds 40, so under concurrent load a slot can be held while its worker waits for a token and the request times out (fail-closed, availability-only, no leak/exposure).
