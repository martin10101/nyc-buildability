## FINDINGS

**1. BLOCKING — Nothing proves `grc2` is the 1a sub-call. The whole S2 premise is untested semantically.**
`services/api/app/connectors/geoclient_address.py:525-526,546` reads `geosupportReturnCode` / `geosupportReturnCode2`. All three recorded fixtures are degenerate: G01 is `00/00`, G02 is `EE/EE`, G03 is `42/42`. The only asymmetric test, `test_geoclient_address.py:171-179`, writes `geosupportReturnCode2="42"` and reads back `res.grc2` — a same-key round trip that proves nothing about which sub-call that key represents. The packet objective names `returnCode1e` **and** `returnCode1a` explicitly, and all three fixtures carry both aliases (`returnCode1e`/`returnCode1a`), but no test asserts them at all (`grep` for `returnCode1` in the test file: zero hits).
*Failure scenario:* swap `grc` and `grc2` in the connector, or read `returnCode1a` into `grc` and `returnCode1e` into `grc2`. All 36 tests still pass. Every ambiguity/rejection message would then be attributed to the wrong sub-call for the caller and for provenance.
*Correction:* add a constructed variant with `geosupportReturnCode="00"`/`returnCode1e="00"` and `geosupportReturnCode2="EE"`/`returnCode1a="EE"` and assert the outcome's `grc`/`grc2`/`grc_message`/`grc2_message` land on the right side; assert `res.grc == addr["returnCode1e"]` and `res.grc2 == addr["returnCode1a"]` on all three recorded fixtures.

**2. BLOCKING — The `os.environ` read path is never executed by any test; S6's central claim is unproven.**
`geoclient_address.py:472-473`: `source = os.environ if env is None else env` then `source.get(KEY_ENV_VAR)`. Line 473 only runs when `key is None`. Every test either passes `key=SENTINEL_KEY` (via `_resolve`, `test_geoclient_address.py:80-88`) or passes an injected `env=` mapping (`:354`, `:365`, `:399`). **No test ever sets the real environment variable.** The accepted sibling precedent does exactly that — `test_pluto_soda.py:399` uses `monkeypatch.setenv("SOCRATA_APP_TOKEN", token)`.
*Failure scenario:* change line 472 to a module-level snapshot captured at import (`_ENV = dict(os.environ)`), or misspell the lookup so it reads a different variable through a helper. Every test passes. The packet's "read at call time from `GEOCLIENT_SUBSCRIPTION_KEY`" is asserted only against a dict the test itself constructed.
*Correction:* a `monkeypatch.setenv(KEY_ENV_VAR, ...)` test with `env=None`, plus a second call after changing the value in the same test to prove "at call time" (no caching).

**3. BLOCKING — The zip-only request path has no test; half the documented endpoint contract is unexercised.**
`geoclient_address.py:487-488` (`params["zip"] = zip_in`) never executes. `zip_code=` appears nowhere in the test file. Untested: zip-only, borough+zip both present, the `zip_in` echo field, and the zip param's appearance in the URL and in `provenance["request_params"]`.
*Failure scenario:* the param is named `zip` per research §2.2 — a rename to `zipCode` or `zip_code`, or dropping the param entirely when borough is absent, ships undetected. Every zip-based lookup then 400s or silently resolves the wrong address in production.

**4. BLOCKING — The S6 leak-absence harvest has no positive control and can pass vacuously.**
`test_geoclient_address.py:315-344`. Three defects compound:
- Nothing asserts the sentinel actually reached `headers[KEY_HEADER]` on any of the six harvested runs. If the connector stopped sending the key entirely, the harvest still passes.
- `:332-341` wraps each failure in `try/except GeoclientConnectorError` with no `else: pytest.fail(...)`. A failure path that stops raising is silently skipped and contributes nothing to `harvested`.
- Nothing asserts `caplog.records` is non-empty. If propagation or the logger name changed, the log-leak half of the assertion becomes an assertion about an empty list.

Also `:343` harvests `record.getMessage()` rather than `caplog.text`, so logger names, levels, and `record.exc_text` (exception tracebacks attached by `logger.exception`) are outside the harvest; `test_pluto_soda.py:410` uses `caplog.text`.
Additionally `caplog.set_level(..., logger="app.resilience.transport")` at `:320` is inert — the retry loop logs through the **connector's** logger (`geoclient_address.py:391` passes `logger=logger`), so no record is ever emitted under that name.

**5. BLOCKING — The emitted URL does not match the URL the fixtures were captured with, and no test compares them.**
`geoclient_address.py:489` uses `urlencode(params)`, which is `quote_plus`: the connector emits `street=w+100+st`. All three fixtures record `request_url` as `...street=w%20100%20st`. Both sibling connectors use `quote(..., safe='')` (`zoning_features_arcgis.py:451,593,595`), i.e. `%20`. `test_geoclient_address.py:152` asserts only `"houseNumber=314" in url and "borough=manhattan" in url` — it deliberately avoids the one param that differs.
*Failure scenario:* if the APIM gateway or Geosupport does not decode `+` as a space in `street`, every live call resolves `"w+100+st"` and fails, while all 36 offline tests stay green. The fixtures are the only evidence of live behavior and they document a different encoding. Either align the encoding with the captured URL or add a test asserting the constructed URL equals the fixture's recorded `request_url`.

**6. HIGH — `_extract_suggestions` is only ever exercised with a single, perfectly contiguous slot.**
`geoclient_address.py:315-337`. G02 has `numberOfStreetCodesAndNamesInList="01"`, so `count == 1` in the only test that reaches this function (`:202-220`). Research §2.7 (doc line 115) documents reason codes `2`–`A` = "THERE ARE `<n>` SIMILAR NAMES" — the multi-suggestion case is exactly what "suggestions surfaced, never guessed" is about, and it has no test. Unreached branches inside the function: the `except (TypeError, ValueError)` fallback to `_MAX_SUGGESTIONS` (absent or non-numeric count, e.g. a JSON number `2` → `str(2)` is fine but `2.0` → `"2.0"` → ValueError); the high clamp (`min(count, 32)` with a hostile count like `"999"`); the low clamp (`max(0, ...)` with a negative); the `continue` for a missing or blank middle slot; and the name-present/code-absent branch that omits `street_code`.

**7. HIGH — `resolved_with_warnings` is never shown to carry a warning message.**

The producer report acknowledges no natural `01` capture; the constructed substitute doesn't close the gap because it omits the message fields.
