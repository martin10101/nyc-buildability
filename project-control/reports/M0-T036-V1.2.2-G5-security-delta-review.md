## G5 focus items — findings

### (1) Model chain + order live in immutable, owner-editable-only config; no lower-trust mutation — HOLDS
- `[model_chain].orchestrator_preference` is read **only** in `load_controller_config` via `_load_model_chain` (`config.py:339,352`). The runtime file loader `load_model_selection` never reads it, and `ModelSelection` has no chain field. A `[model_chain]` in the runtime file cannot reach the loop.
- `manifest.py:48` lists `config.toml` in the covered set → the chain is **manifest-covered** (S13.1); tampering is detectable. Owner-editable-only is enforced by manifest detection + the S13.1 controller-update process.
- The loop receives the chain exclusively from the immutable config: `cli.py:2056 model_chain=config.model_chain`. `SupervisedLoop` never invents or reorders an entry (`loop.py:646-653`).
- A worker/reviewer subprocess has no channel to the controller's sqlite journal or config: it gets `minimal_env` (allowlist) + worktree only (`process.py:165`). It cannot mutate the chain, `_current_model`, or a probe result.

### (2) Non-chain ids (e.g. Opus 5) genuinely unselectable — HOLDS
- `ModelChain.candidates_after` (`config.py:248`) returns only entries drawn from the chain. `__contains__` is EXACT string match (no normalize/alias/prefix; `config.py:237`).
- `_actuate_model` (`loop.py`) refuses any id that is not in the chain and not the pin (`raise LoopError("model_not_in_chain")`). This is the belt-and-braces gate: the only ids that can reach a `--model` launch are chain entries + the owner pin.
- The launch probe rejects a process that reports a **different** id than asked (`PROBE_MODEL_ID_MISMATCH`, `claude_runner.py`) — a picker silently resolving to Opus 5 does NOT make the asked-for id available, and Opus 5 never becomes selectable by being reported. Proven by `test_a_process_that_reports_another_id_does_not_make_that_model_available` and `test_an_unlisted_id_is_never_selectable_even_if_it_launches`.
- Config poisoning of a resumed run fails closed: `effective_model` → `_actuate_model` rejects an unlisted id at construction (loop refuses to start rather than launching on it); a valid chain entry self-heals via return-to-pinned.

### (3) Launch probe cannot reach anything the trust zones forbid — HOLDS
- The probe launches via the same hardened path as a worker: `build_argv` (enforces `--permission-mode`=required and the broker `--permission-prompt-tool`; `claude_runner.py:184-201`) + `minimal_env` allowlist. It is contained in a `ProcessContainer` (Job Object default on Windows), adopts the pid, and `terminate_all()`s the moment a model id is observed, with a watchdog timeout. No live unattended session survives.
- Probe output is treated as **untrusted data**: model ids are extracted only via `_event_models` (structured read of `model`/`message.model`/`modelUsage` keys — `claude_runner.py:400`), never free-text/instruction parsing. stderr is passed through `neutralize_untrusted` (labels injection) and truncated.
- **CONTROLLER/WORKER/REVIEWER separation:** the probe launches the **claude** runner config only; it never touches the codex reviewer. `make_launch_probe` is wired in exactly one place (`cli.py:2032-2033`), guarded by `session_role == SESSION_ROLE_ORCHESTRATOR`. Reviewer/worker paths keep the previous seam default (untouched). R359/R434 (reviewer never gets write) and R105 (IPC not reachable by worker) are unaffected — `codex_reviewer.py` and `model_change_ipc.py` are not in the delta, and the chain switch is an in-process seam-time runner rebind, not the S3.2 owner-confirmation IPC. `session_role` is a supervisor CLI arg a subprocess cannot set.

### (4) No secrets / model-quota state leak beyond bounded+redacted evidence — HOLDS
- Every audit record passes through `redact_structure` **before** persistence (`audit_log.py:171-177`), which masks provider keys (sk-ant, OpenAI, GitHub PAT/fine-grained, AWS, Slack, Google, bearer, basic-auth URL, private-key blocks, JWT, `KEY=value` secrets) and sensitive-keyed dict values, recording a `redaction_count`. The new `model_launch_probe`, `model_substitution`, and `model_chain_exhausted` events all route their `detail` (including any stderr excerpt, already truncated to ≤400/2000 chars) through this redactor.
- The durable journal records carry only model ids, chain entries, reason codes, cycle numbers, session ids, and digests — no raw stderr, no transcripts, no secrets.

### (5) Fable-exhaustion switch not conflatable with a mid-task security downgrade (R606) — HOLDS
- The two triggers share **only** the seam actuator. The security-relevant model-downgrade trigger (`run_result.model_mismatch` → reason `model_downgrade`, recorded as `rotation_pending_flagged`; `loop.py:825-850`) is distinct in trigger, reason code, and record from the quota switch (availability probe → `QUOTA_EXHAUSTED_REASON`, recorded as `model_substitution`). The switch record carries both `reason_code=quota_exhausted` **and** the separate `rotation_reason` (verified by `test_..._distinct_trigger`: durable `reason_code`==quota_exhausted, `rotation_reason`==context_threshold).
- The switch **cannot mask** a downgrade: after a switch, `expected_model` moves to the selected chain entry (`with_model` moves both `model` and `expected_model`), so stream verification still flags any launch that runs on something other than the expected model. The switch only ever selects owner-authorized chain entries; a detected downgrade still rotates to a fresh session on a known-good model. Fail-closed default preserved: any non-quota reason, bare `False`, or `probe_error` → `_pause_model_unavailable` (byte-for-byte the prior pause+notify).

### (6) No new external effects — HOLDS (with LOW note L-3)

## LOW / activation-only observations (NOT acceptance-blocking)
- **L-1 (activation-only, informational-positive):** In production `make_launch_probe` is wired with **no** `classify_unavailable` classifier (`cli.py:2033`), so the default classifier returns `""`; since `"" != quota_exhausted`, the one authorized switch branch **cannot fire in production** until the real live-CLI account-quota signal is captured and a classifier is wired (`QUOTA_EXHAUSTION_SIGNAL_VERIFIED=False`, honestly disclosed by `doctor`/`_check_model_chain_disclosure`). This is maximal fail-closed dormancy — a strength, not a defect. Activation should give the future quota classifier its own security look, since it gates the sole downgrade exception.
- **L-2 (activation-only, standing caveat, re-affirmed):** `config.toml` integrity is manifest-**detected**, not OS-ACL-**enforced**, on single-account Windows. "Owner-editable only" therefore rests on manifest detection + the accepted shadow-only posture; true write-prevention is an activation-time OS-ACL decision, out of scope for this SHADOW-ONLY acceptance.
- **L-3 (LOW, defense-in-depth):** A `[model_chain]` section placed in the RUNTIME `model_selection.toml` is silently **ignored** rather than rejected (`_CONTROLLER_ONLY_KEYS` in `config.py:63-66` does not include `model_chain`/`orchestrator_preference`). It cannot influence the active chain (the loop reads the immutable config only), so this is not an isolation regression; adding those names to the runtime-file rejected-key scan would make the property explicit rather than incidental. Also (minor cost): each launch probe starts an un-budgeted (not counted against `max_model_calls_per_task`) but bounded, job-object-contained, immediately-terminated CLI session — negligible and activation-relevant only.
