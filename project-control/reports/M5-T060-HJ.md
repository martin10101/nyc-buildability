## Findings (all advisory — none blocks acceptance; route to discovery per D-069)

- **HJ-1 (Low, clarity):** The coordinate CRS is named only as "EPSG:2263 feet" (`ProposalEditor.tsx:192`) with no plain-language gloss (e.g. "New York State Plane, Long Island zone; US survey feet") or magnitude hint outside the seeded example values. A licensed architect not steeped in GIS may not recognize the code. Requirement (1) asks whether the 2263 expectation is *explained*; it is *labeled* but not explained.

- **HJ-2 (Medium, accessibility):** Focus is **not managed on row deletion**. The Delete button carrying focus is unmounted by `removeVertex/removeLevel/removeWall` (`ProposalEditor.tsx:222,272,325`) with no nonce/`useEffect` refocus, so a keyboard user who deletes a row is dropped to `document.body`. The add/edit/run/save keyboard flow is genuinely operable and e2e-proven (`proposal-editor.spec.ts:164-215`, real `Tab`+`toBeFocused` before every action; `tabUntil` helper is real keyboard nav) — but the e2e never deletes a row by keyboard, so the gap is untested. CODING_RULES already documents the nonce+`useEffect` remedy for exactly this remount-focus case; it simply isn't applied to deletes. Operable (Tab returns), a WCAG 2.4.3 friction, and explicitly named by review requirement (4) — hence Medium, not a blocker.

- **HJ-3 (Low, recovery/clarity):** Server boundary refusals render honestly but thinly. The 422/413 cards show the message + `Field: {field}` (`ProposalCheckReport.tsx:214-224`) with **no** "adjust the named field and run the check again" next-step, whereas the *client-side* draft-problems section does say "Fix these to match what the checking service will accept" (`ProposalEditor.tsx:350`). Compounding this, `draftIsRunnable` (>=3 vertices; `proposal-draft.ts:196-198`) exists and is unit-tested but is **not** wired to gate the Run-check button — so a degenerate outline makes a doomed round-trip that returns a server-technical field path instead of instant plain guidance. Recovery is still possible (the button stays enabled), so no dead end.

- **HJ-4 (Low, clarity — AS-pinned, not a defect):** The FAIL phrase renders "{shortfall} short" for **maximum** overages too — coverage 0.625 vs a 0.5 maximum shows "0.125 ratio short" (`ProposalCheckReport.tsx:44-48`). You *exceed* the maximum, so "short" reads oddly; "over" would be clearer, and `direction` is available to disambiguate (`CheckResultView.direction`). I flag this only as a human-clarity observation because **AS-1 explicitly pins this exact string** and the server field is `shortfall`; changing it is out of scope for this gate.

- **HJ-5 (Low, clarity):** The PASS note hardcodes "…{required} {unit} allowed" ignoring `direction` (`ProposalCheckReport.tsx:90-94`); for a minimum-direction PASS "allowed" is imprecise ("required" fits). Latent only — the current engine yields no minimum-direction PASS (rear_yard is minimum but always COULD_NOT_CHECK via semantic_gap).

- **HJ-6 (Low, clarity):** The provenance footnote "coverage {coverageStatus}" (`ProposalCheckReport.tsx:115-121`) overloads "coverage" — rule coverage_status shown as "coverage conditional" right next to a check literally titled "lot coverage ratio". Consistent with the accepted surface's vocabulary, so a shared tradeoff, but unglossed here.

- **HJ-7 (Low, recovery):** Failure cards (internal_error / network / timeout / unexpected) omit the captured `X-Correlation-ID` — only the success report shows "Reference:" (`ProposalCheckReport.tsx:209`). The client *captures* the id on failures (`proposal-checks-api.ts:361,392,432`) but a user reporting a 500 has no reference to quote support.

- **HJ-8 (Low, accessibility):** Heading order in the aside is not strictly nested — the report card's h4 group headings (`ProposalCheckReport.tsx:127-130`) appear before the first h3 ("Proposed variations", `ProposalVariations.tsx:61`), and the report region jumps h2→h4. The report is `aria-label`-scoped so it is navigable by region, but the level skip is a WCAG 1.3.1 nit.

- **HJ-9 (Low, clarity):** The compare view shows only per-check outcome + summary counts (`ProposalVariations.tsx:20-38`), **not** the numeric shortfalls, so an analyst comparing two massing options can't see the numeric deltas side by side. AS-4 only requires save/select/compare-two, which works.

- **HJ-10 (Low — concurs with G3-F1 divergence advisory):** After selecting a saved variation, editing the draft, and re-running, the active variation's stored `report` is overwritten but its stored `draft` snapshot is not (`ProposalEditor.tsx:79-81` vs `:84-94`), so a variation's saved geometry and saved report can drift. Human-view impact is contained: compare renders only label + summary + outcome, every value stays labeled "Proposed — not a city record", so nothing false is displayed — but a user could believe a saved variation's report matches its saved geometry when it may reflect later edits.

## Explicit answers to the five review dimensions

1. **CLARITY — Yes, with gloss gaps.** The numeric coordinate table is genuinely usable for a professional: labeled inputs (`aria-label="Vertex N X coordinate"`), a `<caption>` naming the authority, a seeded rectangle that makes the editor immediately meaningful, and levels/walls as plain numeric forms. Gaps: EPSG:2263 is named but not explained (HJ-1); "short" for a maximum overage reads oddly though it is AS-pinned (HJ-4); overloaded "coverage" (HJ-6); compare omits numbers (HJ-9).

Status is icon+text, never color-only (`OUTCOME_META`, icon `aria-hidden`); tables use caption + `scope` headers; report is a labeled region; alerts/`role="status"`/`aria-busy` are correct; the announcer text is honest and distinct from visible text. The gap: focus is not managed on row **deletion** (HJ-2), and heading levels skip (HJ-8).
