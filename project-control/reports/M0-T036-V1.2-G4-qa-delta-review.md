== 4. FINDINGS ==

**F1 (MAJOR, blocking): substitute model never reaches the relaunch launch config; records diverge from actuation.**
Evidence chain, all at the frozen SHA:
- tools/agent_supervisor/cli.py:1966-1970 — `ClaudeRunner(RunnerConfig(..., model=pinned_model, expected_model=expected_model), ...)`: the runner's model is fixed at start to the pinned model, unconditionally (also on resume, where cli.py never consults the durable substitution record that loop.py:607-610 re-derives).
- tools/agent_supervisor/claude_runner.py:176-177 — `build_argv` emits `--model config.model` from that frozen RunnerConfig.
- tools/agent_supervisor/loop.py:1095-1096 — `run_unit(prompt, permission_handler=...)` passes no model; `_current_model` (loop.py:607, 610, 946, 1006) is consumed ONLY by the rotation record ("model": self._current_model, loop.py:908) and a human-readable label (loop.py:919). No code path updates the runner after `_substitute_at_seam`.
Consequence: after a quota substitution, the next unit launches `claude --model <exhausted Fable-5 pin>` while the `model_substitution` audit event, the durable journal record, and the LoopRun rotation record all state the session relaunched explicitly on claude-opus-4-8. In this project's terms that is a provenance divergence — the audit trail asserts a model selection that was never made. Secondary coupled defect: `expected_model` (claude_runner.py:1018: `self.config.expected_model or self.config.model`) also stays pinned, so even a corrected launch on opus-4-8 would flag model_mismatch on every stream event and re-arm rotation_pending(model_downgrade) perpetually; a fix must move BOTH model and expected_model to the substitute for the substitution's duration.
Why the tests missed it: all 7 tests use FakeRunner, which ignores model entirely; every model assertion targets the record side (rotation record, journal, audit), none targets the actuation side (runner config / argv). This is precisely the "first-class events vs. merely-no-exception" question — the answer is "first-class events yes, relaunch config no, and the relaunch config is wrong."
Required regression test for the fix: after a substitution, assert the next `run_unit` invocation's effective model (e.g., a FakeRunner that records the model it was given per call, or a build_argv-level assertion) equals claude-opus-4-8, and that stream verification does not flag a mismatch while the substitution is active; plus the mirrored assertion on return-to-pinned.

== 6. JUDGMENT ON THE RECORDED FINDING ==

**The claimed impossibility is supported.** (a) Mechanism 1 verified in code at the frozen SHA: state_machine.py:248-250 defines the WAIT_FOR_OWNER exits (owner_answer_validated, owner_approved_pending_prompt), but the only firing site is loop.py:1406 (inside a running loop, reachable only via a pre-approved digest); no CLI subcommand fires either exit, and clear-recovery explicitly fires only the PAUSED_RECOVERY exit (cli.py:1491-1510). The F-2 analogy is apt. (b) Mechanism 2 verified in the evidence: I extracted the held prompt_digest from the tier_ask_blocking event of all six declined runs (ex2b 982aecc1…, ex2c 3481ebbb…, ex2d de9aa4fd…, ex3a f6ce35db…, ex3b e7b03960…, ex3c bd62aba1…) — six distinct digests, and the six codex_review_decision output_digests are likewise all distinct. Pre-approval pools cannot converge on a reviewer that rewords next_claude_prompt per run.

**Should a test have caught it?** Mechanism 1: yes. An end-to-end "operator resumes a run parked at WAIT_FOR_OWNER" test would have failed for want of any command to invoke, even with a deterministic fake reviewer — the identical class of gap V1.1's clear-recovery closed for PAUSED_RECOVERY, so the pattern was known. Test-strategy observation: the suite systematically proves fail-closed SAFETY properties but has no liveness/operability tests ("for every held/paused state, an operator command exists that exits it"). Mechanism 2 (digest non-convergence on a live reviewer) is inherently un-catchable by a deterministic harness; live exercising was the correct and only instrument, and the exercises did their job. Recommend a state-machine-level invariant test (every non-terminal hold state has a CLI-reachable exit trigger) alongside the follow-up unit the README proposes.
