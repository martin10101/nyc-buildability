### 2. Findings

#### F1 — DEFECT (blocking): the `field` key of every typed refusal is reflected UNCAPPED, defeating BP-3 on a reachable new surface

`C:\Users\MLFLL\Downloads\nyc-zoning\ctl24\services\api\app\api\v1\proposal_checks_api.py:217-229`

```python
body: dict[str, object] = {
    "state": "validation_error",
    "message": _bounded_message(message),   # capped at 400
    ...
}
if field is not None:
    body["field"] = field                   # NOT capped
```

The packet's binding scope text is *"BP-3 — EVERY error path length-caps embedded values"* (`project-control/tasks/M5-T057.json:13`, item 5). The `message` is capped; the `field` is not — and on the **new lot surface this packet introduces**, `field` carries caller-supplied strings verbatim:

- `services/api/app/rules/proposal_checks.py:457-462` builds `field=f"lot.lot_line_segments[{seg.id!r}].start"` and `field=f"lot.street_lines[{line.wall_id!r}].start"`.
- `proposal_checks_api.py:378-384` and `:399-406` pass those ids straight through (`id=cast(str, seg.get("id"))`, `wall_id=cast(str, line.get("wall_id"))`) with **no length, type, or charset check**. `_enforce_route_caps` (`:415-440`) bounds only the *counts*. The DB-034(b) gate caps only `proposed_massing.*` strings (`app/scenario/proposal_input_gate.py:129-153`) — it never sees `lot`.
- The route then returns `exc.field` uncapped at `:571-578`.

**Reproduction** (read-only, at the reviewed content in `wt-m5t057`, `INTERNAL_RULE_EVAL_ENABLED=1`), POST `/api/v1/proposal-checks` with a valid block and

```json
"lot": {"area_sq_ft": 8000.0, "area_provenance": {"source_id":"s"},
        "lot_line_segments": [{"id": "A"*200000, "start": "not-a-point", "end": [1000000.0,200000.0]}],
        "street_lines": []}
```

Observed:
```
request bytes 200684
status 422
message len 434          <- correctly capped
FIELD len 200031         <- uncapped attacker-controlled reflection
field prefix  lot.lot_line_segments['AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
response bytes 200569
```
Street-line variant (`street_lines[0].wall_id = "B"*150000`, `start:"bad"`): `status 422, field len 150026, msg len 434`.

Why this is a G3 FAIL rather than an observation:
- It falsifies the producer report's closure claim, §2 BP-3: *"every typed refusal routes through `_validation_error` → `_bounded_message`"* and *"EVERY error path length-caps any embedded value"* (`project-control/reports/M5-T057-producer-report.md:74-79`). The `field` key is the exception and the report does not disclose it.
- It is **not inherited** from T053. T053's route accepts only `proposed_massing`, whose every string is gate-capped at `MAX_STRING_LEN=512`; every reachable `field` there is index- or literal-constructed. The uncapped hole is created by the `lot` payload this packet adds.
- The module docstring (`:36-39`) and the packet both designate this route the future **public** trust boundary.

Scope of impact today is limited (internal, `INTERNAL_RULE_EVAL_ENABLED` off by default, ~1:1 byte amplification, no memory blowup) — this is a contract/precondition defect, not an availability exploit.

**In-scope fix** (single file, no seam edits): cap `field` in `_validation_error` (e.g. `body["field"] = _bounded_message(field)` or a tighter dedicated field cap), and/or add BP-2-style bounded-string validation for `lot.lot_line_segments[].id` / `lot.street_lines[].wall_id` in `_build_lot_context`. Add the binding test (see F2).

#### F2 — Required correction (weak tests): nothing binds `field` bounding, and no 500 path of the new route is exercised

- The BP-3 tests assert only the **message** (`tests/api/test_proposal_checks_api.py:275-307`); `grep "len(body\[.field"` over `tests/api/` returns **zero** hits. A test asserting `len(body["field"]) < 500` for the F1 payload is the mutation-proof for the fix.
- `PROPOSAL_CHECKS_STATUS_STATE_MATRIX` declares `(500, "internal_error")` (`proposal_checks_api.py:145`) and the route has three 500 emitters (`:549-551` registry unavailable, `:579-582` unexpected, `:588-592` serialization). **None is exercised.** `test_status_state_matrix_is_the_documented_set` (`:504-513`) compares the constant to a hand-written copy of itself — tautological; it binds no emission. T053's residual (b) (`test_proposal_validation_api.py:658`) proves the *sibling* route's 500 only. Recommend one forced-500 test on the new route (monkeypatch `mod.get_proposal_check_registry` to raise → assert `set(body) == {"state","message","correlation_id"}`, no leak).

#### F3 — Observation: `unmapped_lot_facts` reflects unbounded, arbitrary-charset caller keys in the 200 body

Reproduced: a `lot_rule_facts` key `"<script>" + "C"*100000` returns `200` with `unmapped_lot_facts[0]` length 100008, verbatim. Surfacing unmapped keys is the packet's explicit BP-5 requirement and the engine (`app/rules/proposal_checks.py:536-541`) owns the list, so this is not a contract violation — but it is inconsistent with BP-2's own rationale (label/id are capped at 200 + charset precisely *because* they are "copied into every result and rendered by B3"; unmapped keys are rendered by B3 too). A count/length cap at the route boundary would close it without changing the accepted engine. Flagging for the security reviewer's surface and as a B3-slice-2 discovery.

#### F4 — Observation: the 400-cap "exactness" test binds a 99-char window, not the cap value

`tests/api/test_proposal_validation_api.py:655` asserts `400 < len(message) < 500`. Changing `_MAX_REFUSAL_MESSAGE_CHARS` from 400 to 450 still passes. AS-6 words this residual as "truncated to the **exact** cap". Suggested tightening: assert `message.endswith(f"...<truncated; {true_len} chars total>")` and `len(message) == 400 + len(marker)`.

#### F5..F7 — Observations (non-blocking, maintainability)

- `_derive_enum_domains` (`proposal_checks_api.py:296-315`) is recomputed on **every** request over the whole registry (rules × inputs); `_PRODUCTION_REGISTRY` (`:185-200`) is a module global never invalidated. Bounded and mirrored on the engine's own `_default_registry` (`app/rules/proposal_checks.py:729-733`), but a per-registry memo would be cheap.
- `_assert_fact_type_table_covers_vocabulary()` runs at **import** (`:161`) and `main.py:36` imports the module unconditionally, so a `CALLER_RULE_INPUT_NAMES` drift fails the **whole app** at boot, not just the flag-gated route. Fail-closed and CI-caught, but the blast radius exceeds the flag; worth an explicit note in the module docstring.
- Three private names are imported across modules (`_bounded_message`, `_declared_content_length`, `_read_body_within_ceiling`, `:61-66`). Reuse was correct here (the packet froze `proposal_validation.py`), but promoting them to a shared `app/api/v1/_request_bounds.py` should be queued for whichever route goes public first — discovery, not in-packet.
