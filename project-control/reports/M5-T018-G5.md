## Threat-by-threat findings

### Threat 1 — Validator is the web trust boundary (bypass / closed-key smuggling): PASS
- `checkUnusedFloorArea` is called UNCONDITIONALLY on every validation path — `validateScenarioDocument` line 781 invokes it for all `scenario_kind` branches; not gated on state.
- Missing section fails: it is in `SCENARIO_KEYS` (line 219) and `checkUnusedFloorArea` rejects a non-object (`scenario-contract.ts:591-594`). Test `unused-floor-area.test.tsx:60-66` reproduces.
- Validation problem blocks render: `fetchScenario` returns a distinct `validation_failure` outcome carrying only a bounded problem list, never a document (`scenario-api.ts:331-340`); `CompareScreen.tsx:138-140` mounts `ScenarioResult` (and thus this component) ONLY when `outcome.kind === "scenario"`. Trust boundary holds end-to-end.
- Closed-key discipline INSIDE the section: `checkNoUnknownKeys` at the section, `inputs`, `inputs.draft_zoning_floor_area_cap`, `inputs.existing_building_floor_area`, and each `assumptions[]` element. Reproduced via schema extraction (`packages/contracts/schemas/v1/scenario.schema.json`): key sets `UNUSED_FLOOR_AREA_KEYS` (11), `_INPUTS_KEYS` (2), `_CAP_INPUT_KEYS` (3), `_EXISTING_INPUT_KEYS` (5) match the schema `required`/`additionalProperties:false` EXACTLY. Enums (`state`, `not_computable_reason`) match. Per-field types match; where the validator diverges it is strictly STRICTER (finite-number check, token-representability) and always fails CLOSED — an attacker cannot smuggle an undocumented key or value past the mirror into render. Negatives reproduced in tests: unknown inner key, unknown nested-inputs key, out-of-enum state/reason, NaN value.

### Threat 2 — Free-text rendering (label/scope_note/over_built_statement): PASS
- No `dangerouslySetInnerHTML` anywhere in the new component (grep over `apps/web/src`: the only 2 hits are a comment in `bounded.ts` and an assertion-of-absence in an out-of-scope address test — neither is a usage).
- `boundedText` applied to EVERY rendered free-text field: `label` (`:83`), `scope_note` (`:84`), `over_built_statement` (`:154-157`). `boundedText` caps length at 600 with an explicit truncation marker and strips C0/C1/DEL control chars (`bounded.ts:35-51`). Fields NOT rendered (`formula`, `unit`, `inputs.*`, `assumptions`) never reach the DOM in this consumer.
- No string reaches an attribute/URL/style sink: grep for `href/src/style/window/location/fetch/localStorage/cookie` in the component → NO matches. Free text reaches only JSX text children (React auto-escapes). `data-state={section.state}` is enum-validated and React-escaped.
- Typed reason surfaced via a FIXED mapping (`NOT_COMPUTABLE_PLAIN_LANGUAGE`, keyed by the 3 validated enum values, null→fixed fallback) — arbitrary reason strings are never echoed.

### Threat 3 — Numbers (formatter, precision/layout abuse): PASS (advisory A2)
- Value renders via `formatValue` → `value.toLocaleString("en-US",{maximumFractionDigits:20})` (`format.ts:9-16`) — identical to the existing cap rendering (same formatter used by `ScenarioResult`/`ScenarioCard`). `Intl.NumberFormat` expands large magnitudes to full grouped digits; it does NOT emit scientific notation, so a `1e21`-style value cannot render as `"1e+21"`.
- NaN/Infinity are rejected upstream by the validator (`checkNullableFiniteNumber`, `scenario-contract.ts:502-510`), so `formatValue` never renders `"NaN"`/`"Infinity"` beside a legal figure. Test at `unused-floor-area.test.tsx:113-122`.
- Numbers are deliberately never length-bounded (a material legal value is never transformed — `scenario-bounds.ts:36-38`), consistent with the whole app; this is an intentional honesty decision, not a new hazard. See advisory A2.

### Threat 4 — Honesty-as-security (no clamp/hide/fabricate): PASS
- Negative is never clamped/hidden/restyled: `ComputedLine` renders `formatValue(value)` directly (no `Math.abs`, no `Math.max(0,…)`); tests assert the DOM shows `"-5,000"` and explicitly NOT `"5,000"`/`"0"` (`:186-190`).
- `not_computable` never fabricates a number or zero: `NotComputableLine` emits "No supported estimate" and a plain-language reason with NO value node; test asserts `queryByTestId("...-value")` is null (`:231`). The validator permits `value: null` on any state (schema anyOf number/null), so nothing forces a coerced zero.

### Threat 5 — No new deps/network/storage/eval; scenario-bounds spread: PASS (advisory A1)
- No new dependencies (package files untouched, verified). No network/storage/eval sinks in the new files (grep clean). Imports are all existing internal modules.
- `boundScenarioDocument` spreads `...document` and does NOT centrally bound the `unused_draft_zoning_floor_area` section (`scenario-bounds.ts:153-155`). Assessment: the ONLY current consumer (`UnusedFloorAreaSection`) bounds the 3 rendered free-text fields at render, and does not render the other section strings, so there is NO current unbounded-text DOM exposure. The section's `assumptions` array is still validator-bounded to 64 entries (`checkAssumptions`→`checkBoundedArray`). Latent risk only — see advisory A1.

### Threat 6 — Validator DoS posture / input-size ordering: PASS
- Order confirmed in `scenario-api.ts`: Content-Length guard (fails CLOSED on absent/blank/non-numeric/over-budget, `:285-297`) runs BEFORE `response.json()` (`:301`) which runs BEFORE `validateScenarioDocument(body)` (`:331`). The new validation code therefore only ever runs on an already-parsed body bounded to `MAX_RESPONSE_BYTES` (256 KiB).
- The validator traverses a fixed schema depth (no unbounded recursion) and every array (including the section's `assumptions`) is capped at `MAX_DOCUMENT_ARRAY_LENGTH` = 64, rejected (not truncated) beyond. The problem list itself is bounded at 20 (`Problems`). No deep-nesting or huge-document amplification.

## Advisories (non-blocking, for a future task — do not reopen this accepted work)

- **A1 (LOW, latent, defense-in-depth):** `boundScenarioDocument` centrally bounds every root-level free-text field but passes the `unused_draft_zoning_floor_area` section through unbounded via the `{...document}` spread. Current exposure is nil because the sole consumer bounds at render and the input is already ≤256 KiB. However, this creates an asymmetry: a FUTURE consumer that renders `formula`, `unit`, the `inputs.*` provenance/coverage strings, or `assumptions[].rationale` without its own `boundedText` would surface unbounded server text into the DOM/accessibility tree. Recommend a follow-up (touching the out-of-scope `scenario-bounds.ts`) to bound the section centrally, restoring the module's "bounded before it leaves the module" guarantee. Producer disclosed this explicitly.
- **A2 (INFO):** The C1 value (like the existing cap) is rendered by `formatValue` with no magnitude cap — a maliciously huge server-supplied number would render as a very long grouped digit string (layout stretch, no injection, no scientific-notation leak). This is the app-wide deliberate "never transform a material number" policy and is consistent with existing cap rendering; flagged only for awareness.
