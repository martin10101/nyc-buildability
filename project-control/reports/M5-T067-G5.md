## Findings

**G5-LOW-1 (NEW; same class as the just-fixed LOW-2, in a path T067 touched but left out of its remit): `supersede` retains a message-text existence oracle.**
T067 unified *revoke*'s two not-found messages but left *supersede*'s not-found branches with divergent text: a **missing** `old_id` returns 404 "no site-definition confirmation exists for record id `<old_id>`" (`store.py:310-312`, and it **echoes the id**), while an **existing-but-foreign** record returns 404 "a superseding confirmation must belong to the same condo key as the record it supersedes" (`store.py:329-333`). Given a known (unguessable, 128-bit uuid4) record id, a cross-property caller who addresses their own property and sets `supersedes_id == old_id` reaches the condo-mismatch branch on an existing foreign record but the missing-record branch on a non-existent id — so the **message wording (and the id echo) distinguishes existence**, the exact LOW-2 oracle class, unclosed for supersede. (A deliberately mismatched `supersedes_id`, `store.py:313-318`, is a third divergent message that likewise only fires when the record exists.) This is a status-safe, **read-only existence** leak — LOW-1's status oracle is closed, so it discloses nothing about the foreign record's status, and no cross-property mutation is possible (the scope check 404s before any insert).

*Reproduction:* `s = InMemorySiteDefinitionStore()`; `r = s.create(_make()).record` (condo "A"). Probe missing → `s.supersede("nonexistent", _make(supersedes_id="nonexistent", condo_key="B", reason="x"))` raises "no site-definition confirmation exists for record id 'nonexistent'". Probe foreign-existing → `s.supersede(r.record_id, _make(supersedes_id=r.record_id, condo_key="B", reason="x"))` raises "a superseding confirmation must belong to the same condo key…". The two messages differ ⇒ existence distinguishable; contrast the now-unified revoke pair.
