## VERDICT: **PASS** — with 4 blocking corrections (C1–C4) required before acceptance

The central promise holds. I traced the subscription key from `os.environ` to the wire and found **no open leak surface**: the key exists in exactly one dict (`headers`), that dict is passed to exactly one callable (the transport), and no log line, exception detail, provenance field, response object, or redirect path in this connector or the shared engine ever touches it. ## FINDINGS

**1. [MEDIUM — BLOCKING C1] `_safe_text` passes a trailing newline through verbatim; a hostile response can split a log record.**
`services/api/app/connectors/geoclient_address.py:127` uses `re.compile(r"^[...]{1,300}$")` with `re.match`. Python's `$` matches *at end of string **or just before a trailing newline***, so a value of safe charset ending in one `\n` is returned unchanged rather than `repr()`-escaped. I verified this empirically: `_safe_text("00 status=resolved bbl=1234567890\n")` returns the string **including the newline**.

The reachable path is `geoclient_address.py:565-571`, where `_safe_text(grc)` / `_safe_text(grc2)` interpolate response-body values into `logger.info(... grc=%s grc2=%s)` on **every** parsed response. Exploit: an upstream able to influence `geosupportReturnCode` (a compromised or MITM'd `api.nyc.gov`, or a future caching/proxy layer) sets it to `"00 grc2=00 status=resolved bbl=1000000000\n"`. The emitted record reads as a clean successful resolution and the real remainder of the format string is orphaned onto a second line. In a provenance-and-audit-driven system, forging a "resolved" log entry for an address the source actually rejected is exactly the wrong failure. Fix: `re.fullmatch` (or append `\Z`). **The same `$`-anchor quirk exists in all three sibling connectors** (`mappluto_geometry_arcgis.py:314`, `zoning_features_arcgis.py:266`, `ztldb_soda.py:345`) — pre-existing and out of this packet's scope, but the orchestrator should open a follow-up so the fix lands wave-wide.

**2. [MEDIUM — BLOCKING C2] `_safe_text`'s `repr()` fallback is unbounded, so the sanitizer amplifies instead of bounding.**
`geoclient_address.py:130-133`: values failing the 300-char pattern return `repr(value)` — the *entire* value, merely quoted. `repr()` does escape control characters (so this is not a second injection route), but it applies no length cap. A response with a 9 MB `geosupportReturnCode` string is admitted by the transport (`MAX_RESPONSE_BYTES` is 10 MB) and lands as a 9 MB argument to `logger.info` at `geoclient_address.py:569-570` — built eagerly, since `_safe_text(grc)` is an argument expression, not lazy `%s` formatting. One hostile 200 response inflates one log record by ~10 MB. Fix: truncate in both branches, e.g. `repr(value)[:300]`.

**3. [MEDIUM — BLOCKING C3] `MalformedResponseError.detail["top_level_keys"]` is an unbounded, attacker-chosen list.**
`geoclient_address.py:512-521` builds `sorted(map(_safe_text, parsed.keys()))` with no cap on key *count* and (per C2) no cap on key *length*. A 10 MB JSON object of short keys yields hundreds of thousands of entries inside an exception whose `to_payload()` (`:152-160`) is designed to be serialized into an API error response and logged. The body cap bounds it at 10 MB, which is not a bound worth having in an error payload. Fix: cap to the first N sorted keys (20 is plenty for drift diagnosis) plus a `"truncated": true` marker, and cap each key's length.

**4. [MEDIUM — BLOCKING C4] No length bound on caller input; the resulting URL is embedded in every retry log line and every error detail.**
`geoclient_address.py:453-489` strips and presence-checks `house_number` / `street` / `borough` / `zip_code` but never bounds their length. The URL built at `:489` is then logged verbatim on each retry attempt (`app/resilience/transport.py:459-462, 469-472, 485-488, 492-496`) and embedded in `detail["url"]` of every terminal error (`transport.py:507`, and `geoclient_address.py:375, 381, 509, 517`), which `to_payload()` returns to the caller. A megabyte-scale `street` becomes a megabyte-scale URL repeated across three attempt logs plus the error payload, and burns real upstream calls against a quota the registry records as officially UNKNOWN. This is not a key leak — `urlencode` keeps the URL structurally safe (see the leak table) — it is amplification. Because this packet ships no API endpoint, there is currently no other layer enforcing a bound; fail closed here with `InvalidInputError` at sane caps (Geosupport house numbers and street names are short).

**5. [LOW — non-blocking, but state it in the contract] The outcome object is untrusted content, and the source reflects caller input into it.**
Fixture G02 proves the reflection: `"message":"'W 100 SREET' NOT RECOGNIZED. IS IT 'WEST  100 STREET'?"` and `"streetName1In":"W 100 SREET"` echo the user's typed street back. Those land verbatim on `grc_message` / `grc2_message` (`geoclient_address.py:544-548`), in `suggestions[].street_name` (`:315-337`), and wholesale in `raw_fields` (`:550`). Transporting them verbatim is the *correct* call for this connector and matches the packet's transport-honesty requirement — but it means every consumer packet inherits an escaping obligation. Neither the module docstring nor `docs/research/source-registry-drafts/geoclient.json` says so. Add one line to both: these fields are unsanitized source text containing reflected user input; escape on render, never log verbatim.

**6. [LOW] Two test-coverage gaps and one inert assertion.**
`test_geoclient_address.py:320` sets `caplog.set_level(logging.DEBUG, logger="app.resilience.transport")`, but `transport.py` defines no module logger — every transport warning is emitted on the *connector's* logger via `hooks.logger`. The records are still captured (so the leak sweep is valid), but the producer report's claim that "connector and transport loggers both captured at DEBUG" overstates what was verified. Separately: no test drives a **3xx** through this connector (redirect refusal is covered only for the PLUTO path, `tests/api/test_properties_v1.py:683-717`), and the leak-absence sweep at `:332-341` exercises 401/timeout/malformed but omits 403, 429 and 500. I verified the redirect path by construction instead (see table); adding a 3xx case here would make it self-evident.

**7. [LOW — for G1/G3, not a security defect] Absent second sub-call code is classified `unrecognized_status`.**
`_classify` (`:295-312`) requires **two** shape-valid codes; one present and one absent yields `unrecognized_status`. Given the documented null-omission behavior this could misreport a legitimate single-sub-call response. Fail-closed is the right direction from my lens, so I am not blocking on it — but the semantics deserve a G1/G3 opinion.

**8. [INFORMATIONAL] The transport seam hands the cleartext key to whatever callable is injected.**
`geoclient_address.py:492-501` passes `headers` (containing the key) to the caller-supplied `transport`. That is what makes offline testing possible and is correct, but any future instrumenting, caching, or retrying transport wrapper becomes a new leak surface. One sentence in the seam docstring (`:216-220`) would carry that forward.

## WHAT I VERIFIED

- **Read in full:** the connector (572 lines), the shared transport engine (513 lines), the test module (442 lines), all three fixtures, the registry draft, the producer report, the task packet, and `.github/scripts/secret_scan.py`.
- **Ran the opener live (read-only, no network):** instantiated `DEFAULT_OPENER`, enumerated its handler chain, confirmed `NoRedirectHandler` is present and the stock `HTTPRedirectHandler` is absent, confirmed `redirect_request(...)` returns `None`, and confirmed `geoclient_address._OPENER is DEFAULT_OPENER` — i.e. the redirect refusal is genuinely on this connector's path, not merely on a sibling's.
- **Recomputed all three fixture sha256 digests** from `response_body_raw` against the stored `response_sha256`: all three match (independent of the test that asserts it).
- **Grepped the six new/changed files** for 28+ character alphanumeric runs and for bare 32-hex runs: only sha256 digests and Geoclient camelCase field names. Ran the scanner's `inventory-secret-name-assignment` regex against `services/api`, `docs`, and `project-control`: no hit in any new file.
- **Probed `_safe_text`** with eight adversarial inputs, isolating the `$`-anchor trailing-newline passthrough and the unbounded `repr()` fallback.
- **Probed `urlencode`** with CRLF, `&`, `#`, `?`, and `../` payloads to confirm URL-construction containment.
- **Probed the suggestion-count clamp** with nine hostile values including a 5000-digit string.
- **Searched `services/api/app/` for locals-capturing error reporters and TLS weakening**: none found.
- **Did not** run the test suite, edit any file, write the ledger, or make any network request (ADR-005 read-only discipline observed throughout).

**Recommended recording:** PASS, with C1–C4 recorded as blocking corrections for the next gate and for acceptance per the gate-verdict semantics in `.claude/rules/project-control.md`. C1 and C2 are single-line fixes; C3 and C4 are small and local. The wave-wide `$`-anchor variant of C1 in the three sibling connectors should be tracked as a separate follow-up rather than folded into this packet's scope.
