F2 (Medium; ADVISORY; §0 lines 26-27; §9 line 279). base_z=GROUND_ELEVATION (absolute NAVD88) is arithmetically sound (roof_z = ground + HEIGHT_ROOF; HEIGHT_ROOF is above-ground/datum-independent - all confirmed), but it is NOT reconciled with the M5-T082 massing model, which pins parcel + proposed building to a RELATIVE z=0 frame (massing_model.py: parcel elevation_ft=0.0; floor stack z starts 0). Placing existing neighbours at absolute NAVD88 base_z beside a z=0 proposed building floats them ~ground-elevation feet up. The connector needs ONE shared ground datum (e.g. relative_base_z = building_ground_elev - site_ground_elev) or the massing frame lifted to site ground. The note should say this; it currently reads as directly consumable.

F3 (Low-Med; ADVISORY; §2 line 61; §3 line 99). SODA the_geom is MultiPolygon (confirmed live) and courtyards can appear as holes, but the M5-T082 prism builder takes a SINGLE ring and REFUSES holes (_lot_polygon -> lot_has_holes; _prepare_ring single ring). The note quotes "single outer ring" but gives no connector policy for multipart/holed footprints mapping onto the massing model. Surface for the connector packet.
