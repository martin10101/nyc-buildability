## Security posture assessment (in-scope, PASS)

**Auth / exposure (given the flag gate).** The write route needs BOTH flags to serve, with defense in depth: registration is gated on the dedicated default-off `SITE_DEFINITION_WRITE_ENABLED` (`main.py:217-218` — `include_router` only when true), and each handler is gated on `internal_rule_eval_enabled()` returning the generic sentinel otherwise (`site_definition.py:499-500, 551-552, 591-592, 660-661`). Production sets neither, so the route is absent from the routing table entirely. `site_definition_write_enabled` (`site_definition.py:121-135`) is fail-safe — only explicit true tokens flip it on; absent/empty/unknown → False. The DB-040(f) read-authorization is deferred behind the flag by design (documented `main.py:203-216`); mounting default-ON is explicitly prevented. This matches the packet's declared scope; the G3 F1/F2 auth LOWs are correctly deferred.

**Fail-closed behavior.** The single emission point `_json` (`site_definition.py:214-250`) asserts every `(status, state)` against `SITE_DEFINITION_STATUS_STATE_MATRIX` and fails closed to `(500, internal_error)` on an off-matrix pair, non-recursively. An unmapped `SiteDefinitionError` fails closed to 422, never a 500 that would hide a typed cause (`site_definition.py:305`). Store guards (id collision `store.py:227-232`, chain-depth cap `store.py:237-246`) raise before any mutation, so a refused insert leaves records/transitions/indexes byte-unchanged.

**Cross-property isolation (withdrawal path).** Revoke evaluates scope before status (`store.py:390-418`): a foreign-property/foreign-condo probe is an indistinguishable `(404, not_found)` whatever the record's status, closing the DB-040(a) status oracle; the 409 is reachable only on the record's own binding. Degraded-resolver revoke (`site_definition.py:451-486`, `store.py:351-372`) never unscopes — a `None` condo_key falls back to the record's own `billing_bbl`/`entered_bbl`, so a foreign probe still 404s while the legitimate human withdrawal still succeeds (D-051 fail-direction). No cross-property mutation is possible on any path.

**Input validation / injection.** BBL normalized to a typed 422 before any resolver call (`site_definition.py:383-393`); body guarded by a declared-Content-Length 413 plus load-bearing streaming accumulation that catches an under-reporting/chunked body (`site_definition.py:332-380`); strict JSON-object parse; `parcels` shape-validated with its own `ParcelShapeError` class (never mislabeled invalid_confirmer); confirmer role constrained to a closed human vocabulary (no AI/agent/service principal representable); `note`<=2000 and confirmer.name<=200 caps. Store is an in-memory dict — no SQL/shell/eval/template sink. No SSRF (only a normalized numeric BBL flows to the accepted read-only condo resolver), no file upload, no AI/prompt surface.

## Findings

**LOW-1 (out-of-declared-scope, same class as the in-scope revoke fix): supersede retains a cross-property status oracle.**
`supersede` (`store.py:312-337`) calls `_require_active(old_id)` (`store.py:204-216`) — existence then ACTIVE status (409) — *before* the condo_key binding check (`store.py:328-332`). So a cross-property probe of a known foreign record leaks its status: a foreign non-active record returns 409 (`ConfirmationNotActiveError`) while a foreign active record returns 404 (condo_key mismatch) — the exact status-before-scope oracle that DB-040(a) closed for revoke. No cross-property *mutation* is possible (the binding still 404s an active foreign record before any insert), so this is a status-read leak only. Mitigants: record_ids are 128-bit `uuid4` (unguessable), the route is default-off/unmounted in production, and reaching the store requires a healthy multi-lot resolution + matching parcels for the addressed foreign property. Because the packet's scope item (a) named *revoke* specifically, this is a LOW residual, not an in-scope FAIL. Remediation: for consistency, reorder supersede to bind scope before the ACTIVE-status check (mirror revoke) in the follow-up auth/hardening packet.

**LOW-2 (informational): revoke not-found message text distinguishes existence.**
Both revoke not-found branches map to identical `(404, "not_found", confirmation_not_found)`, but the free-text `message` differs: a non-existent id echoes "no site-definition confirmation exists for record id ..." (`store.py:395-398`) while an existing-but-foreign id returns the static "must belong to the property addressed ..." (`store.py:407-410`). Given a known (unguessable) record_id, a cross-property probe can therefore distinguish exist-vs-not from the message wording alone. The in-scope requirement (identical status/state, no 409-vs-404 status oracle) is fully met; this is a residual existence oracle via message text, requiring an already-known 128-bit id, on a default-off route. Remediation: emit an identical message for both not-found branches; route with LOW-1.

**Deferred by design (G3 F1/F2, acknowledged):** endpoint auth / public-exposure posture (DB-040(f)) is deferred behind the default-off flag pending B-001; correctly out of this slice's scope.

No critical, high, or medium findings. The two LOW items are consistent with the packet's stated deferrals and do not block acceptance.
