## 2. Findings by severity

### BLOCKING-1 — `FORBIDDEN_FACT_KEYS` is enforced only at the TOP level, so a caller can place a fact-shaped object (canonical cap key + `coverage_status: "verified"` + a fake `rule_evaluation`) into a 200 response body

**Location:** `services/api/app/api/v1/scenario_analysis.py:348-357` (`_prepare_request` step 5: `injected = sorted(FORBIDDEN_FACT_KEYS & set(body.keys()))`) — the check tests only `body.keys()`. The iterative walk at `:263-295` already visits every nested key but tests only string length.

**Failure scenario (reproduced, offline, through the producer's own fixture harness):**

```
POST /api/v1/properties/1000010100/scenario/ranking
{"objective": "maximize_illustrative_usable_area",
 "assumption_sets": [[{"assumption_type": "utilization_factor", "value": 0.8,
                       "draft_zoning_floor_area_cap_sq_ft": 987654321,
                       "coverage_status": "verified", "verified": true,
                       "rule_evaluation": {"outputs": {"max_residential_floor_area_sq_ft": 987654321}}}]]}
```

Actual response: **200**, and the body contains, verbatim:

```
$.result.candidates[0].assumption_set[0] =
  {"assumption_type": "utilization_factor", "value": 0.8,
   "draft_zoning_floor_area_cap_sq_ft": 987654321, "coverage_status": "verified",
   "verified": true, "rule_evaluation": {"outputs": {"max_residential_floor_area_sq_ft": 987654321}}}
```

The **producer's own AS-6 invariant fails on this body.** Using the test file's own helper (`test_scenario_analysis_api._coverage_values`, which scans every nested `coverage_status`), against this response:

```
1) status 200 | producer AS-6 helper _coverage_values -> ['conditional', 'verified']
   assert 'verified' not in _coverage_values(envelope) WOULD: FAIL
```

The exact assertion on line 681 (`test_as6_response_is_strict_json_safe_and_never_verified`) and line 340 (`test_as1_endpoint_returns_engine_result_envelope`) would fail — the tests pass today only because no test sends a fact key nested one level down. The same keys are rejected with a typed 422 when sent at the top level (`test_as2_fact_injecting_body_is_typed_422` covers 11 of them), so the module's stated boundary is real but applied at the wrong scope.

**What is and is not compromised** (stated precisely so this is not over-read): the **authoritative** cap is safe. `envelope["scenario_cap_sq_ft"]` stayed `15000.0` (the server-rebuilt trace value) on every probe, and I confirmed by reading the engines that each one merges caller data only as `{**scenario_document, "assumptions": <caller data>}` (`sensitivity.py:326`, `ranking.py:314`, `comparison.py:316`), so `draft_zoning_floor_area_cap_sq_ft` in the document itself can never be overwritten and `derived.canonical_cap_sq_ft` is always the server value. What *is* compromised is the packet's explicit AS-2 requirement and AS-6's never-Verified guarantee: a body that "supplies or attempts to override a fact — a property_profile, a rule_evaluation, a scenario document, a max_residential_floor_area_sq_ft / cap value, or a coverage / verification / Verified status — is REJECTED with a typed 422 ... and is NEVER merged into the server-rebuilt document." This body is not rejected; it is merged into a copy of the server-rebuilt document as `assumptions` and echoed. In a legally sensitive product, a 200 response that carries an attacker-chosen number under the **exact canonical cap key name** alongside `"coverage_status": "verified"` is precisely the forged-fact surface this task was shaped to prevent — any consumer (including the parked Compare UI M5-T004) that greps the response for `draft_zoning_floor_area_cap_sq_ft`, for `max_residential_floor_area_sq_ft`, or for a verified coverage status finds the forgery.

**Exact minimal fix I would require (NOT applied):** in `_structural_error` (`:263-295`), which already walks every node iteratively, test each dict key against `FORBIDDEN_FACT_KEYS` at every depth and return the same typed 422 with the same `detail.rejected_keys` — i.e. inside the existing `for key, value in node.items():` loop at `:285`, before the length check, reject when `key in FORBIDDEN_FACT_KEYS`. Then keep (redundantly) or retire the top-level check, update the docstrings that say "top-level" (`:135-139`, `:348`), and add two tests: the nested body above must be a 422, and `"verified" not in _coverage_values(envelope)` must hold for it. Entirely inside `allowed_paths`; no engine or forbidden-path change is needed. (Note for whoever fixes it: the key `verified` would then also reject a legitimately-named caller field of that name — that is the intended trade, and it matches the top-level behaviour already shipped.)

### MEDIUM-2 — `MAX_BODY_BYTES` is enforced only after the entire body has been buffered; no `Content-Length` pre-check and no body-size middleware

**Location:** `scenario_analysis.py:321-323` — `raw = await request.body()` reads the whole stream, then `if len(raw) > MAX_BODY_BYTES`. I read `main.py` in full: the only middleware is CORS plus the security-header stamp, so nothing upstream bounds the body.

**Reproduced:** an 8 MiB body returns the correct 422 in 0.02 s — but all 8,388,650 bytes were accepted into memory first. At an edge with no authentication (documented in `main.py:6-11`), the documented 64 KiB cap does not bound what a caller can make the process allocate. The producer report's table claim "checked on raw bytes BEFORE parsing" is accurate; "before *buffering*" is what would be needed. Fix: reject on the `content-length` header before awaiting the body, and/or read `request.stream()` against a running byte budget.
