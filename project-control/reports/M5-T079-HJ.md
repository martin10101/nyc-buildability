M5-T078 human-journey review, part 2 of 6: the one BLOCKING finding (HJ-1).

HJ-1 (BLOCKING). Pressing Convert while it cannot convert now rewrites the text of the last refusal card. This packet introduced it. It misleads the user and announces twice.

CAUSE
- The refusal card's body is the shared announcer state. ProposalOutlineDraw.tsx:419-420 renders `<strong>Outline not converted</strong><p>{announcement}</p>`, inside a role="alert" section (:382).
- The new blocked-press path writes into that same state: onConvertActivate (:231-237) calls setAnnouncement(convertBlockedReason) at :233.
- `outcome` only changes in convert() (:221), so the old card stays on screen with the new text.

JOURNEY (reachable in production)
1. Draw 3 points and press Convert. The card reads: "Outline not converted / Map-drawing conversion is not available in this environment. Enter coordinates in the table instead."
2. Delete one point and press Convert again. It still looks enabled (see HJ-2).
3. The card now reads: "Outline not converted / Add 1 more point to convert — an outline needs at least 3 points (you have 2)."

The "not available" statement is gone, and the card now implies one more point will make conversion work. The user adds a point, converts, and gets the not-available card again: a futile loop.

SAME OVERWRITE ELSEWHERE
- A double-click during any retry after a refusal gives "Outline not converted / Conversion is already in progress."
- Once the bridge is mounted, residual_too_high, out_of_neighborhood and every other refusal lose their explanation the same way. The card keeps its old data-outcome-kind but shows a client hint as the cause.

ACCESSIBILITY
- The role=alert card changes content, so screen readers loudly re-read "Outline not converted. Add 1 more point…".
- The polite announcer (:241) then says the same reason again.
- That is a duplicate, and an alarm for a press that sent no request.

This breaks the packet's binding MEANING PRESERVATION rule ("no existing disclosure … deleted or weakened"). It also breaks AS-4's wording: "announce the reason through the existing status region". No spec covers a refusal followed by a blocked press; proposal-outline-draw.test.tsx:414 starts with no outcome on screen.

REMEDY (inside allowed_paths: about one line plus one spec)
- Build the card's text from the outcome itself: announcementForOutlineBridge(outcome), or a state that only convert() sets.
- Keep the blocked reason in the announcer only.
- New spec: stub a refusal, delete a point, press Convert, then assert the card text is unchanged, no fetch was made, and the announcer holds the reason.

M5-T078 human-journey review, part 3 of 6: advisories HJ-2 to HJ-4.

HJ-3 (MEDIUM; screen-reader-only contradictions in the one status region, ProposalOutlineMap.tsx:201-207).
- (a) The suffix "The lot map is ready to draw on — click it to place points." (:206) is added to EVERY status update while the map is showing.

  - But a click then MOVES point 1 (handleMapClick :167-170). The visible copy (:178) correctly says "move it".
- (b) The new clause "it has no coordinates yet, so a map click will place it" (:204) ignores whether a map exists.
  - On condo and other fallback lots, and while the map is loading, it tells screen-reader users to click a map that is not there.
  - This is the T071 B1 class returning in the screen-reader-only channel.
- (c) role=status reads the whole region each time, so "ready" is repeated after every place and every select.
  - The min-hint (ProposalOutlineDraw.tsx:372) often changes on the same click, and the map's own summary region also speaks, so announcements stack up.

HJ-4 (LOW-MED; awkward copy, ProposalOutlineDraw.tsx:199-203). For one half-typed row the rendered text is: "Convert will include 3 points. 1 row without a latitude is not filled in and will not be included — fill it in or delete it to include it."
