### MINOR
- **MINOR-1 — the `--` option-injection hardening for `/loop-codex` is present and correct but untested/unmutated for this path.** `loop_command_interceptor.py:138` appends `["--", rest]` so a message/question starting with `-` or containing metacharacters/quotes/Unicode/newlines is one data argv element. I verified this works (probe: `new -rf; rm -rf / $(whoami) … line1\nline2` and `continue cxt_abc --sandbox danger message` both ride behind `--` as a single element). But **no K-pack test reaches that line** — every K2 hook test uses `NO_PROVIDER_ENV`, which blocks in the `if not (exe and cfg and sel)` branch before the argv is built, and `show/promote/close` don't add `--`. The report §1 explicitly features this as the "unit-G G5 ADVISORY-2 hardening," yet a behavior-neutral mutation to `tail += [rest]` would survive the K-pack. Actual security impact is low (shell=False; `build_argv` hardcodes `--sandbox read-only` and `assert_argv_safe` rejects forbidden flags; worst case without `--` is an argparse error, not a sandbox escape), and the shared pattern is tested for `/loop-ask`. *Smallest sufficient fix:* add one direct unit test importing `_codex_argv` (with provider env) asserting `argv[-2:] == ["--", "<dash-leading message>"]` for `new` and `continue`; optionally add it to the §6 mutation list.
- **MINOR-2 — K6.1 claims "non-text messages" but only empty + oversized are tested.** `test_empty_oversized_and_non_text_messages_refuse_typed` covers `""`→`empty_question` and `"x"*5000`→`question_too_large`; no non-string input is exercised on `new_thread`/`sanitize_question`. Through the CLI/hook a message is always a string, so this is coverage-completeness, not a live risk. *Fix:* add a non-str case (or drop "non-text" from the row prose).
- **MINOR-3 — K6.2 claims redaction "BOTH directions" but only the outbound (owner message → packet) direction is asserted.** Inbound redaction (a secret inside the Codex *reply*) relies on `bound_answer` reuse (proven in the operator-channel pack) and `test_the_audit_trail_is_privacy_bounded` (which only proves the reply isn't leaked to the audit, not that a secret in the reply is redacted in the stored/displayed reply). *Fix:* add a reply carrying a fake secret and assert it is redacted in `outcome.reply`/the stored thread.
- **MINOR-4 — K2.5 `close` no-provider clean-execution path is not directly exercised.** `show` and `promote` prove the id-only, no-provider round trip; `close` is only hit via the extra-text refusal (`test_extra_text_after_an_id_only_subverb_refuses_visibly`), which returns before argv construction. Same argv shape as show/promote, so low risk. *Fix:* one hook test running `/loop-codex close cxt_x` under `NO_PROVIDER_ENV` and asserting execution (e.g. `unknown_thread`).
