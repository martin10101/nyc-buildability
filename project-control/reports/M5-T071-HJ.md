## Part 3 — Blocking findings

### B1 (BLOCKING) — The section still leads with a dead map-click invitation in every fallback state; the chartered defect reproduces one node up

The gating landed on `ProposalOutlineMap`'s own instruction paragraph. But the composed section the analyst reads, in this order, is:

1. `<h3>Draw the outline</h3>`
2. `ProposalOutlineDraw.tsx:182` — *"Proposed — your sketch, not a city record. **Click the lot map to place points** (or add and type them by keyboard below)…"* — **ungated**

4. `ProposalOutlineMap.tsx:149` — *"Add proposed outline points by keyboard… The reference map on this lot has no interactive drawing surface."* — correctly gated

On a condominium unit lot (no parcel polygon — common in NYC and the exact case that produced my T066 HJ-1), the analyst reads a map-click instruction, then a claim that a map is shown, and only then the sentence saying there is no interactive map. The first two are false and they come first. The packet's binding input names the literal string: *"the instruction copy 'Click the lot map to place…' renders ONLY when the interactive map actually rendered"* — `grep` over `apps/web/src` finds that string at `ProposalOutlineDraw.tsx:182` rendering unconditionally. AS-1's "the section leads with the keyboard-entry copy and never invites a map gesture" is not satisfied for the section a human sees.

Why the suite missed it: the `it.each(FALLBACK_STATES)` specs render `ProposalOutlineMap` alone, so the parent paragraphs are not in the DOM at all. And `proposal-outline-draw.test.tsx:32-37` mocks the leaf as a bare `<div data-testid="mock-lot-map">` with **no** aria-label, so every draw-level test runs with `mapRendered === false` and none of them assert copy. **No test in the repo renders the composed section with a map present, and none asserts the composed section's copy in a fallback state.** The contradiction is invisible to the whole suite.

Remedy (small, in scope): gate or neutralize those two sentences the same way — e.g. lead the honesty paragraph with the state-neutral claim and move the gesture clause into the already-gated wrapper copy, and make the map-context sentence conditional. Both files are in `allowed_paths` and were already edited by this increment.

### B2 (BLOCKING) — New on the dominant happy path: the wrapper asserts a definite negative while the map is still loading

`mapRendered` initializes to `false` and the effect runs after first paint, so the first thing **every** analyst sees — including on a perfectly drawable single lot — is:

> "Add proposed outline points by keyboard in the table below… **The reference map on this lot has no interactive drawing surface.**"

That is not a loading message. It is an unbounded negative claim about the lot, and it is false. It persists for the whole leaf load window: geometry fetch → dynamic `import("maplibre-gl")` → map construction → parcel render, bounded only by the leaf's 10-second readiness timer (`LotOutlineMap.tsx:436`). On a slow connection that is several seconds of a visible false statement on the primary path — long enough for an analyst to give up on the map and switch to typing coordinates.

It is also self-contradicting inside one subtree: while the wrapper says the lot has no interactive drawing surface, the leaf's own `lot-outline-summary` live region is simultaneously announcing *"Loading the approximate lot outline…"* (`LotOutlineMap.tsx:283`). A screen-reader user hears both.

Before this increment, drawable-lot users saw correct copy from mount; the wrong copy appeared only in fallback states. This increment fixes the fallback states at the wrapper node and introduces a new wrong state on the majority path. The wrapper's mock has no loading variant (`lotMock.variant` is `"interactive"` or a fallback testid), so this state is untested.

Remedy: a three-state copy — loading / drawable / typed-fallback — where the loading branch makes no claim about the lot, only about the current state ("Preparing the reference map — you can start entering points by keyboard now"). The existing `mapRendered` boolean cannot express it; a tri-state (`"unknown" | "present" | "absent"`) seeded from whether the leaf's loading node is present would.

## Part 4 — Advisories (non-blocking)

**A1 (MEDIUM) — Convert silently drops untyped rows once three finite points exist.** With 4 rows where 3 are finite, `canConvert` is true, the hint is suppressed (it gates on `finiteCount < MIN`), and `convert()` filters the empty row out of the payload with no notice. The status says "3 points drawn" while the table shows rows 0-3. Nothing says "1 row without coordinates was not included." The frontend rule "never silently apply a default that materially changes a scenario" points at a one-line disclosure here.

**A2 (LOW-MED) — The disable hint counts incomplete rows but does not identify them.** "3 rows still need a longitude and latitude" with eight rows on screen means hunting for empty inputs; no `aria-invalid`, no row marker. A screen-reader user must tab the whole table linearly. Row-level marking would make the recovery direct.

**A3 (LOW-MED) — The map-render transition is not announced (answering your question 1 directly).** When the map finishes loading and the copy flips from keyboard-only to "Click the lot map to place…", nothing announces it: the instruction `<p>` is not a live region. A screen-reader user who has already passed that text never learns the map became clickable; a sighted user only notices if looking. I am explicitly *not* recommending making it a live region as-is — that would add a sixth live region to the stack I flagged as T066 HJ-3. The better fix is folding the state change into the one status region the wrapper already owns.

**A4 (LOW) — The invitation can precede a clickable canvas.** The leaf paints the observed `aria-label` as soon as `drawable` is true (`LotOutlineMap.tsx:640-647`), which is before map construction completes. In that window the copy says "Click the lot map" while the container has no MapLibre instance and a click is inert. Short, but it is the inverse of B2 and the same tri-state fix covers it.

**A5 (LOW) — Selection of a non-drawn point announces inconsistently.** With one untyped row selected, the wrapper status reads "No points drawn yet." and drops the selection clause entirely (it lives inside the non-zero branch, `ProposalOutlineMap.tsx:160-164`), while the instruction copy says "Point 0 is selected — click the map to move it." Two regions, one selection, one of them silent. Functionally the click does place coordinates into that row, which is a nice hidden recovery, but "move it" describes moving something that is not on the map.

**A6 (LOW) — Empty-state copy assumes a map.** `outline-draw-empty`: "Add at least 3 points **over the lot**, then convert." Same class as B1, lower stakes.

**A7 (LOW) — Disabled Convert is unreachable by keyboard.** A `disabled` button is out of the tab order, so a keyboard-only user tabbing the actions never encounters Convert and learns of it only through the hint's live-region announcement, never on demand. `aria-disabled` with a click-time explanation is the usual remedy. Pre-existing, not introduced here.

**A8 (NIT, routes to G3-code/G4 rather than me) — one exact cross-render tally survives in the DB-048 file.** `lot-outline-map.test.tsx:568` still does `await waitFor(() => expect(mocks.addLayer).toHaveBeenCalledTimes(4))` in the AS-2 spec. The AS-1 sync spec itself is properly hardened (per-instance `sourceAddCounts`, `toHaveBeenLastCalledWith(overlay2)`, presence-not-tally on layers) and I believe it keeps its teeth. AS-4 scoped the requirement to the AS-1 spec, but the packet's DB-048 binding said "never an exact tally of calls across renders/effects **anywhere in the file**".
