The packet's binding input says "MAX-ENVELOPE CONTRACT (binding; exact names - never guess)" and requires unit fixtures to mirror `as_dict()` byte-shape; an invented enum value inside the fixture that claims to be that mirror is precisely what that clause prohibits. Reproduce with `grep -rn 'status: "no_fit"' apps/web/` (two hits) against `grep -n '= "' services/api/app/scenario/max_envelope.py` (lines 157-172, five real values).

**F2 (blocking). The one-action adoption deliverable cannot occur in production with the request this client builds, and nothing discloses it.**

The proof chain, each hop verifiable in source:

1. `maxEnvelopeRequestForProfile` always sends `lot_line_segments: []` and `street_lines: []` (`apps/web/src/lib/architect/max-envelope-api.ts:538-547`) — correctly, because the profile's geometry is display 4326 and must never be measured.

3. `_build_candidate` therefore returns `(None, CandidatePlacement(status=LOT_GEOMETRY_UNSUPPORTED, detail=geo_detail))` (max_envelope.py:797-800).
4. With `candidate` null and status not `fitted`, `candidateIsAdoptable` (max-envelope-api.ts:566-572) is false, so the `adopt-candidate` button never renders (MaxEnvelopePanel.tsx:176-189).

So packet output #2 ("One-action adoption of the Generated building option into the accepted draft model") and AS-4's first clause describe a path that, as wired, will never execute against the real route. Every adoption test — the panel suite, the entry AS-6 suite, and the e2e journey — supplies a hand-authored `status: "fitted", contained: true` placement plus a candidate block the server provably would not emit for the very request those same tests assert. The production code is honest about this: `max-envelope-api.ts:40-42` and `:521-523` both state "this surface sends none … so the engine returns the binding limits with an explicit placement gap and no candidate", and the panel degrades correctly to the `candidate-unavailable` card.
