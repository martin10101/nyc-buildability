## Human-style walkthrough findings (advisories — none blocking)

**HJ-1 (demo-critical wording).** In production the confirmed branch is **dormant**: the write router is unmounted (`main.py` has zero references) and the read document binds the empty process-wide `_DEFAULT_STORE` (`store.py:249`). Every multi-lot condo therefore shows, permanently, "**No one has recorded a confirmation** to treat these base lots as one site" — copy that invites an action that exists nowhere in the UI. A B3 demo attendee will ask "where do I confirm it?". Suggested addition: "Recording a confirmation is not available yet." Honest, and it closes the question before it is asked.

**HJ-2 (jargon, same always-visible sentence).** "…stand on their **honest unconfirmed footing**" (`:247`) is internal engineering voice (CLAUDE.md p19: plain facts, no jargon). Suggested: "…so the development limits above are not calculated for a combined site."

**HJ-3 (raw machine token in prose).** `(${confirmation.confirmerRole})` renders "(qualified_professional)" (`:232`, asserted verbatim in the test). Suggest a typed display map over the closed vocabulary (`user` → "user", `qualified_professional` → "qualified professional") — a map, never free text. Same line embeds the raw microsecond ISO instant mid-sentence ("on 2026-09-20T08:23:30.089123+00:00"); the never-reformat-a-timestamp convention is right, but a separate "Recorded: <iso>" clause would read better than a prose insertion.

**HJ-4 (supersession/revocation detail is dropped).** The web parses only `activeConfirmation` plus `confirmations.length` (`condo-records.ts:496-500`), so the unconfirmed-with-history copy can only say "it was **revoked or superseded**" — it cannot say which, when, by whom, or why, even though the payload carries every chain record's status, required `reason`, and transitions (`records.py:348-353`, block `confirmations` at `:525`). For slice 2 (and arguably now) parse the newest non-active record: "A confirmation recorded by <name> on <date> was revoked on <date>. Reason: <reason>."

**HJ-5 (provenance attribution).** The trailing provenance line (`:321`) is the **current** records fetch, yet it now sits directly beneath a confirmation that carries its own provenance snapshot (`source_id`/`dataset_ids`/`retrieved_at`/`resolution_path`, `records.py:240-251`) which is never displayed. A reader will naturally attribute the retrieval time to the confirmation. Suggest surfacing "Recorded against city records retrieved <ts>" inside the block, or relabelling the footer "Source for the lots above".

**HJ-6 (the same BBLs appear twice, in two formats).** The `<ul>` at `:316` is the *current* base-lot set; "Recorded base lots: a, b" at `:237` is the set *recorded at confirmation time*. They are semantically different but nothing says so unless the discrepancy note fires. Suggest "Base lots recorded in this confirmation: …". Sub-note: when every parcel is dropped by the bounder the sentence degenerates to "Recorded base lots: the recorded base lots." (`:234`) — prefer omitting the clause over a self-referential fallback.

**HJ-7 (legal framing — matters most at slice 2).** "treat these base lots as **one site**" will be read by an architect as a zoning lot (ZR §12-10), which requires ownership/declaration evidence the product does not hold. Harmless while nothing is calculated; load-bearing the moment slice 2 wires it. Suggest: "This records how a professional intends to treat these lots; it is not evidence of a zoning lot under the Zoning Resolution."

**HJ-8 (a11y asymmetry / heading outline).** Confirmed state = `role="group"` + `aria-label` nested inside the section's own `role="group"`, with no heading (`:235`); unconfirmed state = a bare `<p>` with no grouping (`:247`). Neither joins the heading outline the section now populates (`h2` at `:307`). Suggest an `<h3>Site definition</h3>` for **both** states — continues the T056 fix that promoted `<strong>` to real headings.

**HJ-9 (visual weight vs "LOUD").** `architect-condo-site-definition` has no CSS rule; everything inherits `.section-note` (12px, muted — `architect.css:37`). The packet's "loud" self-attested refusal is typographically the quietest text in the section. Honesty holds because the wording is explicit; suggest weight or a rule/border on the refusal line only.

**HJ-10 (latent copy gap).** The "recorded for reference only / refused for calculation" reassurance renders only when `refusedForCalculation` is true (`:238`). Today always true (single-member vocabulary, `records.py:127`), but if an authenticated status is ever added the confirmed block would render with no statement at all about calculations. State the calculation posture unconditionally.

**HJ-11 (malformed-payload copy invents a history).** If a well-formed ACTIVE confirmation is present but the block's top-level `status` literal drifts, the view correctly falls safe to unconfirmed (`condo-records.ts:512-517`) while `confirmationCount >= 1`, so the screen asserts "it was revoked or superseded" — false for that payload. Fail-safe direction is right; gate the history clause on an observed non-active record rather than on count > 0.
