=== M5-T083 findings (services/api/app/drawings/sheet_reader.py, sheet_primitives.py) ===

F1 (HIGH, BLOCKING) — single Bezier curve defeats the MAX_PATH_POINTS bound; ~1.9 GB from a ~330-byte input.
sheet_primitives.flatten_cubic (sheet_primitives.py:81-96) fully expands one cubic to a binary tree of up to 2**MAX_FLATTEN_DEPTH leaf points (MAX_FLATTEN_DEPTH=24, line 25) and RETURNS the whole list; only then does _curveto call _charge_points (sheet_reader.py:602-613, charge at 613; MAX_PATH_POINTS=500000 at line 82). So the per-page point budget is checked AFTER a single operator has already allocated the entire list. When control-point coordinates exceed what the depth cap can flatten (PDF numbers allow ~1e63, 64-byte tokens), every branch stays non-flat to depth 24 → 2**24 = 16,777,216 points for ONE `c` op.
Repro (measured): content `0 0 m <1e60> <1e60> <2e60> <-1e60> <3e60> 0 c S` (323 bytes) with MAX_FLATTEN_DEPTH rebound to 20 → tracemalloc peak 120.1 MiB, then refusal `path points`. Direct call at depth 16 with 1e60 coords → exactly 65536 points (2**16), confirming full expansion; default depth 24 → ~16.8M points ≈ ~1.9 GB transient before the 500k charge fires. This directly contradicts the module doctrine "untrusted input is bounded on ... path points ... Bezier subdivision."
Fix: thread the remaining budget into flatten_cubic and stop appending/subdividing once (point_count + len(out)) would exceed MAX_PATH_POINTS; or cap out-list length to the remaining budget and refuse. Charge incrementally, not after the fact.

F2 (MEDIUM) — Form XObject `Do` re-decodes its stream every time (no memoization); decode volume is uncharged.
_place_form (sheet_reader.py:877-908) calls _decode_stream (209-236) on each placement; there is no cache keyed by ref. Each `Do` costs one operator (op_count charged at 517-519, cap 200000) but the operator budget does NOT bound how many 8 MiB FlateDecode inflations occur. Worst case ≈ 200,000 Do × MAX_DECODED_STREAM_BYTES (8 MiB) ≈ 1.6 TB of decompression from a tiny file (CPU-time DoS).
Repro (measured): 50 `Do /F` on one FlateDecode form → 50 zlib.decompressobj() calls (proxy-counted), no cache. Fix: memoize decoded form content per (number,generation) for the document, or add a document-wide decoded-bytes budget that decode consumes.

G5 report part 2/3 — M5-T083 continued + verdict.

F3 (MEDIUM) — one _SheetInterpreter is shared across all pages and never reset: cross-page primitive leak + O(pages×primitives) memory.
read_sheet creates the interpreter ONCE (sheet_reader.py:336) and passes it to every _build_page; _SheetInterpreter.__init__ sets self.polylines/text_runs/images = [] once (428-435). interpret at depth 0 returns tuple(self.polylines/…) (453-454), i.e. the ACCUMULATED lists, so every page's SheetPage contains all EARLIER pages' geometry, and the cumulative per-page tuples grow O(pages × total primitives) (≈1 GB worst case with 512 pages under the 500k-point budget).
Repro (measured): 2-page doc, page0 draws one line, page1 draws another → page0.polylines len 1, page1.polylines len 2, and page1.polylines[0].points == page0's line ((0,0),(10,10)). Primary impact is correctness/provenance integrity (wrong geometry attributed to the wrong sheet — flag to G3/G4 too); the security angle is the bounded quadratic memory amplification. NOTE: sharing also makes op_count/point_count document-wide, which is fine for bounding — keep those shared via an explicit counter, but give each page its own output lists (fresh interpreter per page, or snapshot+reset).

F4 (LOW, ADVISORY) — read_sheet (305-376) has NO top-level try/except, unlike the sibling read_dxf (630-641). Any future/edge exception in a helper would escape, breaking "refusal is a VALUE." 6000 fuzz inputs (mutations + random blobs) produced 0 escapes today, but the backstop is absent. Fix: wrap the body and return a SheetRefusal on unexpected Exception.

F5 (LOW, ADVISORY) — unknown-operator refusal detail echoes the raw operator token untruncated (_execute 676-679; the word run at 511-515 has no length bound). Measured: a 100000-char token → refusal.detail length 100061 (bounded only by the 8 MiB stream cap). Contrast the lexer's 64-char bounded diagnostics. Fix: truncate attacker-derived detail to a short preview.

F6 (LOW, ADVISORY) — CTM arithmetic can overflow with no output-finiteness guard. Measured: eight `cm` ops with scale 1e40 then a line → output polyline points ((nan, nan), (inf, inf)), accepted (no refusal, no crash). Downstream consumers may not expect non-finite coordinates. Fix: validate finiteness of emitted coordinates.

POSITIVES (verified): FlateDecode decompression-bomb is correctly bounded via decompressobj().decompress(raw, MAX_DECODED_STREAM_BYTES) + unconsumed_tail/eof check (_decode_stream 229-235) — a 20 MiB→8 MiB bomb refused at 16.1 MiB peak. Inherited strict-reader bounds hold (≤4096 objects, nesting 32, 8192 items/collection, 64-byte numbers, exponents/nan/inf rejected at the lexer). q-depth (128), XObject depth (8) and ref-cycle refusal all present/correct. No code exec, file, or network; no logging; bounds are module constants (NOT caller-injectable). Non-bytes input and non-finite/zero flatten_tolerance refused.

M5-T083 G5 VERDICT: FAIL — F1 is a reproducible bypass of a documented safety bound (single ~330-byte op → ~1.9 GB) and is blocking on its own; F2/F3 are additional DoS/integrity defects. The planned parser-isolation gate is defense-in-depth, not a substitute for the reader honoring its own stated path-point bound. Fixes are small and local.

G5 report part 3/3 — M5-T086 DXF reader (services/api/app/drawings/dxf_reader.py) + verdict.

Findings — all ADVISORY (no blocking issue found):

A1 (LOW) — DxfLimits is a public keyword param (read_dxf, line 622) with __post_init__ enforcing only `>= 1` (172-175); there is no upper clamp. A production caller could pass a permissive DxfLimits and effectively disable the size/line/entity/vertex protections. Confirmed: DxfLimits(max_bytes=10**18, max_lines=10**18, …) constructs fine. Recommend the later isolation-wiring packet pass DEFAULT_LIMITS and never let request input tune limits.

A2 (LOW) — _to_pairs uses text.splitlines() (474-475), which splits on more than the documented CR/LF: \x0b \x0c \x1c \x1d \x1e are all ASCII (survive the ascii decode) and are treated as line breaks. Confirmed: "1\nAB\x0cCD".splitlines() == ['1','AB','CD']; a TEXT value containing \x0c → odd_pair_count refusal (safe misparse, no crash). Robustness/doc gap only; recommend splitting on \r\n/\r/\n explicitly or documenting the wider set.

A3 (LOW) — the `str` input branch of _decode (469-471) skips the binary-sentinel and non-ASCII checks (documented as test convenience). Confirmed: a str with a non-ASCII char is not caught as NON_ASCII (returns a different refusal, still a value). Ensure production only ever passes bytes.

A4 (LOW) — splitlines() allocates the full line list before the max_lines check (475-477); an 8 MiB newline file materializes ~8M short strings (hundreds of MB transient) before refusal. Bounded by max_bytes; minor.

POSITIVES (verified): every refusal is a VALUE and the public boundary has a defensive catch-all (read_dxf 636-641) — 9000 fuzz inputs (mutations + random blobs) → 0 escaping exceptions. Coordinate finiteness enforced: nan / inf / -inf / 1e999 / 400-digit integers all → BAD_COORDINATE (_to_float 283-294). Binary sentinel, non-ASCII, file-size, line-length, line-count (odd-pair), entity-count and polyline-vertex bounds all fire at their edges (verified with injected small limits). Non-zero bulge refused (UNSUPPORTED_BULGE). Unknown ENTITIES types are disclosed/counted, whole non-HEADER/ENTITIES sections skipped — no crash. Units reported honestly (feet from $INSUNITS; absent → unitless/"absent"). Python arbitrary-precision ints (no integer overflow); int()/float() digit-limit ValueErrors are caught. No code exec, file, or network; no logging of attacker content (bounded refusal detail only). CRLF/CR/LF all handled.

M5-T086 G5 VERDICT: PASS — solid fail-closed parser; only the advisories above (chiefly A1: don't expose limit-tuning to untrusted input when wiring it in).

SUMMARY: M5-T083 G5 VERDICT: FAIL (blocking F1; also F2, F3). M5-T086 G5 VERDICT: PASS (advisories only). Both parsers correctly avoid code execution, filesystem, and network access, and neither is route-wired yet.
