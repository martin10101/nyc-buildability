== FINDING 1 — HIGH / BLOCKING — O(n^2) CPU DoS in the new line splitter ==
File: services/api/app/drawings/dxf_reader.py:549-568 (`_iter_dxf_lines`), specifically the per-line double find at :550-551.

Root cause: every loop iteration calls BOTH `text.find("\n", pos)` and `text.find("\r", pos)`. When a file uses only ONE terminator type (pure LF, or pure CR), the other `find` returns -1 only after scanning the ENTIRE remaining string — every line. That is O(lines x bytes) = quadratic.

Measured (read_dxf, DEFAULT_LIMITS), LF-only input `"0\n"*k`:
- k=50000 (100KB): 0.507s
- k=100000 (200KB): 1.819s (3.59x)
- k=200000 (400KB): 6.794s (3.74x)  -> clean quadratic (~4x per doubling)
CRLF control `"0\r\n"*k` scales ~2x (linear): 400KB=1.1s, 1.2MB=1.85s.

Extrapolation to the DEFAULT cap (max_bytes 8MB, max_lines 2M) with valid-pair LF content: ~1.2e13 char-scans / ~5.9e9 scans-per-sec (measured) ≈ ~30-36 MINUTES of CPU for a SINGLE upload. At the clamp ceiling (64MB / 8M lines) it is far worse (hours). The bytes production path is identical (decode is a one-time O(n) then the same str).

Why this is blocking, not cosmetic:
(a) Remotely-triggerable CPU-exhaustion DoS on exactly the untrusted input this packet exists to bound (threat model: a later import packet feeds user-uploaded DXF to read_dxf). A handful of 8MB uploads saturate the worker.
(b) REGRESSION introduced by this commit: the old `_to_pairs` used `text.splitlines()` — a single O(n) pass. The streaming refactor fixed MEMORY but made TIME quadratic.
(c) Hits LEGITIMATE files too: our own writer emits LF-only (services/api/app/cad/dxf_writer.py:85 `_EOL="\n"`, joined at :318), and Unix/macOS/AutoCAD exports are commonly LF-only. So even our round-trip output degrades at scale.
(d) Not caught by the suite: the AS-2 "allocation probe" (test_dxf_reader.py `test_t097_as2_max_lines_enforced_before_full_list_allocation_probe`) caps at max_lines=1000 and asserts only tracemalloc PEAK MEMORY — it never measures wall-time near a cap. The threat model's "measure a worst-case input near each cap" was done for memory, not CPU.

Remediation: replace the double-find with a single-pass terminator scan that never re-scans for an absent terminator — e.g. `re.finditer(r"\r\n?|\n", text)` (one C-level pass) or a combined-search loop — preserving CR/LF/CRLF-only semantics, streaming, and the line/char caps. Add a TIME/work probe near max_bytes/max_lines asserting bounded, near-linear scaling (not just memory).

== ADVISORIES (non-blocking for this module; named for the later import/wiring packet) ==

A1 — MEDIUM (for the import/display/logging route, DB-057 follow-up): ASCII control chars are KEPT VERBATIM in TEXT values, layer names, and $ACADVER (by design; correct here for provenance). Observed: a TEXT group-1 value `HI\x1bWORLD\x0b\x0c\x1c\x1d\x1eEND` survives intact, including ESC (0x1b). Downstream terminal-escape / log-injection / (if rendered) UI-injection risk. The consuming route MUST escape/sanitize on output and MUST NOT log raw primitive text. NUL is refused in structural positions (bad_group_code / bad_coordinate) but kept inside a TEXT value — same handling required.

A2 — LOW: refusal `detail` embeds up to `max_line_chars` of raw attacker content (measured detail_len=4025 for a 4000-char bad coordinate). It is repr-escaped (control chars neutralized in the detail itself) and bounded (default 4096, ceiling 65536), but the API/log layer should not reflect `detail` verbatim/unbounded to end users.

A3 — LOW (defense-in-depth): the huge-integer group-code/flags/$INSUNITS defense relies on the interpreter default `sys.get_int_max_str_digits()`=4300 plus `max_line_chars`. If a deployment sets PYTHONINTMAXSTRDIGITS=0 AND a caller raised max_line_chars toward the 65536 ceiling, `int()` on a ~64K-digit line is O(digits^2). Default Python is safe; consider an explicit small digit cap on group codes.

A4 — LOW/INFO: only exact `bytes`/`str` accepted; `bytearray`/`memoryview` are refused as MALFORMED_STRUCTURE (fail-closed, not a vuln). Import packet should pass `bytes`. Also DxfLimits(<1) raises ValueError at construction (outside read_dxf's try/except) — acceptable since limits are reviewed constants, not user-controlled; do not build DxfLimits from untrusted input.
