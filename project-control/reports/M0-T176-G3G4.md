=========================== G3 (CORRECTNESS): PASS ===========================

1) The fix is correct and minimal. A new `except PermissionError as exc:` sits BETWEEN `except FileExistsError` and the generic `except OSError`. FileExistsError and PermissionError are sibling OSError subclasses (neither subclasses the other), so the top-down order routes each correctly: FileExistsError->clause1, PermissionError->clause2, EIO/other->clause3. On Windows (`_is_windows()` True) a PermissionError is treated as busy -> `_wait_or_fail_closed(deadline)` -> continue (retry to the deadline), and NEVER calls `_holder_is_stale`/`_take_over`. On POSIX (`not _is_windows()`) it raises slot_lock_error at once (pre-fix behavior, unchanged). The shared `_wait_or_fail_closed` helper is byte-equivalent to the old inline FileExistsError check+sleep, so the FileExistsError path is behaviorally unchanged.
   - Grant without the lock? NO. acquire() returns only after a successful O_EXCL create or a confirmed `_take_over()`; the PermissionError branch only ever `continue`s or raises. No success path bypasses the create.
   - Take over a live lock? NO. The PermissionError branch has no takeover call; the FileExistsError takeover path (readable + provably dead/reused only) is untouched. A genuinely stale, non-delete-pending lock still surfaces as FileExistsError (file present+readable) and is reclaimed as before, so Windows loses no reclaim capability; a delete-pending file is a holder mid-RELEASE (not a dead holder), and it clears on its own.
   - Permanent Windows permission fault hang? NO. Every create raises PermissionError -> wait one poll -> ... -> at `time.monotonic() >= deadline` raise slot_lock_timeout. Bounded by timeout_s and fail-closed; no infinite loop. Verified by test_persistent_permission_error_times_out_as_nt (0.2s timeout -> slot_lock_timeout, calls>1).

2) Per-site analysis — I AGREE each untouched site is fail-safe on Windows:
   - _read_holder: read_text opens/reads/closes in one call (short-lived handle, narrows the delete-pending window); a delete-pending/mid-write read raises OSError -> caught -> None -> "not stale" -> wait, never steal. Doc comment only.
   - _take_over/os.replace: runs only after _holder_is_stale()==True; any OSError from temp write or os.replace is caught -> temp.unlink (suppressed) -> return False -> acquire falls to `_wait_or_fail_closed` -> retry. A failed takeover can only degrade to wait/retry (then timeout fail-closed), never a grant and never an over-admit. No sharing violation becomes a spurious hard refusal here — it becomes a bounded wait.
   - release unlink: reads holder, unlinks ONLY when on-disk lock_id==this lock's id; unlink wrapped in suppress(OSError). Never removes/forges another's lock, never crashes. Delete-pending walk-through is sound (either unlink succeeds+marks pending and clears, or raises+suppressed and the still-present file yields FileExistsError on the next create, i.e. the §1 defect does not arise).
   - state-file I/O (_read_raw/_read_live/_write): executes only while holding the exclusive cross-process _SlotLock, so exactly one process touches review_slots.json at a time — no concurrent reader to cause a Windows sharing violation; _write uses a pid-suffixed temp + os.replace. Contention-free. Agreed.
