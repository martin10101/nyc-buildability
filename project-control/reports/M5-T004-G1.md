## Findings

**1. HIGH — `assumptions` never rendered or surfaced.** Zero references across `components/compare/**` and `app/property/compare/**`. Schema (`scenario.schema.json:21` required, `:85` property): *"Preliminary scenarios vary ONLY via explicit typed assumptions (no hidden utilization/optimization defaults)"* and *"Any variation exists ONLY as an explicit entry here."* Consequence: two preliminary scenarios differing **only** by a declared `utilization_factor` or `efficiency_ratio` render **byte-identically** — the one honesty field distinguishing them is invisible. `docs/PRODUCT_FLOW_AND_AI_BOUNDARIES.md:49` lists Assumptions as a required evidence element. *Fix:* render each assumption (`key`, `assumption_type`, `value`, `unit`, `rationale`) in `ScenarioCard`; when empty, say so explicitly rather than rendering nothing.

**2. HIGH — `reasons` dropped on every `preliminary` scenario.** `ScenarioResult.tsx:178-182` routes preliminary → `ScenarioCard`, which never reads `document.reasons`; the only renderer is `NoScenarioBlock` at `:49-53`. `preliminary_r5_cap.json` carries: *"Preliminary scenario: surfaced the canonical draft residential zoning-floor-area cap (ZR 23-21) from the rule_evaluation trace, verbatim. NOT a buildable envelope — see the coverage matrix for the rule families still MISSING."* Schema `:90` documents `reasons` as carrying named missing constraints and integrity disagreements — precisely what a reader of a *successful* cap most needs. *Fix:* render on all three `scenario_kind` paths.

**3. HIGH — top-level `data_completeness` never rendered.** Only the per-constraint value is shown (`ScenarioCard.tsx:112`). All fixtures carry `missing_critical`. The screen shows `coverage_status: conditional` glossed "Official source fact, not yet professionally reviewed" and never states the data is **critically incomplete**. The helper `completenessDisplay()` already exists (`lib/coverage.ts:79`) and is used by `ConfirmScreen.tsx:180` and `PropertyLookup.tsx:99` — one import away. *Fix:* render it in the `scenario-summary` header beside the coverage label.

**4. HIGH — every `constraints[].note` dropped.** `ScenarioCard.tsx:103-115` renders `key`, `value`, `unit`, `state`, `data_completeness` and stops; `note` is schema-required (`:158`). The notes are the only carrier of *"MUST NOT be inferred, defaulted, or estimated"* on all 8 missing families, and of the full *"DRAFT maximum residential ZONING-FLOOR-AREA CAP under ZR 23-21 … NOT a buildable envelope … NOT Verified"* text on `residential_far_cap`. The state label ("missing (no rule family provides it)") is weaker, not equivalent.

**5. HIGH — `cap_provenance.citations` never rendered anywhere in the repo.** `ScenarioCard.tsx:70-94` renders `rule_id`/`rule_version`/`rule_status`/`output_name`/`note` and stops. The cap at `:50-52` — the only material number on the screen — displays without `snapshot_id: zr-23-21`, `section: 23-21`, the quoted ZR text, `source_id: nyc-dcp-zoning-resolution-portal`, `request_url`, `retrieved_at: 2026-07-21`, `last_amended: 2024-12-05`, `raw_html_verified: false`, `extraction_status: extracted_draft`. Schema's `citation` def: *"a material value may never be surfaced without it, PRD section 19"*; `CLAUDE.md:13` principle 2 is unconditional. The accepted sibling `rule-evaluation/RuleEvaluationResult.tsx:107-150` renders exactly this set in a collapsed `<details>`, so progressive disclosure does not justify omission. `ScenarioResult.tsx:136-139` ("Evidence and provenance … arrive with a later milestone") acknowledges a deferral but does not license dropping provenance the document already carries. *Fix:* collapsed `<details>` mirroring `RuleEvaluationResult.tsx:77-150`.

**6. HIGH — competing-rule conflicts never surfaced; `ruleConflict()` is dead code.** Defined `scenario-display.ts:126-160`; imported by no component and no test (repo-wide grep). `no_scenario_conflict.json` records two competing draft rules on `constraints[residential_far_cap].provenance` — `r5-residential-far@0.1.0-draft` vs `r5-residential-far-alt@0.2.0-draft`, both emitting `max_residential_floor_area_sq_ft`. The screen shows only two generic `reasons` strings; *which* rules conflict never reaches the user. The producer report §1 lists `ruleConflict` as delivered, which is not accurate as wired. *Fix:* call it from `NoScenarioBlock` and render competing output names + rules, as `baseDistrictCandidates` already is at `ScenarioResult.tsx:30`.

**7. HIGH — `evaluated_input` dropped in full; the displayed BBL comes from the URL, not the document.** No file reads `document.evaluated_input`. `ScenarioResult.tsx:167` prints "Preliminary comparison for BBL {bbl}" from the route param threaded via `CompareScreen.tsx:153-159`. A document whose `evaluated_input.bbl` or `input_fingerprint` did not match the requested property is indistinguishable on screen — the contract identifies input by reference precisely so consumers can confirm this. Sibling renders all four at `RuleEvaluationResult.tsx:77-100`. *Fix:* render the four fields in the provenance disclosure; title from `document.evaluated_input.bbl` when non-null.

**8. MEDIUM — `constraints[].provenance` never shown as provenance.** `ScenarioCard.tsx:106` shows `lot_area = 10,000 square_feet` with no source, though the fixture carries `profile_field: lot_geometry.area_sq_ft`, `source_id: nyc-dcp-lot-geometry`, `dataset_version: 26v1`. Only two narrow readers exist and one is unwired (finding 6). The professional-review fixture's `zoning_district` provenance also carries `review_reasons`, `coverage_note`, `lot_overall_class` — all dropped; the stated reasons for the escalation never render.

**9. MEDIUM — `needs_review` is accepted as `false` for a field the schema pins as always-true.** `scenario-contract.ts:318-322` type-checks the field only, while `scenario.schema.json:44` declares it "Always true" (typed as a bare boolean with no `const`). Validator-depth defect, same family as findings 10–12.

> **CORRECTION (recorded 2026-09-11, reviewer-initiated on re-read).** This finding was first reported as HIGH with the claim that `needs_review: false` would make the DRAFT label vanish, leaving "a bare, unlabelled cap number." **That claim was wrong and is withdrawn.** `ScenarioCard.tsx:47-49` is an **unconditional static prefix** immediately before the number — "**Draft** maximum residential zoning floor-area cap:" — which no server field can switch off. Three further draft signals also survive independently: `cap_label` directly beneath (`:61-65`), `not_verified_disclaimer` in the summary header (`ScenarioResult.tsx:173-175`), and the page header "Draft engineering only — never a Verified determination" (`CompareScreen.tsx:103-107`). What `needs_review: false` actually removes is only the *additional* inline status label at `:55-59`.
>
> **Consequently AS-1 is PASS, not PASS WITH DEFECT** — its requirement is that a text label always accompany the value rather than colour alone, and the unconditional prefix satisfies that in every case.
>
> **Note on the DCV report:** `M5-T004-DCV.md` carries the same original claim in its AS-1 section, including the "with `cap_label: null` … no draft qualifier at all" variant. That claim is **superseded by this correction** — the unconditional prefix at `ScenarioCard.tsx:47-49` defeats it regardless of `cap_label`. DCV's AS-1 verdict of PASS is unaffected.

*Fix (unchanged, lower priority):* reject `needs_review !== true` in the validator.
