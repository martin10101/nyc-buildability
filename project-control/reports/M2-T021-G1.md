## VERDICT

## FINDINGS

### 1. BLOCKING — `services/api/tests/fixtures/geoclient/G02_address_ambiguous_ee.json:8` and `G03_address_rejected_42.json:8`: the recorded retrieval timestamp post-dates the commit that contains the fixture, so it cannot be the capture time.

Both fixtures record `"retrieval_timestamp_utc": "2026-09-11T19:55:00Z"`. Both are added by commit `dc227c0a`, authored *and* committed at `2026-09-11T15:41:40-04:00` = **19:41:40Z** — 13 minutes 20 seconds *before* the claimed capture.

Supporting evidence:

- `git log -- services/api/tests/fixtures/geoclient/` returns exactly two commits: `dc227c0a` (G02, G03) and `ccf64f75` (G01). No later commit touches the fixtures.
- Every commit on the branch ends at `d4cdbe79` = `2026-09-11T15:43:55-04:00` = 19:43:55Z, still before 19:55Z. There is no commit after the claimed capture time.
- Author date equals committer date for `dc227c0a`, so this is not a rebase or amend artifact.
- Two independently issued live GETs share the same timestamp to the second.
- Every timestamp in all three fixtures lands on a round `:00` second (G01 18:45:00, G02/G03 19:55:00).

The combination reads as hand-authored placeholder values, not recorded capture times. No timezone reading rescues it: 19:55Z interpreted as 15:55 local is still 14 minutes after the 15:41:40 local commit; interpreted as 19:55 local it is later still.

**Failure scenario.** The packet path note requires each live capture to record "the request URL WITHOUT the key, http status, **retrieval timestamp** and response sha256," and CLAUDE.md principle 2 requires material facts to retain provenance. A retrieval timestamp that is provably not the retrieval time is a fabricated provenance field in the exact evidence that S3 and S4 acceptance rest on. Downstream, any staleness or data-currency reasoning that trusts this field reasons from a false value.

**Correction.** Re-record the true capture timestamps, or — if the captures were real but the timestamps were written by hand — state that explicitly in the fixture and correct the values.

**Orchestrator response (received after this review was delivered; recorded here, NOT independently verified by me).** The orchestrator confirms the finding: the two timestamps were hand-authored round estimates rather than recorded capture times. It states that the captures themselves were live, and that the raw response files held in the session scratchpad carry the true filesystem write times which will anchor the correction. It further states that G01's `18:45:00Z` will receive the same treatment — which matches the round-`:00`-second pattern I flagged across all three fixtures. I have not inspected those scratchpad files and take no position on the live-capture claim; the mechanical contradiction in the committed field stands as written above, and the correction remains blocking until the true times and an explicit basis statement are committed.

### 2. BLOCKING — `services/api/app/connectors/geoclient_address.py:453-454`: a truthy non-string `house_number` or `street` escapes the typed error taxonomy as a bare `AttributeError`.

`house_number_in = (house_number or "").strip()` calls `.strip()` on whatever the caller passed. Confirmed against the tree:

```
resolve_address(314, 'w 100 st', borough='manhattan', key='k')
  -> AttributeError: 'int' object has no attribute 'strip'
```

`None`, `""` and `[]` happen to produce `InvalidInputError` only because they are falsy. Lines 455-456 immediately below guard `borough` and `zip_code` with `isinstance(...)` checks, so the omission is an inconsistency rather than a deliberate contract.

**Failure scenario.** This connector exists to back an address-entry endpoint, where `{"house_number": 314}` is an entirely natural client payload — house numbers look numeric. The endpoint gets an unhandled `AttributeError` (HTTP 500) instead of the typed `InvalidInputError` the packet objective promises, and packet S4's "no exception escapes as an unhandled error" is violated.

**Correction.** Guard `house_number` and `street` the same way `borough` and `zip_code` are guarded.

### 3. BLOCKING — `services/api/tests/connectors/test_geoclient_address.py:347-358`: `test_s6_key_is_read_from_env_at_call_time_header_only` never reads an environment variable; the `os.environ` production branch has zero coverage.

The test passes `env={KEY_ENV_VAR: SENTINEL_KEY}` — the injected mapping, not the environment. The production branch at `geoclient_address.py:472` is `source = os.environ if env is None else env`, and no test in the module ever reaches the `env is None` side. Nothing in the suite demonstrates that `GEOCLIENT_SUBSCRIPTION_KEY` is read from the process environment at all, nor that it is read *at call time* rather than captured at import.

**Failure scenario.** Change line 472 to read a module-level constant captured at import, or to read the wrong variable name, and all 36 tests still pass while the deployed connector fails on Render (where the key arrives only as an env var). Packet S6 explicitly requires "the key is read at call time from `GEOCLIENT_SUBSCRIPTION_KEY`"; that requirement is currently asserted against a test double.

**Correction.** Add a test using `monkeypatch.setenv(KEY_ENV_VAR, SENTINEL_KEY)` with `env` left at its default, plus one that sets the variable *after* a first call to demonstrate the call-time read.

### 4. HIGH — `geoclient_address.py:315-337`: `_extract_suggestions` trusts the declared count downward, silently discarding suggestions the source actually returned; the docstring calls the count "untrusted."

`count` is clamped with `max(0, min(count, _MAX_SUGGESTIONS))` — bounded above at 32, but taken verbatim below. Confirmed by direct call into the module:

```
declared='00', streetName1..3 present  -> []
declared='-3', streetName1..3 present  -> []
declared='01', streetName1..3 present  -> [slot 1 only]
declared absent / 'abc' / '999999'     -> all three surfaced
```

So a response that declares zero (or a negative) while carrying populated slots yields `status == "ambiguous"` with an empty `suggestions` list — a dead end for the UI and the precise outcome packet S3 exists to prevent ("typed AMBIGUOUS outcome for EE carrying the source's suggestion list verbatim").

The docstring at line 319 says "The declared count is untrusted: it is bounds-clamped," which is accurate only in the upward direction. The rest of the docstring **is** accurate: I verified the `continue`-on-missing-slot behavior matches "walked past a missing index only up to the clamp" — `{count: '03', streetName1: 'A', streetName3: 'C'}` returns both A and C.

None of this is tested. The only EE fixture (G02) declares `"01"` and carries exactly one slot, so the loop, the clamp, and every hostile-count branch ship unexercised.

**Correction.** Walk to `_MAX_SUGGESTIONS` and use the declared count as a cross-check rather than an upper bound, or document that it is authoritative downward — and add the tests either way.

### 5. HIGH — `geoclient_address.py:413`: the connector uses the legacy no-jitter retry policy and silently ignores `Retry-After`, diverging from every other M2-wave connector, undisclosed in the producer report.

`compute_delay=fixed_exponential_delay(backoff_base)`. The shared transport module documents this at `app/resilience/transport.py:235-242` as the "Legacy M1-T002 `pluto_soda` policy... plain exponential with no jitter and **no Retry-After wait**," and documents `jittered_retry_after_delay` at `transport.py:252-264` as "the M1-T009 policy used by the M2-T007/T008/T009 connectors." I confirmed all three siblings (`ztldb_soda.py:681`, `zoning_features_arcgis.py:632-662`, `mappluto_geometry_arcgis.py:1153-1180`) use the jittered policy.

**Failure scenario.** Geoclient sits behind an Azure APIM gateway whose rate limits the registry record itself lists as officially UNKNOWN. On a 429 the shared engine captures the gateway's `Retry-After` into the error detail (`transport.py:482-484`) and this connector then throws it away, retrying at 0.5s and 1.0s regardless of a `Retry-After: 120`; with no jitter, concurrent address-entry requests retry in lockstep. The M1-T009 "honor an over-cap Retry-After by not retrying" stop is also lost.

Neither the module docstring (which claims only "bounded and small") nor the producer report mentions the choice. `.claude/rules/backend-api.md` requires connectors to "handle pagination, rate limits, nulls, and schema drift explicitly."

### 6. MEDIUM — `geoclient_address.py:524`: no injectable clock; `provenance["retrieved_at"]` is untestable.

`retrieved_at = _rfc3339(datetime.now(UTC))`, whereas `pluto_soda.py:608` and `ztldb_soda.py:764/1128/1482` all take `clock: Callable[[], datetime] = _utc_now` and call `_rfc3339(clock())`.

Consequence: `test_s1_provenance_is_complete_and_key_free:140` can only regex the *shape* of the timestamp, never its value; a bug that stamped the wrong instant (or a non-UTC one) would pass. The siblings also stamp deliberately *after* a successful response (`pluto_soda.py:654`, "G3 D3"); here the ordering is correct by accident of statement position, with no comment pinning it.

### 7. MEDIUM — `geoclient_address.py:295-312`: GRC disagreement precedence is entirely untested, and non-`resolved` outcomes carry populated canonical fields with no warning on the result contract.

The parametrized S2 table at `test_geoclient_address.py:182-195` covers only `{00,01} x {00,01}`; the recorded EE (G02) and 42 (G03) fixtures both carry *identical* codes in both sub-calls. Every disagreement path ships unexercised. I ran the matrix directly against `_classify`:

```
('00','EE') -> ambiguous     ('42','EE') -> ambiguous
('EE','00') -> ambiguous     ('EE','11') -> ambiguous
('00','11') -> not_found     ('11','00') -> not_found
('01','11') -> not_found     ('00','42') -> rejected
('00',None) -> unrecognized_status      ('00','0')  -> unrecognized_status
('ee','EE') -> unrecognized_status      ('00','00\n') -> rejected  (see Finding 12)
```

Two consequences worth a deliberate decision rather than an accident:

- `('42','EE') -> ambiguous` offers the user street suggestions when the real failure is an out-of-range house number.
- `('00','11') -> not_found` is the documented *common* case (research doc 2.7: "many locations are valid for only one of the two sub-calls"), and because `bbl`/`bin` are extracted at lines 536-537 regardless of status, that outcome carries a populated `bbl` while reading `not_found`.

The information is preserved — both codes are on the outcome, so a caller can distinguish the cases — so this is not data loss. But `AddressResolution`'s docstring (lines 250-253) never warns that canonical fields may be populated on non-resolved statuses, and the S4 test that exercises the behavior buries the fact in a comment.

To the module's credit, I confirmed the invariant that matters most holds: **no input can reach `resolved` without both codes being exactly `"00"`** — `shaped` must have length 2 (line 302), then `all(c in _GRC_SUCCESS for c in shaped)` (line 308).

### 8. MEDIUM — `geoclient_address.py:238-245`: `RESOLUTION_STATUSES` is dead code.

### 9. MEDIUM — `geoclient_address.py:422-435`: no `AnalysisBudget` threading, unlike all three M2-wave siblings.

`ztldb_soda.py:767`, `zoning_features_arcgis.py:625`, and `mappluto_geometry_arcgis.py:1153` all accept `budget: AnalysisBudget | None` and pass `budget_error=RequestBudgetExceededError` into `standard_retry_hooks`; `request_with_retry` consumes one unit per attempt before I/O (`transport.py:452-454`). ### 10. MEDIUM — `geoclient_address.py:25-26` vs `:525-526`: the documented GRC alias fields are never read.

Fail-closed, so not a correctness hazard — but the docstring should say the aliases are deliberately not consulted, or the code should fall back to them.

### 12. LOW — `geoclient_address.py:118` and `:127`: `$` instead of `\Z` lets a trailing newline through.

### 13. LOW — `geoclient_address.py:213-220`: `_OPENER` plus the local `urllib_transport` wrapper are a no-op indirection with zero coverage.

## CLAIMS CHECKED

### Verified true

- **"36 tests"** — counted 36 including parametrization.
- **"Three fixture sha256 checks"** — recomputed independently; all three match.
- **"Fixtures verified key-free"** — no key-shaped material in any fixture; the only 32-hex runs are the `response_sha256` values themselves; the recorded `request_url` fields carry no key; the test sentinel is an obvious non-credential.
- **"Reuses the shared hardened transport… no redirect following"** — traced `NoRedirectHandler` → `DEFAULT_OPENER` → `urllib_transport(opener=...)`. The claim holds.
- **"Error classes match the `standard_retry_hooks` contract"** — `GeoclientConnectorError.__init__(message, *, correlation_id, detail=None)` matches the `(message, *, correlation_id, detail, **error_kwargs)` contract documented at `transport.py:353`, with `error_kwargs` correctly omitted.
- **"401/403 never retried"** — confirmed in code (`raise_for_unexpected_status` raises before any retry decision) and by `test_s5_auth_failure…:271` asserting a single call under the default `max_attempts=3`.
- **"Anti-tautology discipline throughout"** — the S1/S3/S4/S8 fixture-equality tests genuinely load expected values from the fixture. S1's literal `request_params` restate the test's own inputs, which is legitimate and not a fixture-value restatement.
- **"Modularity clean"** — 572 raw lines is under the 600 `WARN_SLOC` threshold and roughly 18 top-level symbols is well under the 40 `SYMBOL_CEILING`. Plausible; I did not run the checker.
- **"`canonical_json_digest` from `pluto_soda`"** is the established repo convention — `zoning_features_arcgis.py:80`, `ztldb_soda.py:100`, and `mappluto_geometry_arcgis.py:112` all import it the same way. Not a coupling defect.

### Contradicted

- **"Two new RECORDED fixtures (live captures from the owner machine)… each recorded with… retrieval timestamp"** — the recorded timestamps post-date the commit containing them by 13+ minutes and are identical to the second across two separate GETs (Finding 1). I can neither confirm nor refute that live captures occurred; I can state that the timestamps as committed cannot be the capture times. The orchestrator has since confirmed the timestamps were hand-authored estimates and states the captures were live — see the recorded response under Finding 1, which I did not independently verify.

### Overstated

- **"S6 exercises… every failure path… asserts the sentinel appears in no outcome, exception, payload, or captured log record"** — the harvest covers six paths (three fixtures, 401, timeout, malformed). 429, 500, unexpected-status and invalid-input are not harvested, so "every path" is not accurate. The residual leak risk is low (the key never enters a URL or a detail dict), but the claim overreaches.
- **"Bounded retry on 429/5xx/timeout/network only via `standard_retry_hooks`"** — true as far as it goes, but omits that the legacy no-jitter policy was selected and that `Retry-After` is discarded (Finding 5).
- **"~500 lines incl. documentation"** — the file is 572 lines.
- **"The default network transport is proven unreachable before the key check"** — `test_s7_key_check_precedes_any_transport_use` proves the key check precedes transport *invocation*, which is the useful property; the wording overstates what is asserted.

### Unverified by me

- **"375 connectors tests pass," "ruff clean," "secret-scan PASS"** — all three require running write-producing tooling, which read-only discipline forbids. The producer's own report already notes CI has not run on this branch and that the local run was on Python 3.11 while CI runs 3.12.
