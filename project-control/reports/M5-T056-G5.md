- **(d) No other uncapped reflection of caller input in this route — NO. See G5-1.**

### G5-1 (MEDIUM, advisory — pre-existing, out-of-literal-scope): the sibling `message` field defeats the cap's stated goal

The 422 branch also emits `"message": payload["message"]` **uncapped** (condo_records.py:592). `payload["message"]` is the `BBLValidationError.message`, which for three error codes embeds the caller-supplied value at unbounded length:

- `non_numeric` → `f"BBL {text!r} contains non-numeric characters"` (bbl.py:106) — `text` = stripped input.
- `wrong_length` → `f"BBL must be exactly 10 digits; got {len(digits)} digits ({digits!r})"` (bbl.py:137) — for an all-numeric input of length N, `digits` = ~N chars, embedded verbatim.
- `non_integer_decimal` → `f"BBL {text!r} has a non-zero fractional part"` (bbl.py:113).

The BBL is a URL path segment (`/properties/{bbl}/condo-records`, condo_records.py:564), so a caller can send e.g. `9`×5000 and receive a 422 whose `raw_value` is capped at 256 **but whose `message` still echoes ~5000 chars**. This directly contradicts rider (h)'s own stated intent (condo_records.py:135-141: "a hostile or oversized entered value must never let the echoed repr flood the error body"). The producer's own end-to-end test (`test_422_oversized_bbl_raw_value_is_length_capped`) asserts only `state`, `detail.code`, and `detail.raw_value` — it never checks `message` length, so the gap is untested.

**Severity rationale (MEDIUM, non-blocking):**
- **Pre-existing, not introduced here.** At 5b7b4b30^ the 422 branch already emitted `"message": payload["message"]` uncapped and `"raw_value": payload["raw_value"]` uncapped; this commit only *added* the raw_value cap. M5-T056 introduces no new reflection and no regression.
- **No injection / no real amplification.** The reflected content is `repr()`-escaped, JSON-encoded server-side, and React-escaped on the web (no `dangerouslySetInnerHTML` — verified). Response body grows ~1× the input (not a DoS force multiplier).
- **Route is fail-safe-disabled by default** (`internal_rule_eval_enabled()` guard first, generic 404 when off; `include_in_schema=False`; internal/dev only).
- **Web consumer re-bounds it:** the client renders the 422 message through `boundedText(record?.message, …)` capped at 600 chars (condo-records.ts:493-496), so the accessibility-tree concern is mitigated web-side.
- **Literal packet scope is satisfied** (AS-6 = raw_value cap only), and the message text is constructed in `services/api/app/connectors/bbl.py`, which is in this packet's **forbidden_paths** — a complete fix belongs to a connector-touching follow-up.

**Remediation (recommend as a D-069 discovery / next-packet item, not a gate blocker):** either bound `payload["message"]` with the same length cap inside condo_records.py (in-scope, one line, keeps ordinary bodies byte-identical since ordinary messages are short), or bound the value-embedding f-strings at their source in `app.connectors.bbl` under a follow-up packet. Reproduction: `GET /api/v1/properties/9999…(N≫256)…/condo-records` with the flag on → 422 `detail.raw_value` length 256+marker, but `message` ≈ N+ chars.

**Item-1 ruling: the raw_value cap itself is correctly and airtightly applied (a/b/c PASS); the route is NOT free of uncapped caller-input reflection (d) because of the pre-existing `message` echo.**
