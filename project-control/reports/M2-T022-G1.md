## Findings by severity

### HIGH-1 — Production default resolver rejects the route's positional call; endpoint 500s on every real request (packet S1–S6 unmet in production; masked by the test seam)

The route calls the resolver with `house_number` and `street` **positionally** (`address_resolution.py:401-406`):

```python
outcome = resolver(
    house_number,
    street,
    borough=borough if borough else None,
    zip_code=zip_code if zip_code else None,
)
```

The production dependency returned by `get_address_resolver()` is `_default_resolver`, which accepts **keyword arguments only** (`address_resolution.py:228-231`):

```python
def _default_resolver(**kwargs) -> AddressResolution:
    return resolve_address(**kwargs)
```

Calling a `**kwargs`-only function with two positional args raises `TypeError: _default_resolver() takes 0 positional arguments but 2 were given`. That TypeError is swallowed by the generic `except Exception:` guard (`address_resolution.py:439-445`) and returned as HTTP 500 `internal_error`. `resolve_address` is never reached, so the failure is unconditional (independent of key, network, or input).

Reproduced at HEAD `ec4b75dc` (offline, production wiring, `dependency_overrides` cleared, `INTERNAL_RULE_EVAL_ENABLED=1`, sentinel key set so key-missing is excluded, egress seams blocked to prove no network is reached):

```
default resolver is _default_resolver: True
DIRECT CALL TypeError: _default_resolver() takes 0 positional arguments but 2 were given
ROUTE (prod wiring) code: 500 state: internal_error
```

Why the pack does not catch it: every test replaces the seam with a fake whose signature *does* accept positionals — `install_resolver_for_body` / `install_raising_resolver` / S7 all register `_resolver(house_number, street, *, borough=None, zip_code=None, **kwargs)` (lines 124, 151, 559; `app.dependency_overrides[get_address_resolver] = ...` at 144, 155, 565). No test ever exercises `_default_resolver` or the real `get_address_resolver()` contract. The override contract diverges from production, so S1 "resolved_end_to_end", S2, S3, S4, S5-set, and S6 all pass against a fake while the real endpoint is inert. This is exactly the masked/vacuous failure class the packet risks call out.

Required correction (producer's to make): make the production dependency match the route's call contract — e.g. `def _default_resolver(house_number, street, *, borough=None, zip_code=None): return resolve_address(house_number, street, borough=borough, zip_code=zip_code)` (still no `budget=`, preserving C4 duty 3) — and add a test that exercises the real `get_address_resolver()` path (with `app.api.v1.address_resolution.resolve_address` monkeypatched, or the connector's `transport` seam overridden as the packet S1 input actually specifies) so production wiring is covered.

### LOW-1 — STATUS_STATE_MATRIX omits a pair the error handler can actually emit; matrix comment is inaccurate about it

`RequestBudgetExceededError.error_type == "request_budget_exceeded"` is a `GeoclientConnectorError` subclass, so if it were ever raised it would be caught by the `except GeoclientConnectorError` handler and mapped via `_ERROR_STATUS.get(state, _DEFAULT_ERROR_STATUS)` → `(503, "request_budget_exceeded")`, which is **not** in `STATUS_STATE_MATRIX`. Probe confirms:

```
RBE-edge code 503 state request_budget_exceeded inMatrix False
```

This is unreachable in production because the route passes no budget (correct C4 duty 3, pinned by S8), so it is LOW, not a functional defect. However the matrix comment (`address_resolution.py:154-156`) and module docstring claim "the generic internal_error guard would still type it if that ever changed" — that is wrong: it would be the connector-error handler emitting an undocumented `(503, request_budget_exceeded)` pair, not a `(500, internal_error)`. Note also HIGH-1 makes this doubly moot today. Recommend either adding the pair to the matrix (documented as unreachable) or correcting the comment.

### LOW-2 (informational) — flag-off generic 404 is an emission path outside the matrix

`_not_found()` returns `404 {"detail":"Not Found"}` with no state and no correlation header (verified: `flagoff code 404 body {'detail': 'Not Found'} corr-absent True`). This is deliberate and correct (indistinguishable from an unmounted route, fail-safe disable, checked before any correlation id is minted). It is called out only because `STATUS_STATE_MATRIX` is documented as "the single source of truth for every emitted (HTTP status, state) pair"; the 404 is intentionally outside that typed space. No change required; wording is slightly overbroad.
