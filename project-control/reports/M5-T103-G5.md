FINDING 1 — HIGH, BLOCKING. Unbounded predictor buffer bypasses the mandatory memory guard.
- Where: sheet_objects.py:384 `previous = bytearray(row_len)`; row_len from apply_predictor sheet_objects.py:360-366 with NO upper bound on /Columns, /Colors, /BitsPerComponent; invoked for EVERY xref/object stream carrying /DecodeParms via pdf_object_streams._decode_stream:665.
- Mechanism: when a stream decodes to EMPTY bytes, the row-alignment guard sheet_objects.py:381 `len(data) % stride != 0` passes (0 % anything == 0), so `bytearray(row_len)` allocates an attacker-chosen size BEFORE any byte is materialized. The mandatory inflated-bytes cap (8 MiB) and the shared decoded budget do NOT cover this working buffer — it is sized by /Columns, not by decompressed length. Empty decoded is reachable two ways: a tiny flate stream that inflates to b"", or /Length 0 with no /Filter.
- Proven end-to-end: resolve_object_table() on a 198-byte crafted cross-reference-stream PDF (empty-inflating stream + /DecodeParms << /Predictor 12 /Columns 50000000 >>) → tracemalloc PEAK 50,004,634 bytes (6x the 8 MiB cap), returns SheetRefusal only AFTER the alloc. /Columns in the billions → GB-scale → OOM. Unit probe apply_predictor(b"", cols=50M) → same 50 MB, returns bytes (no refusal).
- Also: this falsifies resolve_object_table's "Never raises" docstring (a large row_len raises MemoryError); today it is caught only by read_sheet's top-level backstop, and a moderate 1-2 GB alloc can succeed and OOM the worker rather than raise cleanly.
- This defeats the packet's central mandatory criterion (AS-2 / M5-T099 G5 F2(a): cap + charge BEFORE materialization on every xref/object stream). The predictor buffer is an uncharged, unbounded materialization.
- Fix: bound row_len/stride against the absolute cap (and charge it) BEFORE allocating; return b"" for empty data before touching row_len; reject oversized /Columns·/Colors·/BitsPerComponent geometry as a typed refusal.

FINDING 2 — MEDIUM, ADVISORY. Object-count cap enforced too late (memory amplification).
- Where: pdf_object_streams._collect_stream_entries:253-287 merges entries into entries_map/seen (lines 277-282) with NO running cap; the MAX_PDF_OBJECTS=4096 check is only in _materialize:497, after the whole /Prev chain is collected.
- Mechanism: each xref stream may declare up to MAX_XREF_ENTRIES=131072 entries, /Prev chain up to MAX_PREV_DEPTH+1=33 hops → up to ~4,325,376 distinct entries accumulate before the 4096 cap trips (~1000x the intended object ceiling; exceeds the 128 MB decoded budget too).

- Fix: enforce MAX_PDF_OBJECTS incrementally inside _collect_stream_entries as seen/entries_map grow; refuse the moment distinct in-use entries exceed the cap.

FINDING 3 — LOW, ADVISORY. _png_unfilter is pure-Python per-byte (Average/Paeth inner loops sheet_objects.py:392-406); worst-case predictor CPU scales with the 128 MB shared budget → tens of seconds/doc.
