**File:** `project-control/reports/M2-T021-evidence-map.json:10`

### 5. HIGH — `response_digest` is emitted without `digest_canonicalization`, breaking the accepted house pattern
**File:** `services/api/app/connectors/geoclient_address.py:561`

Every sibling connector that emits a canonical digest also records the spec needed to recompute it: `mappluto_geometry_arcgis.py:1898`, `zoning_features_arcgis.py:1346` and `:1626`, `ztldb_soda.py:919`/`:940`, `profile/builder.py:789`. The accepted contract schema says so explicitly (`app/_contract_schemas/v1/common.schema.json:52`: the canonical form is *"recorded verbatim per profile in reproducibility.digest_canonicalization"*). The Geoclient provenance block (lines 551–563) carries the digest alone.

**Consequence:** a consumer holding an `AddressResolution` cannot verify or recompute the digest from the record, and when a follow-up packet feeds this provenance into a property profile's `reproducibility` block — the field's stated purpose — the profile will carry a digest stripped of its spec.

**Fix:** one line — add `"digest_canonicalization": CANONICALIZATION_SPEC` (already importable from `pluto_soda`).

### 6. MEDIUM — empty string is silently reinterpreted as absence
**File:** `services/api/app/connectors/geoclient_address.py:340-342`

`_string_or_none` returns `None` when the source emitted `""`. The null-omission rule in research section 2.5 and in the module's own docstring covers *omitted* fields; it says nothing about empty values. So if Geoclient ever emits `bbl: ""`, a caller reading `res.bbl is None` concludes "the source omitted BBL" when the source actually sent a value. This is the mirror image of the fabrication rule the packet's S8 guards.

**Mitigations:** `raw_fields` still carries the true `""`, and I confirmed none of the three fixtures contains a single empty-string field, so there is no observed impact today. No test covers the case.

**Fix:** preserve `""` verbatim, or document the coercion in the module docstring and the registry record.

### 7. MEDIUM — provenance completeness is asserted on only one of six outcome statuses
**Files:** `services/api/app/connectors/geoclient_address.py:551-563` vs `services/api/tests/connectors/test_geoclient_address.py:121-142`

The packet requires provenance with both GRC codes on *every* outcome. The code builds it unconditionally, so this holds structurally, but the only test that checks it (`test_s1_provenance_is_complete_and_key_free`) runs the `resolved` path. Nothing asserts provenance on `ambiguous`, `rejected`, `not_found`, `resolved_with_warnings`, or `unrecognized_status` — including the interesting case where `unrecognized_status` puts `None` into both `geosupport_return_code` fields.

**Consequence:** the packet's "every outcome" clause is verified by reading the code, not by the suite, so a future refactor that moved provenance under a status branch would pass green.

### 8. MEDIUM — GRC `50` and `75` are documented ambiguity classes but are classified `rejected`, and their suggestions are suppressed
**File:** `services/api/app/connectors/geoclient_address.py:112, 549`

The research doc's own heading "Ambiguity signals (official GRC meanings, UPG Appendix 4)" lists five codes: `11`, `EE`, `50` ("IS AN INVALID STREET NAME FOR THIS LOCATION", with *"reason code indicating how many valid alternatives exist"*), `75`, and `63`. `_GRC_AMBIGUOUS` contains only `EE`. Because `_extract_suggestions` runs solely when `status == "ambiguous"` (line 549), a GRC 50 response carrying a street list is returned as a plain rejection with `suggestions == []`.

**Consequence:** a user who types a street that is real but wrong for that location gets "rejected" and no alternatives, even when the city returned them.

The packet's S3 names only EE and 11, so the producer built to contract — but neither the producer report's "Honest limits" nor the registry record discloses the narrowing.

### 10. MEDIUM — `raw_fields` is the live parsed dict, aliased, and the digest that attests to it is defenseless against mutation
**File:** `services/api/app/connectors/geoclient_address.py:522, 550`

`address = parsed["address"]` and `raw_fields=address`: the returned object is the *same* dict, not a copy. `provenance["response_digest"]` is computed over `parsed`, which contains that dict by reference. Since the digest is computed at construction, it is correct at return time — but any caller that mutates `outcome.raw_fields` silently invalidates the outcome's own digest, with nothing to detect it. `request_params` is defensively copied on line 554; `raw_fields` is not.

**On the round-trip question:** I confirmed all three fixtures parse without duplicate keys, round-trip exactly at parse level, and that all four G01 floats re-serialize to literals identical to those in the raw body — so the 171 fields do survive intact, and `canonical_json_digest` is deterministic over them.
