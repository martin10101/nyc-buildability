### L-1 (LOW) — an error body names an environment variable, which AS-5 forbids verbatim

**Where:** emitted by `services/api/app/api/v1/evidence.py:426-437`, transporting
`PlutoConnectorError.to_payload()["message"]`, whose text is fixed at
`services/api/app/connectors/pluto_soda.py:507-510`.

**Observed (probe D14):**

```
503 rate_limited -> {"state":"rate_limited","message":"SODA throttled the request (HTTP 429) and
the retry budget is exhausted; configure SOCRATA_APP_TOKEN to leave the shared tokenless pool", ...}
```

AS-5 states: "no error body contains a traceback, filesystem path, secret, **env var name** or
internal implementation string." This body contains an env var name.

**Exploit scenario and honest impact:** an unauthenticated caller who reaches the endpoint while SODA
is throttling learns the string `SOCRATA_APP_TOKEN`. That is a public Socrata convention; the same
body already discloses `source_id: nyc-dcp-pluto-soda` and the dataset URL; and the **value** never
leaks — proven by canary probe (section 4.2): with `SOCRATA_APP_TOKEN`, `SUPABASE_SERVICE_ROLE_KEY`,
`GEOCLIENT_SUBSCRIPTION_KEY` and `ANTHROPIC_API_KEY` all set to canary values, no canary appears in
any response body or header, and the 200 body is byte-for-byte the same size whether a token is
configured or not (no length oracle). Practical severity is negligible; what is real is that a stated
acceptance criterion is not literally met.

**Inherited, not introduced — verified (probe D15):** the identical string is emitted by the accepted
`/properties/{bbl}`, `/properties/{bbl}/rule-evaluation`, `/properties/{bbl}/scenario` and
`/scenario/sensitivity` routes on the same 429 fixture. Its source file is a **forbidden path** for
this packet, so the producer could not have fixed it inside `allowed_paths`.

**Recommendation (not for this packet):** either reword the connector hint to drop the variable name
(e.g. "configure a Socrata application token"), or amend the shared clause to forbid secret **values**
and non-public configuration identifiers. Route it through the queued connector cleanup task, not a
forbidden-path edit here.

### L-2 (LOW) — the 422 reflects the raw BBL twice; bounded only by the request-line limit

**Where:** `evidence.py:404-413` forwards `payload["message"]` and `detail.raw_value` from
`BBLValidationError.to_payload()` (`app/connectors/bbl.py:57-64`, `repr(raw_value)`, unbounded).

**Measured (probe D5b):**

| raw BBL length | 422 body | factor |
|---|---|---|
| 10 | 200 B | x20 |
| 1,000 | 2,180 B | x2.18 |
| 10,000 | 20,180 B | x2.02 |
| 40,000 | 80,180 B | x2.00 |

**Exploit scenario:** a caller sends a long junk BBL and receives ~2x that many bytes back, repeatable.
It is self-reflection only (the attacker sees their own input), the value is JSON-escaped, and it is
capped in production by the server's request-line limit. **Safety checks all pass:** with a
`%0D%0A` / `%00` / quote / backslash payload the 422 body contains **no raw CR, LF or NUL byte**,
parses as JSON, and no injected header appears (`X-Injected` absent on every probe). Inherited verbatim
from `bbl.py` (forbidden path) and identical in the accepted routes; I raised the same item in the
M5-T012 review. Backlog alongside the other `bbl.py` item.

### Advisory observations (not findings)

- **BBL canonicalisation is lenient by design.** ` 1000010100 `, `1000010100%0A`, tab-wrapped,
  `%0D%0A`-wrapped and the Socrata decimal form `1000010100.00000000` all normalise to `1000010100`:
  **200**, `doc.bbl == "1000010100"`, document byte-identical to the canonical request (probe D6). The
  fetcher receives the canonical string and the outbound URL is `...?bbl=1000010100` in every case, so
  there is no request-splitting, SSRF or outbound-injection consequence. Relevant only if an HTTP cache
  is ever placed in front of this service, since several distinct URLs map to one response. Inherited
  from `bbl.py`.
- **Probe artefact, explicitly not a finding.** My first BBL sweep showed two `500 internal_error`
  results (trailing-newline and space-wrapped BBLs). Those two inputs *pass* validation and reach the
  fetch stage, where my **landmine** fetcher raises by design; the route correctly typed that as
  `(500, internal_error)`. Re-run with a real fetcher they are 200s (above). Recorded so the transcript
  is not misread as a defect.
- **The AS-6 surrogate mechanism is two-layered, and only one layer is the new check.** An unpaired
  surrogate arriving in official source data never reaches the assembler: the connector's
  `canonical_json_digest` raises `UnicodeEncodeError` at `app/connectors/pluto_soda.py:255` during the
  fetch, which the route types as `(500, internal_error)` (probe D8). `_assert_json_safe`'s second form
  is nonetheless load-bearing — proven directly on a real assembled document and by RED run
  (section 4.6) — and would be the only defence if a future non-SODA seam supplied surrogates without a
  digest step. Worth a sentence in the module docstring so nobody later "simplifies" the check.
- **Flag blast radius grew by one surface in the e2e harness.** `apps/web/e2e/harness/fixture_api.py:250`
  sets `INTERNAL_RULE_EVAL_ENABLED=1` and imports the real `app.main:app`, so the evidence route is now
  reachable in that local Playwright process too. Zero security impact (localhost fixture API, fixture
  data, test-origin CORS), but the harness comment naming only "the internal rule-evaluation endpoint"
  is now slightly stale. `apps/web/**` is a forbidden path here; noted for whoever owns it.

## 3. Ruling 1 — is reusing `internal_rule_eval_enabled` the right flag choice?

**Ruling: yes, and it is the better choice than either a new flag or the scenario flag.**

1. **The two surfaces are one disclosure decision.** This endpoint publishes nothing except the
   provenance *behind the very document that flag already governs*. Gating them separately produces two
   incoherent states: evidence-on/rule-eval-off would publish the audit trail for a conclusion the
   operator has chosen not to expose, and rule-eval-on/evidence-off is the status quo the packet exists
   to end (conclusions with no way to check them). One switch matches one decision.
2. **My M5-T012 "one token, several surfaces" concern does not transfer.** There the objection was
   specific: one token opened both a body-less GET *and four body-accepting POSTs* — two different
   threat models under one switch, so flipping it for the GET silently exposed an untrusted-input
   boundary. Here both surfaces under the token are body-less GETs over the same server-side rebuild
   with a structurally zero untrusted-input surface (section 4.1). The blast radius stays homogeneous,
   which is the property that makes flag reuse safe rather than a smell.
3. **Isolation verified, not assumed (probe D9b).** With `INTERNAL_SCENARIO_ENABLED=1` and the
   rule-eval flag off, the evidence route returns **404** — the wrong flag cannot open it. The two
   internal domains remain independently gated, so reuse did not collapse them into one switch.
4. **It satisfies the hard constraints:** `config.py` is byte-unchanged, no new flag exists, and the
   enabling-token semantics are exactly the shared helper's (`1/true/yes/on`, case- and
   whitespace-insensitive; absent/empty/unknown -> off).

**One recommendation:** the flag's comment in `config.py` still describes it as gating the
rule-evaluation endpoint. When that file is next legitimately touched, note that it now governs two
routes, so an operator flipping it knows the full surface. Not actionable here (`config.py` is
forbidden), and not a defect.

### 4.6 AS-6 fail-closed serialisation — implemented, or recited? (probes D7, D8)

**(a) Hostile content driven through the injected PLUTO seam** (the real connector → profile → rules →
assemble path, not a patched assembler). Every case typed, in-matrix, with a correlation id,
`application/json`, and **never an untyped text/plain 500**:

| Injected into the official response body | Result |
|---|---|
| clean fixture (control) | 200, both `json.dumps` forms OK |
| unpaired surrogate in `address` / in `ownername` / in a **field name** | 500 `internal_error` |
| bare `NaN` / bare `Infinity` / `1e400` numeric | 500 `internal_contract_error` |
| string `"NaN"` / `"Infinity"` / `"0"` / `""` / 4300-digit numeric string | 200, both forms OK (quoted text transported verbatim; no bare NaN token, no ZeroDivisionError) |
| 4300-digit **bare** int | 500 `internal_error` |
| malformed JSON body / empty body | 503 `source_unavailable` |
| JSON object instead of array | 502 `schema_drift` |

**(b) A forced raise in every stage** (in-memory patch; repo untouched) — all nine typed, in-matrix,
`application/json`, with a correlation id, and **zero leakage** of the planted
`"secret-internal-path C:\hostile\n::injected"` (`leaks=[]` in every row: no `hostile`, no
`secret-internal-path`, no `Traceback`, no `File "`):

```

rebuild: build_property_profile             -> 500 internal_error
rebuild: evaluate_property                  -> 500 internal_error
rebuild: serialize_rule_evaluation          -> 500 internal_error
rebuild: validate_profile                   -> 500 internal_error
rebuild: validate_rule_evaluation_document  -> 500 internal_error
assembly: assemble_evidence_document        -> 500 internal_error
serialisation: _assert_json_safe            -> 500 internal_contract_error
substrate provider raises                   -> 500 internal_error
```

**(c) Is the two-form check load-bearing, and which form catches what?** Tested directly on a real
assembled document:

| Mutation | `allow_nan=False` | `ensure_ascii=False` + `.encode("utf-8")` | `_assert_json_safe` |
|---|---|---|---|
| unpaired surrogate | **passes** | **raises UnicodeEncodeError** | caught |
| NaN | raises ValueError | raises ValueError | caught |
| Infinity | raises ValueError | raises ValueError | caught |

Each form catches a class the other misses, exactly as the criterion states — and the
surrogate / `allow_nan=False` row is the precise disagreement that was M5-T012's BLOCKING-1.
End-to-end, non-finite content reaches the assembler and is caught by the first form
(`internal_contract_error`), while surrogates are stopped earlier by the connector digest
(`internal_error`) — both typed.

**(d) RED: is the 200 return inside the guard?** With `_assert_json_safe` neutralised to a no-op,
surrogate content still produced `500 internal_error` with `application/json` and a correlation id —
because `return _json(200, evidence, correlation_id)` (`evidence.py:512`) sits **inside** the `try`
whose `except Exception` is at `:513`. A render raise therefore cannot escape even if the pre-send
check is bypassed. That is strictly stronger than the structure M5-T012 shipped with, and it is the
specific defect class my earlier finding was about.

**(e) RED: are the producer's tests load-bearing, or would a regression slip through?** Using an
in-memory plugin that neutralises one guarantee at a time (repo never modified); GREEN baseline is
37 passed:

| Neutralised | Result |
|---|---|
| `_assert_json_safe` -> no-op | **3 failed** (surrogate, NaN, infinity) |
| `_assert_json_safe` -> **only** the `allow_nan=False` form (exactly the M5-T012 mistake) | **1 failed** — the `unpaired_surrogate` case |
| `_verification_status` -> always `"verified"` | **4 failed** (AS-7 + AS-5) |
| assembly rounds caps and truncates citation quotes | **2 failed** (AS-1 + AS-2 byte-equality) |

The second row is decisive: the suite **discriminates the two forms**, so a future "simplification"
back to one form would be caught. The criteria were implemented and are regression-protected.

## 5. Ruling 2 — the no-authentication position for *this* endpoint

The service still has **no authentication** (`app/main.py` docstring; M0-T007/T008 blocked on the
Supabase credential), and the feature flag is the only containment. Restated for this endpoint, with
the differences from the M5-T012 POSTs made explicit:

1. **Containment today is real.** The flag is fail-safe for all nine non-true token variants
   (byte-identical 404, no correlation id, no body read, rebuild never reached), it is **not declared in
   `render.yaml` or any CI workflow**, and the wrong flag cannot open the route. In every deployed
   environment this endpoint is indistinguishable from an unmounted path.
2. **The amplification concern from M5-T012 does *not* transfer in its dangerous form.** There the
   objection was a *caller-steered* multiplier (a 2 KB body selecting 256 candidates -> 925 KB, x437).
   Here there is no caller-controlled dimension at all: response size is a function of the property's
   official record only. Measured: 64 B request -> 59,561 B response (x930) at a 239 ms median. For
   calibration, the **already-accepted and completely ungated** `/api/v1/properties/{bbl}` returns
   **74,804 B in 206 ms** on the same property. So this endpoint introduces no new amplification class
   and is smaller than the unauthenticated surface that already exists.
3. **What it *does* newly expose is audit value, not secrets.** The evidence trail is the
   highest-signal read surface in the service for an adversary doing reconnaissance on *how* the
   product reasons (rule ids, rule versions, lifecycle statuses, snapshot ids, coverage vocabulary).
   None of that is a credential or a path, and all of it is intended to be legible — but it is the
   surface where "read-only" and "harmless" diverge most, which is why the flag should stay off until
   auth lands.
4. **What this endpoint needs when auth arrives:** (a) authentication **and** authorisation, with
   access logging — a provenance/audit view is exactly where "who looked at this" matters; (b) a
   per-caller rate limit shared with the other property routes rather than an endpoint-specific one,
   since its cost profile is the same flat ~240 ms rebuild; (c) **nothing body-related** — there is no
   body, no query parameter and no header input, so none of M5-T012's input-boundary hardening has an
   analogue here. The M1-T005 G5 condition (service must not be publicly exposed until the
   auth/organisation layer lands) stands and I re-affirm it.

## 6. The out-of-scope `B905` question (asked; here is my view)

There are exactly **two** `zip()`-without-`strict=` instances in the repo:
`services/api/app/scenario/breakeven.py:535` (product) and
`services/api/tests/scenario/test_scenario_comparison.py:162` (test).

The product one is the adjacent-pairs idiom:

```python
for (raw_lower, lower), (raw_upper, upper) in zip(derivable_rows, derivable_rows[1:]):
```

The two operands differ in length by one **by construction**. So this is a real fail-closed question,
not cosmetics, and the answer is asymmetric:

- **`strict=True` would be a security regression**, not a fix: it raises `ValueError` for every
  non-empty `derivable_rows`, turning a documented fail-closed crossing scan into an all-inputs crash —
  reachable from the accepted `POST .../scenario/threshold` endpoint, i.e. exactly the "a boundary that
  must never raise, does" class that was M5-T011's and M5-T012's blocking defects.
- **Ruff's autofix is safe** — I previewed it read-only (`ruff check --diff`, no write; worktree
  verified unchanged) and it inserts `strict=False`, which is behaviour-preserving.
- **But a blind `ruff --fix` trades one error for another:** the fixed line becomes ~107 characters
  against this repo's `line-length = 100`, so it would introduce `E501`.
- **Cleanest fix:** `itertools.pairwise(derivable_rows)` — it expresses the intent, removes the length
  question entirely, and stays inside the line limit.

For whoever reviews that cleanup task, I would require: no `strict=True` on a pairwise idiom; the 388
scenario tests re-run green; and a line-length re-check after the fix.
