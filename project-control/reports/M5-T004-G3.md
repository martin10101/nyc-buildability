## VERDICT: FAIL

---

## Summary

The Compare screen is well-built defensively — every documented `(status, state)` pair has its own honest card, nothing partial renders from an unvalidated body, no state is a dead end, and the announcer/focus wiring is correct and single-fire.

It fails on **honesty-as-experienced**, not on plumbing: the document's own `data_completeness` (`missing_critical` in all three shipped fixtures) and its own `reasons` caveat are both dropped on the exact path that renders a bold 15,000 sq ft number; the CSS class carrying every draft/review warning does not exist in any stylesheet; and the screen silently diverges from the Property/Confirm heading and loading-region conventions. Additionally **no test of any kind was ever executed and no browser-level walkthrough was possible**, which G3 explicitly requires for UI work.

---

## Findings

**1. HIGH — the document's own `data_completeness` is never rendered; Compare shows a number for a property it knows has missing critical inputs.**
Belongs at `ScenarioResult.tsx:164-176` (the summary card). Grep across `components/compare/` finds only `constraint.data_completeness` (`ScenarioCard.tsx:112`); the top-level `Scenario.data_completeness` (`packages/contracts/generated/scenario.ts:75`) renders nowhere. All three committed fixtures carry `"data_completeness": "missing_critical"`, including `preliminary_r5_cap.json`, the one producing the 15,000 sq ft cap. `lib/coverage.ts:71-76` already holds the exact copy: *"Critical official inputs are missing — At least one field classified critical is missing from the official record. Feasibility conclusions cannot be complete without it."*
**User-visible consequence:** a user walking Property → Confirm → Compare for the same BBL is told in a bordered banner on Step 1 (`PropertyLookup.tsx:97-112`, `CompletenessBanner`, `role="status"`) that critical inputs are missing — then on Step 3 is shown a bold number and never told again. **The screen's most quantified claim is the one place the completeness caveat disappears.**
*Fix:* render `completenessDisplay(document.data_completeness)` in the summary card above the cap, using the same `completeness-banner` treatment the property screen uses.

**2. HIGH — `document.reasons` silently dropped on the preliminary path and replaced by hard-coded client prose.**
`ScenarioResult.tsx:49-53` renders `document.reasons` only inside `NoScenarioBlock`; `:178-182` routes `scenario_kind === "preliminary"` to `ScenarioCard`, which never touches `reasons`. The backend emits a reason on the preliminary path too (`services/api/app/scenario/builder.py:536-543`): *"Preliminary scenario: surfaced the canonical draft residential zoning-floor-area cap (ZR 23-21) from the rule_evaluation trace, verbatim. NOT a buildable envelope - see the coverage matrix for the rule families still MISSING."* In its place, `PracticalRangeBlock` (`ScenarioResult.tsx:85-100`) hard-codes prose that happens to say something similar today.
**User-visible consequence:** the engine's own explanation of what the number is and is not is discarded on the only screen showing a number, and the client substitute cannot track the server. Any reason the backend adds later — a substituted input, a narrowed applicability — is swallowed with no UI change and no test failure. Same defect class as the silent projection that failed M5-T013 at G1.
*Fix:* render `document.reasons` on the preliminary path; delete or demote the duplicated static prose so the server text is the source of truth.

**3. HIGH (gate-level) — no browser walkthrough of this screen exists or is possible anywhere in the repository.**

> **CORRECTION (recorded 2026-09-11, reviewer-initiated).** This finding was first reported in two parts. **Part (a) — "no test was ever executed" — was wrong and is withdrawn.** `compare-screen.test.tsx` runs under `npm run test` at `ci.yml:96` in the `web-e2e` job, so the component suite **did** execute and passed. The error came from conflating "no *reviewer* could execute tests locally" (true — `apps/web/node_modules` is absent everywhere under the thin-client policy) with "the tests never ran" (false — CI ran them).

**Part (b) stands, and is sharper than first stated.** `web-e2e` green covers 18 Playwright specs, **none of which navigate to `/property/compare`** (`grep -rln "compare" apps/web/e2e/` returns nothing). Further, the e2e harness `fixture_api.py` enables `INTERNAL_RULE_EVAL_ENABLED`, **not** `INTERNAL_SCENARIO_ENABLED` — so **no browser can reach this screen anywhere in the repository today**, in CI or locally.

G3's definition requires real browser interaction for UI work. G3 therefore discharges 7 of its 8 steps; step 3 is owed and cannot currently be discharged by anyone.

**Recommendation: do NOT hold the FAIL on this.** The rework is already required by findings 1, 2, 7 and 14, all of which are code-read and independent of test execution. Instead **fold into the rework scope**: extend `fixture_api.py` to enable `INTERNAL_SCENARIO_ENABLED`, and add a `compare-journey.spec.ts`. CI is the only place this step can ever be discharged, so the capability has to be built there.

Separately recorded for orchestrator follow-up: an undefined CSS class (finding 4) fails neither typecheck nor lint — confirmed independently by G4 — which is precisely the defect class a walkthrough exists to catch.

**4. HIGH — `.status-label` has no rule in any stylesheet; every draft/review warning renders unstyled.**
The class carrying the draft and review-required warnings is applied in the compare components but defined nowhere. Searched the full stylesheet set (`apps/web/src/app/globals.css`, `dashboard/dashboard.css`, `survey/review/survey-review.css`, and all component-adjacent CSS) — no rule exists.
**User-visible consequence:** the warning text is present in the DOM and legible, but carries **no visual differentiation whatsoever** — no color, weight, border, or background. It reads as ordinary body copy sitting next to a bold, tabular-numeral 15,000. Severity is **undifferentiated, not invisible** — the text is readable, so this is not a CRITICAL disappearance, but on a product whose core claim is honest labelling, the honesty label having no visual weight while the number has maximum visual weight is a material defect.
*Ironic interaction:* the absence of this rule is also what makes AS-1/AS-3's "not color-only" requirement pass trivially — there is no color to encode anything with.
*Fix:* define `.status-label` with a treatment at least as prominent as `.fact-value`.

## On the two clauses specifically checked

**"Not color-only" (AS-1, AS-3) — PASSES, more strongly than required.** Checked rather than assumed: the cap uses `.fact-value` (`globals.css:322` — `font-variant-numeric: tabular-nums; font-weight: 600`, no color); `.status-label` has no rule anywhere, so it cannot carry color; the coverage legend deliberately avoids `CoverageBadge` and renders `<code>{symbol} {value}</code>` (`CoverageMatrixSection.tsx:63-69`) with non-color symbols (`✓ ◐ ! ≠ ∅ —`, `coverage.ts:22-47`). No `.status-verified`-family node exists anywhere in the compare tree — the S7 invariant the producer claims is genuinely upheld. Every status prints its exact enum value as text.

**"Preserved share ranges, never collapsed" (AS-2) — the numbers PASS; their qualifiers do not.** `ScenarioResult.tsx:60-74` prints all three bounds per candidate ("share range min 0.4 / point 0.55 / max 0.7"); both R5 and R6 render; `minor_portion: true` surfaces as "(minor portion)". No averaging, no point-estimate substitution, no dropped candidate. The clause passes. The dropped items are the *qualifiers* (F14/F15), not the ranges.
