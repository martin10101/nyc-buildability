## Findings

**F1 — [Major] Heading-order inversion on the composed flag-on page (a11y document outline).**
On the shipped `/property` page (app/property/page.tsx:34 has no page-level h1; InternalBanner is `role="note"`), the address front door renders an `<h2>` *before* the page's only `<h1>`:
- AddressResolutionScreen.tsx:704 — `<h2 className="section-title">Address lookup</h2>` (first heading on the page)
- PropertyLookup.tsx:267 — `<h1 className="section-title">Property lookup</h1>` (the BBL fallback, appears second)

A screen-reader user navigating by headings lands on an h2 first, and the page's h1 is the *secondary* BBL fallback rather than the intended primary address surface. This inverts the document outline (WCAG 1.3.1 / 2.4.6 best practice) and mis-ranks the primary action. Both files are in `allowed_paths`; fixable by promoting the address surface heading (or restructuring the levels) without touching the flag-off byte-equivalent DOM (address surface is unmounted when the flag is off, so S1 is unaffected). **Required correction.**

**F2 — [Minor] Focus drops to `<body>` during suggestion re-resolution.**
`onPickSuggestion` (AddressResolutionScreen.tsx:620-632) does not set `retryFocus`, so when "Use this address" unmounts as the ambiguous card is replaced by the `ResolvingCard`, focus falls to `<body>` for the duration of the re-query, then jumps to the outcome heading on arrival. The retry path (lines 634-641) deliberately prevents exactly this drop by setting `retryFocus`. The pick path should do the same for parity with the spec's "never dropping to `<body>`" rule (section 5). Transient and self-correcting, hence Minor.

**F3 — [Minor] `invalid_input` card omits the spec's "points at the field" recovery.**
AddressErrorCard (AddressResolutionScreen.tsx:451-457) renders the connector's message honestly but provides no affordance back to the form — no edit button, no focus move, no `aria` linkage to the offending field — unlike not_found/rejected which offer `RecoveryActions`. The form persists above so it is not a hard dead end, but the spec section-2 posture ("Points at the field") and the "edit and resubmit" recovery are not realized for the one error whose fix is on the user's side.

**F4 — [Minor] Modularity boundary divergence from the reference flow.**
AddressResolutionScreen.tsx is ~725 lines and bundles ~15 presentational outcome-card components plus the state-machine host in a single file, whereas the reference property flow separates its cards (FailureState.tsx) from its host (PropertyLookup.tsx). CI `modularity_check` passes and the file is cohesive, but it is past the 600-line warn threshold; extracting the cards into an `AddressOutcomeCards` module would match the established boundary and keep the host lean. Advisory.

**F5 — [Minor / observation] Competing primary actions on the flag-on page.**
Two equal-weight `primary-button` actions coexist ("Resolve address" and "Look up property"), plus the disabled "Continue with this lot" stub — a mild five-second-hierarchy competition. This is the sanctioned transitional design (the BBL form is retained as fallback and as the `#bbl-input` recovery target), so it is acceptable for Packet 1; revisit when Packet 2 routes resolved → confirm.

**Observations (not defects):**
- `resolved_with_warnings` mounts a `role="status"` banner in addition to the announcer. This is spec-mandated (section 2) and matches the existing CompletenessBanner idiom — intended layering of the extra warning detail, not a double-announce bug. The announcer/warning-banner pairing is consistent and honest.
- The cloned `Meta` primitive (AddressResolutionScreen.tsx:69-77) adds a `if (!correlationId) return null` guard the FailureState.tsx original (lines 40-48) lacks (the original renders an empty `<code>`). Markup is byte-identical when a correlation id is present; the guard is a benign honesty improvement (no empty reference id). `FailureTitle` is byte-identical; `RetryButton` differs only in the address-appropriate label.
